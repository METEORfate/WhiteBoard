# 协作白板 · 支持离线编辑与多人实时同步

一个**零依赖**的多人实时协作白板。两个人同时改同一块画布，谁也不会覆盖谁；断网了照样能画，网一恢复自动补齐。

```
node server/index.js   →   打开 http://localhost:8787
```

没有 `npm install`，没有构建步骤，没有 `node_modules`。服务端只用 Node 内置模块，连 WebSocket 的 RFC 6455 握手与分帧都是自己写的。

---

## 为什么值得看

大多数「实时协作」demo 在断网那一刻就散架了：本地还在改，服务端也在改，重连时要么整份覆盖（丢数据），要么把离线操作重放一遍（重复图形）。这个项目把这几件事拆开处理：

| 问题 | 这里的做法 |
| --- | --- |
| 两人同时改同一图形 | **字段级 LWW-Register** —— 你改颜色、我挪位置，两个修改都保留 |
| 断网期间的编辑 | 本地乐观应用 + localStorage 队列，界面从不等待网络 |
| 重连时的对齐 | 快照全量替换 → 叠回未确认队列 → 按 `clientSeq` 顺序重放 |
| 重复投递 | 服务端按 `opId + 内容指纹` 幂等去重，同一条 op 应用一万次结果不变 |
| 删除被「复活」 | 删除只打**墓碑**（`deleted=true`），永不物理删除 |
| 脏数据 | 白名单字段 + clamp/取整/颜色正则/码点计长，客户端与服务端共用同一份校验代码 |
| 撤销在协作里失效 | 撤销不重放旧 op，而是用「当前版本 +1」生成新 op，否则版本落后会被服务端拒掉 |

一致性不是靠服务端「算对」来保证的，而是靠合并函数本身满足**交换律、结合律、幂等性**——所以 op 以任何顺序、重复任意次到达，两端都会算出同一个结果。服务端只负责三件事：给 op 排一个单调序号、去重、把越界值归一化。

## 功能

**图形与编辑**

- 矩形、椭圆、文本、画笔四种图形；拖拽创建，实时预览
- 画笔带采样点（最小间距过滤 + 点数上限），选中后缩放会连同笔迹一起缩放
- 选中 / 框选 / 全选（Ctrl+A）；移动、8 方向缩放把手、双击改文本
- 复制 / 粘贴 / 原位再制（Ctrl+C / V / D），粘贴生成新图形而不是重放旧 op
- 图层置顶 / 置底；导出当前画布为 PNG（含画笔笔迹，2 倍图）
- 样式面板：填充（含透明）、描边、线宽、字号
- 删除（Delete）、撤销 / 重做（Ctrl+Z / Ctrl+Shift+Z），拖动整体算一步
- 画布平移（空格拖拽 / 中键拖拽）与缩放（滚轮 / Ctrl+±/0）

**协作**

- WebSocket 实时双向同步，广播含发起者（保证发起者与旁观者看到同一序列）
- 多房间：`?room=` 即房间号。**没有房间号时进入落地页**（创建房间 / 粘贴链接加入 / 最近打开），不会静默落到任何公共房间
- 邀请：顶栏房间胶囊 → 「邀请协作」弹层，一键复制链接；「换个房间」回到落地页
- 进房间之前就知道会进哪：输入房间号或粘贴链接时实时显示「已存在 · N 人在线 · X 个图形」或「新房间 · 进入后自动创建」；链接里带 `?room=` 也能直接识别
- 房间号大小写归一（`Team` 与 `team` 是同一个房间）；昵称自动生成（`访客-xxxx`）并存在本地，成员列表里显示在线人数

- 多人光标 presence（带昵称与派生颜色）
- 断线自动重连（指数退避 0.5s→15s + 抖动），心跳 15s / 32s 判死
- 离线编辑队列，localStorage 持久化，刷新页面不丢
- 重连后按令牌桶限速重放（30 条/秒、32 条在途），几百条离线操作也不会被服务端限流吞掉
- 同步调试面板：连接状态、`serverSeq`、队列深度、收发计数、`bootEpoch`、重连次数、实时日志

**房间治理**

访客能自己建房之后，「房间」本身就成了要管的资源：

- **大小写归一**：房间号同时是内存 key 和磁盘文件名，而 NTFS / APFS 大小写不敏感。统一小写后，`?room=Team` 与 `?room=team` 不会变成「两个房间共用一个日志」
- **空闲回收**：无人在线且 30 分钟无操作，房间从内存卸载（磁盘 jsonl 保留，下次进入自动加载），进程内存不随房间数无限增长
- **建房配额**：单 IP 每小时 60 个新房间、内存驻留上限 500 个；进**已有**房间不消耗配额——分享链接本来就是给一群人点的
- **探测限速**：`GET /api/rooms/:id` 只回答「在不在 / 几个人 / 多少图形」，不返回内容，并按 IP 限流，避免被当成房间号枚举器
- **`/api/stats` 仅限本机**：房间清单等于绕过「房间号即凭证」，非回环地址一律 403

断网这一段不是调用应用内的「模拟断网」开关，而是在 A 页与服务器之间挂一个可控 TCP 代理：`cut()` 把在途连接全部 RST，并掐掉之后每一个新连接，所以断网期间的重连是**真的失败**，恢复后是**真的重连**，离线队列才被真正考验到。同一次运行里还会断言「断网后新请求确实失败」，避免测成一条假路径。

每个用例用独立的临时 `DATA_DIR`，互不干扰，也不会污染仓库里的 `data/`。

## 常见问题

**启动报 `EADDRINUSE: address already in use 0.0.0.0:8787`**

上次的实例没关干净。现在的默认行为是自动顺延到 8788、8789…（最多 10 个），启动日志会写实际地址；10 个全被占用才会报错退出，并打印可复制的排查命令。

想固定端口（部署 / 反向代理 / CI）就设 `STRICT_PORT=1`，冲突即失败退出：

```powershell
# 看谁占了端口并结束它（PowerShell）
Get-NetTCPConnection -LocalPort 8787 -State Listen | % { Stop-Process -Id $_.OwningProcess -Force }

# 或者换个端口 / 让系统分配
$env:PORT=9000; node server/index.js
$env:PORT=0;    node server/index.js     # 随机空闲端口，启动日志里有实际地址
```

**页面白屏 / 改了代码没生效**

多半是浏览器缓存了旧的 ES Module。`Ctrl+Shift+R` 强刷；或 F12 看控制台是否有 404（说明模块路径错了，不是缓存问题）。

**画布上有上一轮演示的图形，想清空**

点顶栏房间胶囊 → 「换个房间 →」回到落地页，在那里新建一个空房间。也可以直接手改地址：`?room=demo2`。要彻底清掉某个房间的数据，停掉服务后删 `data/<roomId>.jsonl`。

**房间号能用中文吗**

不能。房间号会变成磁盘文件名，协议只接受 `[A-Za-z0-9_-]`。落地页输入中文房间名时界面会提示，并直接给你分配一个随机房间号——**不会**把你悄悄丢进某个公共房间。想保留可读性就用拼音或英文：`?room=chanpin-pingshen`。

**直接打开首页会进哪里**

进落地页（`/`），由你选择「创建房间」或「加入房间」。只有地址里带 `?room=xxx` 才会直接进白板——分享链接和刷新页面都走这条路径。


**两个窗口画的图形互相看不到**

看顶部状态条：不是「已连接」就点一下浏览器窗口（获得焦点会触发立即重连）；仍是「离线」则检查调试面板里的「模拟断网」是否被勾上了。

## 设计要点（详细推导见 `docs/项目说明.md`）

**1. 每个字段是一个独立的 LWW-Register**

图形不是整体比较，而是每个字段各自带一个全序戳 `(ver, clientId, opId)`，合并时逐字段取最大。这样「A 改颜色」和「B 挪位置」是两个不相交的字段集合，两个都保留——这是最直观能感受到「字段级合并比整体覆盖好」的场景。

**2. 全序戳让合并与到达顺序无关**

`(v, c, o)` 三元组按字典序比较，任意两条 op 都有确定顺序且无并列（`opId` 是 uuid）。因此 `merge(a,b) = merge(b,a)`、`merge(merge(a,b),c) = merge(a,merge(b,c))`、`merge(a,a) = a`。这三条性质保证了收敛——不需要任何协调协议。

**3. 删除是墓碑，不是物理删除**

离线端手里还有这个图形，如果服务端物理删掉，离线端重连时会把它的 `create` 重放回来，图形「复活」。所以删除只是把 `deleted` 字段写成一个更高版本的 `true`，墓碑参与合并。

**4. `lastAppliedSeq` 只由快照和广播推进，绝不由 ack 推进**

如果 ack 也推进序号，那么 ack(seq=10) 会把还在途的 seq=9 当成「已应用」而丢弃，产生永久缺口。这条规则写在 `net.js` 顶部注释里，因为破坏它只需要一行代码。

**5. 服务端先落盘再广播**

广播出去的 op 一定是已经持久化的。否则崩溃恢复后客户端认为自己收到过某个 `seq`，而服务端重放时没有它——两端对同一个序号对应哪个状态产生分歧。

**6. 撤销生成新 op，而不是重放旧 op**

重放旧 op 会带着旧版本号，服务端按逐字段 LWW 会直接丢弃它，用户点撤销却毫无反应。所以撤销用「当前最大版本 + 1」重新构造一条反向 op，撤销本身也是可同步、可收敛的。

**7. 离线 op 被判定陈旧时重基一次，而不是丢弃**

`ver` 在入队那一刻就冻结了（重试必须同戳，否则两端分叉），但离线端的本地副本可能落后好几版，算出的 `ver` 必然输给在线端。若直接丢弃，用户在离线期间的修改就凭空消失了——而它在因果上明明是更晚发生的。所以 `accepted:false` 时不只回滚，还会用 `max(本地, 权威)+1` 和新 `opId` 重发一次：语义从「版本大者胜」变成「重连后的写入算一次新写入」，只重试一次以避免活锁，删除不参与（避免「删了又活」）。

**8. 重放要走令牌桶，不能把整队灌进去**

服务端限流是 60 条/秒、突发 120。重连时如果一次性 flush 整个离线队列，超出的部分会被服务端丢掉——如果服务端还「静默丢弃」，客户端既不重试也不报错，待发队列就永远清不空（实测 200 条只到 129 条）。所以客户端按 30 条/秒发、最多 32 条在途，服务端对被限流的消息**必须回 `RATE_LIMITED`**，客户端收到后退避重发（同 `opId` 重发是幂等的）。

## 已知限制

- **单进程内存态**：房间状态在进程内存里，只适合单实例部署。多实例需要把广播改为 Redis Pub/Sub 或粘性会话，持久化换数据库。
- **无鉴权**：房间号即访问凭证，谁拿到链接谁就能进。生产环境需要接入身份系统并在 `hello` 阶段校验。
- **房间没有归属与过期删除**：任何人知道房间号就能进、能改；空闲房间只从**内存**卸载，`data/<roomId>.jsonl` 会一直留着，需要定期手工清理或另写清理任务。配额（`MAX_ROOMS` / `ROOM_CREATE_PER_HOUR` / `ROOM_TTL_MS`）只是防滥用的闸，不是权限模型。
- **字段级 LWW 不是「意图保留」**：两人同时拖同一个图形，最终位置是版本大的那个赢，而不是把位移叠加。离线场景靠 rebase 补偿（重连后的写入算新写入），代价是它可能覆盖对方在线期间的修改；要做到双方向都保留需要 CRDT 的位置类型（如 Yjs 的 `Y.Map` + 相对定位），复杂度高一个量级，本项目选择了明确可解释的取舍。
- **文本编辑是整串替换**：两人同时编辑同一段文本，LWW 会让后写的整段覆盖先写的。字符级协同需要 OT 或序列 CRDT。
- **历史无限增长**：`seen`（去重表）有上限并做 FIFO 淘汰，JSONL 超过阈值会压缩成快照，但没有做增量快照或时间旅行。
