# 协作白板：同步协议、离线方案与冲突处理

## 一、同步协议

### 通道

单条 WebSocket 连接，路径 `/ws`，RFC 6455，只收发文本帧，单帧上限 64 KiB。HTTP 只用于静态资源、`/healthz`、`/api/stats`、`/api/rooms/:id` 探测，不参与同步。

### 消息

| 类型 | 方向 | 作用 |
| --- | --- | --- |
| `hello` | C→S | 进房，带 roomId、clientId、sessionEpoch、name、lastSeq |
| `welcome` | S→C | 权威快照：bootEpoch、serverSeq、全部图形、成员名单 |
| `op` | C→S | 提交一次编辑 |
| `ack` | S→C | 单条 op 的处理结果，含 accepted、duplicate、seq、shape |
| `presence` | 双向 | 成员加入 / 离开 / 光标移动 |
| `resync` | S→C | 要求客户端全量重拉 |
| `error` | S→C | 拒绝，携带 code、message、opId |
| `ping` `pong` | 双向 | 心跳 |

### 时序

```
C → S   hello
S → C   welcome（先发快照，再标记 joined，期间产生的广播进缓冲补发）
C → S   op
S → C   op（广播给房间内所有人，含发起者）
S → C   ack（仅回给发起者）
C ⇄ S   presence、ping/pong
```

服务端处理一条 op 的顺序固定为：校验与归一化 → 房间与身份绑定 → opId 幂等去重 → clientSeq 高水位 → 版本上界 → 逐字段合并 → 落盘 → 广播。

### 序号与顺序

`serverSeq` 由服务端分配，在房间内单调递增，是广播帧的全局顺序。

客户端维护 `lastAppliedSeq`，只由 `welcome` 的快照和 `op` 广播推进，不由 `ack` 推进。收到广播时：`seq` 不大于 `lastApplied` 则丢弃；出现缺口（不等于 `lastApplied + 1`）则断开重连拉全量；`bootEpoch` 与当前不一致同样全量重拉。

### 幂等

服务端维护 `opId → 内容指纹` 表。同一 opId 重复到达且指纹相同，回放上次结果、不重复应用；指纹不同则判定为异常，拒绝并要求重同步。

### 流控

服务端连接级令牌桶：60 条/秒，突发 120。超限回 `RATE_LIMITED`，不静默丢弃。

客户端发送侧：30 条/秒，最多 32 条在途，单条 5 秒未收到 ack 则移出窗口重发。

心跳间隔 15 秒，32 秒未收到任何消息判定连接失效并主动断开重连。

## 二、离线方案

### 本地优先

所有编辑先在本地生效，再进入待发队列，界面不等待网络。断网时队列持续累积。

### 队列持久化

| 键 | 内容 |
| --- | --- |
| `wb:doc:<room>:<clientId>` | 图形副本 |
| `wb:queue:<room>:<clientId>` | 待发 op 队列 |
| `wb:seq:<room>:<clientId>` | clientSeq 高水位 |

三个键都带 clientId，同一浏览器多标签页互不覆盖。页面隐藏或卸载前强制落盘，绕过 120ms 写盘防抖。

### 断网与重连

连接状态：`idle → connecting → syncing → online ⇄ offline`。`syncing` 期间不发 op，编辑照常入队。

断线后按指数退避重连：0.5 秒起，15 秒封顶，附加随机抖动。浏览器触发 `online` 事件、页面重新可见、或用户手动重试时立即重连，不等退避。

### 重连后的对齐

1. 发 `hello`，携带本地 `lastSeq`。
2. 收 `welcome`，用快照整体替换本地文档。
3. 把待发队列重新叠回快照之上（`replayPendingLocally`），避免已画的图形闪一下再出现。
4. 按 `clientSeq` 升序重放队列。

服务端不做"断点续传"：只要 `bootEpoch` 变化或 `seq` 有缺口，一律全量拉取。

### 重放节流

重放走与在线发送相同的通道：30 条/秒、32 条在途、5 秒 ack 超时重发。`opId` 幂等，重发安全。

### 版本号冻结

op 的 `ver` 在入队那一刻确定，重试与重放都不重算。重算会让同一个逻辑操作在两端得到不同的戳，进而分叉。

## 三、冲突处理

### 粒度

冲突以字段为单位裁决。图形的每个字段是一个独立的 LWW-Register，各自携带戳 `(v, c, o)`，即版本号、clientId、opId。

### 裁决规则

戳按字典序比较：先比 `v`，再比 `c`，最后比 `o`。合并时逐字段取较大者。

同一戳且来自服务端时（客户端应用广播或快照），采用服务端值，用于吸收服务端的取整与越界钳制。

### 各类冲突的结果

| 场景 | 结果 |
| --- | --- |
| 并发修改不同字段（A 改颜色、B 移动） | 两个修改都保留 |
| 并发修改同一字段 | 戳大者胜，两端结果一致 |
| 并发修改同一图形，一方删除 | 比较 `deleted` 字段的戳，版本高者生效 |
| 删除后收到陈旧修改 | 墓碑版本更高，修改被丢弃 |
| 同 id 修改图形类型 | 服务端拒绝（`TYPE_CONFLICT`） |
| 同 opId 不同内容 | 服务端拒绝并要求重同步（`OPID_CONFLICT`） |

### 离线冲突

离线期间基于旧版本产生的 op，重连后必然输给在线端的更高版本。服务端合并后无状态变更，回 `ack{accepted:false, shape:权威态}`。

客户端处理分两步：先采用权威态覆盖本地，再重基一次——换新 opId、以 `max(本地版本, 权威版本) + 1` 作为新版本重发。语义上等同于"重连后的这次写入算一次新写入"。只重试一次，避免两端反复覆盖；删除不参与重基。

### 撤销

撤销与重做不重放旧 op，而是以当前版本加一构造一条新的反向 op。旧 op 版本落后会被合并规则直接丢弃，重放等于无效。

### 收敛依据

逐字段合并等价于按戳取最大值。取最大值满足交换律、结合律、幂等性，因此合并结果只取决于收到的 op 集合，与到达顺序和重复次数无关。所有副本收到相同集合后必然一致，不依赖服务端的处理顺序。

### 已知限制

同时拖动同一图形，最终位置为戳大者，不叠加位移。同时编辑同一段文本，为整串替换，不做字符级合并。这两项需要位置型或序列型 CRDT，本项目未实现。
