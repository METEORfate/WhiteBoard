# 演示脚本

> 面向现场演示与录屏。核心目标：**90 秒内让人相信「这个白板在断网、并发、重连三种情况下都不丢数据」**。
>
> 演示的难点不是功能多，而是让观众**看见**看不见的东西（队列、版本号、收敛）。所以全程开着调试面板。

---

## 一、演示前准备

### 1. 启动

```bash
cd whiteboard
node server/index.js
# → 白板服务已启动 http://localhost:8787  (bootEpoch=m3k9x2-9c1d)
```

### 2. 窗口布局

先打开 `http://localhost:8787` 进落地页，点「创建并进入」拿到一个房间链接（形如 `http://localhost:8787/?room=k3f9a2b7`），
再开**两个**浏览器窗口（不要用标签页，窗口并排才能同屏看到），都打开这条链接。

> 想直接用固定房间号，也可以在落地页「加入房间」里粘贴 `http://localhost:8787/?room=demo`——`data/demo.jsonl` 里那批演示图形会直接出现。

窗口 A 放左边，窗口 B 放右边，各占一半屏。两个窗口都点右上角 📈 图标**打开同步调试面板**。

> **为什么要两个窗口而不是两个标签页**：标签页切换会触发 `visibilitychange`，虽然不影响功能，但录制时看不到两边同时变化的效果。另外 `clientId` 存在 `sessionStorage`，两个标签页天然是两个身份——这点可以顺带讲。

### 3. 检查清单

| 检查 | 怎么看 |
| --- | --- |
| 两个窗口状态条都是绿色「已连接」 | 顶部右侧 |
| 两端成员列表各有 2 个成员 | 顶部成员头像 |
| 两端 `serverSeq` 相同 | 调试面板 |
| 调试面板「模拟断网」未勾选 | 调试面板底部 |
| 画布是空的（若上次演示有残留，点「新建房间」拿一个干净的随机房间） | — |

### 4. 一键重置

如果上一轮演示留下了数据：

```bash
# 最省事：点顶栏「新建房间」，随机一个空房间，不用重启
# 要彻底清掉某个房间的数据，停掉服务后删它
rm -f data/demo.jsonl
node server/index.js
```

## 二、90 秒分镜

> 旁白按「先讲现象，再讲原理」组织。观众先看到结果，才会关心实现。

### 0:00–0:10　开场

**操作**：两个窗口并排，鼠标在两个窗口之间移动一下。

**旁白**：
> 这是一个支持多人实时协作的白板。两个窗口是两个独立的客户端，同一个房间。注意两边的光标——你能看到对方的光标和名字。

**看点**：presence 光标（这是最直观的「实时」信号）。

---

### 0:10–0:30　基础协作

**操作**：
1. 在 A 画一个矩形（按 `R` 拖拽）
2. 在 B 画一个椭圆（按 `O` 拖拽）
3. 在 A 用文本工具写一句「hello」（按 `T` 点击输入）
4. 在 A 按 `P` 切画笔，随手画一条曲线（笔迹会带采样点，选中后能整体缩放）

**旁白**：
> 四种图形：矩形、椭圆、文本、画笔。任何一端画的东西，另一端立刻出现。拖动、缩放、改样式、删除都是实时的。

**看点**：B 上的矩形是「无中生有」出现的；A 上的椭圆同理。

**操作补充**（可选，时间够就做）：在 A 选中矩形，把填充色改成黄色 → B 上同步变色。

---

### 0:30–0:50　★ 断网继续编辑

**操作**：
1. 在 A 的调试面板勾选「**模拟断网**」
2. 指一下 A 的状态条变红「离线」、B 的状态条仍是绿色
3. 在 A 上画 2 个矩形（动作要明显，画大一点）
4. 指一下 A 的调试面板：「待发队列 **2**」，图形数 5
5. 指一下 B：「B 还是 3 个图形，什么都没收到」

**旁白**：
> 现在 A 断网了。注意状态条变红，但**画布完全正常**——可以继续画、继续拖、继续撤销。这些操作全部进入本地待发队列，存在 localStorage 里，刷新页面都不会丢。
>
> 右边的 B 完全不知道 A 在干什么，因为它一个字节都没收到。

**看点**：这是整场演示最关键的一幕。**必须让观众看到「A 能画」和「B 没收到」同时成立**。

**如果被问「队列在哪」**：打开 A 的 DevTools → Application → Local Storage → `wb:queue:demo`，能看到 2 条 op 的 JSON。

---

### 0:50–1:10　★ 重连自动合并

**操作**：
1. 取消勾选「模拟断网」
2. 等 1～2 秒（状态条变绿）
3. 指 B：刚才 A 断网时画的 2 个图形出现了
4. 指两边调试面板：`serverSeq` 相同、「待发队列 0」
5. （可选）在控制台跑一行比对：

```js
// 分别在两个窗口的控制台执行，输出应完全相同
JSON.stringify(__board.store.digest())
```

**旁白**：
> 网络恢复，自动重连——不需要点任何按钮。断网期间的操作按顺序重放，两边的 `serverSeq` 追平，待发队列清零。
>
> 这里最容易出的 bug 是「重放导致重复图形」或者「快照覆盖掉本地修改」。我们的做法是：先用服务端快照整体替换，再把未确认的队列叠回去，然后按 `clientSeq` 顺序重发，服务端用 `opId` 做幂等去重——同一条 op 应用一万次结果都一样。

**看点**：`serverSeq` 两边一致 + 队列归零 + 图形数一致。三个数字同时对上，比任何口头保证都有力。

---

### 1:10–1:30　★ 并发改不同字段

**操作**：
1. 确保两端都选中**同一个**矩形
2. 在 A 上拖动这个矩形到新位置（**拖完再松手，不要拖一半**）
3. 几乎同时（或者紧接着）在 B 上把这个矩形的填充色改成另一个颜色
4. 指两端：位置变了**而且**颜色也变了

**旁白**：
> 现在两个人同时改同一个图形：A 改位置，B 改颜色。如果按「整个图形谁后写谁赢」，一定有一个人的修改会消失。
>
> 我们做的是**字段级**合并——每个字段独立带版本号，位置和颜色是两个不同的字段，互不干扰。所以两个修改都保留了。

**看点**：这是最能体现设计深度的一幕。观众会预期「有一个被覆盖」，结果两个都在。

**注意**：这一步要真的让两个操作「并发」才有说服力。如果时间不好控制，可以在 A 拖动的同时让 B 点颜色——因为拖动有 60ms 节流，很容易重叠。

**如果被问「同一个字段同时改呢」**：诚实回答——版本号大的赢，另一个被覆盖，但可以撤销回来。见 Q&A 第 4 题。

---

### 1:30–1:40　收尾

**操作**：点一下「复制链接」，说明换个浏览器/设备打开同一个链接就能加入。再点一下「新建房间」，说明访客也能自己开一块新白板——房间号是随机生成的，不用注册。

**旁白**：
> 房间号在 URL 里，复制链接就能邀请别人；想开新的就点「新建房间」，随机房间号，不需要注册。顺带一提：在房间输入框里打错字时，提示条会明确告诉你这是个「新房间」——不会让你以为数据丢了。整个项目零依赖，`node server/index.js` 就能跑，WebSocket 的 RFC 6455 握手和分帧是自己实现的。

## 三、三个「杀手锏」的台词卡

如果时间被压缩到 60 秒，只讲这三个。

### ① 断网继续画（30 秒）

> 「断网了，状态条红了，但我还能画。为什么？因为所有编辑**先本地生效**，再进队列。界面从来不等网络。
>
> 你可能会问：那网络回来了怎么办？——先拉全量快照，再把队列叠回去，然后按序号重发。服务端用 `opId` 去重，重复发一百次也只应用一次。」

### ② 字段级合并（20 秒）

> 「我改颜色、他挪位置，两个都在。因为合并粒度是**字段**不是图形。每个字段带自己的版本号，位置和颜色是两个不相干的字段，谁也覆盖不了谁。」

### ③ 收敛性（10 秒）

> 「一致性不靠服务端算对，靠合并函数满足交换律、结合律、幂等性。所以消息以任何顺序到达、重复多少次，所有客户端最终都会算出同一个结果。这是数学保证，不是工程约定。」

## 四、答辩 Q&A

### Q1：为什么不用 Yjs / Automerge？

**答**：可以用，而且会更省事。但这两个库会把「op 怎么比较、怎么合并」藏在 API 后面，而这道题的核心考点恰恰是那部分。自己实现字段级 LWW 大约 145 行（`shared/merge.js`），换来的是每一行都能解释、能单测、能在答辩时画出比较链。

另外 Yjs 是**序列 CRDT**（为文本设计），用在白板这种「扁平对象集合」上属于用大炮打蚊子，而且它的 `Y.Map` 语义和「字段级 LWW」并不完全一样（Yjs 的 Map 也是 LWW，但版本向量机制复杂得多）。

如果项目要上生产、要支持富文本协同编辑，我会直接用 Yjs——那时候省下来的时间应该花在业务上。

### Q2：为什么用 LWW 而不是 OT？

**答**：OT 需要一个中心化的转换函数，且转换函数必须对所有操作对都正确——这是出了名的难写对（Google Docs 的 OT 论文有几十页在讨论各种边界情况）。而且 OT 的转换结果依赖操作顺序，服务端必须严格串行。

LWW 不需要转换函数，只需要一个全序比较。代价是「并发改同一字段」时会丢一个修改，但白板场景里这个代价可接受——用户拖同一个图形到两个位置的场景本来就少见，而且撤销能救回来。

**关键的工程判断**：LWW 的错误是「可预期、可解释、可撤销」的，OT 的错误是「偶发、难复现、可能永久分叉」的。前者对用户友好得多。

### Q3：字段级 LWW 和整图形 LWW 差在哪？

**答**：差在「并发改不同字段」这一种场景。

- 整图形 LWW：A 改颜色、B 挪位置 → 版本大的那个赢，另一个的修改**整体消失**
- 字段级 LWW：两个字段不相交，**都保留**

实现上只差一个「合并粒度」，但用户感知差别巨大。现场演示第 3 幕就是为了说明这个。

代价是存储变大（每个字段带三元素戳）和代码稍复杂。

### Q4：两个人同时拖同一个图形，会怎样？

**答**：版本号大的赢，另一个被覆盖。这不是 bug，是 LWW 的语义。

补偿手段有三个：
1. **撤销仍然有效**——被覆盖的一方按 Ctrl+Z 会生成一个版本更高的反向 op，一定生效
2. **拖动只提交节流点**（60ms），不逐帧发 op，减少无意义的版本竞争
3. **一次拖动只登记一条撤销记录**，撤销体验符合直觉（不会只回退一个节流点）

要做到真正的「位移叠加」需要 CRDT 的位置类型（相对定位 + 意图保留），复杂度高一个量级。这是一个明确的取舍，写在文档的「已知不足」里。

### Q5：服务端重启会怎样？

**答**：客户端会全量重拉，用户无感。

机制是 `bootEpoch`：服务端每次启动生成一个新的随机字符串，广播和快照都带它。客户端发现收到的 `bootEpoch` 和自己记录的不一致，就知道服务端重启过，立刻 `_forceResync`——丢弃增量状态，重新拉全量快照。

持久化是 JSONL 追加写，每行是某个图形在某时刻的**全量**状态（不是 patch），所以重放时后写覆盖前写就得到最终状态，不需要排序。

崩溃留下的半行 JSON 会在加载时被识别并跳过，然后立刻用内存态原子重写文件（写临时文件 → rename），避免「坏行 + 新数据粘成一行新的坏数据」。

### Q6：为什么 `lastAppliedSeq` 不能由 ack 推进？

**答**：会造成永久丢帧。

假设客户端连发 op₁、op₂，服务端产生 seq=1、seq=2。如果 ack(seq=2) 先到，`lastApplied` 被推到 2；然后广播 seq=1 到达，被 `if (msg.seq <= lastApplied) return` 当成重放丢弃——op₁ 的修改永久丢失，两端分叉。

正确做法：**广播负责推进序号，ack 只负责从待发队列摘除 op**。这条规则写在 `net.js` 顶部注释里，因为破坏它只需要改一行代码。

### Q7：如果两个客户端用了同一个 clientId 会怎样？

**答**：仍能收敛，但体验不好。

全序戳是 `(ver, clientId, opId)`，`clientId` 相同还有 `opId` 兜底，所以比较仍是全序，不会分叉。但裁决结果取决于 `opId` 的字典序——用户会看到「图形莫名跳回另一个位置」。

所以 `clientId` 存在 `sessionStorage`（每标签页独立），从根上避免同浏览器双开时共用 id。

### Q8：幂等去重表有上限，淘汰之后重复的 op 会不会出问题？

**答**：不会，因为合并本身是幂等的。

去重表（`seen`，50000 条上限，FIFO 淘汰）只是**性能优化**——避免重复应用同一条 op 做无用功。即使表里没有某条 op、它被重新应用一次，`mergeOp` 逐字段取最大值的结果和只应用一次完全相同。

这是幂等性带来的额外好处：正确性不依赖任何有状态的去重机制。

### Q9：删除为什么不用物理删除？

**答**：会让离线端把图形「复活」。

离线端手里还有这个图形，如果服务端物理删掉，离线端重连时重放它的 `create`，服务端会当成新图形接受——已删除的图形回来了。

所以删除只是把 `deleted` 字段写成更高版本的 `true`，墓碑参与合并。离线端的旧 op 版本更低，合并时被丢弃。

墓碑也支持复活：如果后续有更高版本的 `deleted=false`（撤销删除就是），图形正常回来。语义自洽。

### Q10：怎么保证「不损坏数据结构」？

**答**：三层。

1. **数学层**：合并函数满足交换律、结合律、幂等性 → 任何到达顺序、任意重复次数都收敛（`tests/merge.test.js` 直接验证这三条性质）
2. **协议层**：白名单字段 + 类型 + 范围校验，脏数据进不来（`tests/protocol.test.js` 13 个用例覆盖边界）
3. **持久层**：先落盘再广播、原子压缩、尾行截断修复 → 崩溃不会留下不一致状态

另外服务端是**串行**处理 op 的（Node 单线程 + 同步 apply），不存在「两个 op 同时修改一个 Map」的竞态。

### Q11：为什么不直接用 `ws` 库？

**答**：两个原因。

一是**题目要求展示协议理解**，自己实现才能讲清楚握手魔数、帧头布局、掩码、分片这些细节。

二是**这个决定帮我们抓到了两个 bug**——其中一个就是握手 GUID 写错（`C5AB0DC85B11` 写成 `5AB0DC85B11F`），因为测试客户端和服务端共用同一个错误常量，64 个单测全绿但任何真实浏览器都拒绝握手。如果用了 `ws` 库，这个错误根本不会存在，但也就不会去想「怎么验证一个协议实现是对的」这个问题。

修复方式是用 RFC 6455 的**官方测试向量** + Node 内置 `WebSocket`（undici 实现）做真客户端验证——测试的价值取决于它有多「不同」，而不是它有多「多」。

### Q12：这个项目的技术难点是什么？

**答**：不是 WebSocket，也不是画布渲染，而是**「怎么证明它是对的」**。

WebSocket 和 Canvas 都有大量资料，照着写就行。但「两个客户端在任意时序下最终会不会一致」这个问题，靠跑 demo 是证明不了的——你得把合并函数的三条代数性质单独抽出来验证，得构造乱序、重复、并发、断网、重启各种时序去撞它。

我们最终的测试是 96 个单元/集成用例 + 21 项端到端，其中大部分用例不是为了「证明功能能跑」，而是为了「证明特定时序下不会分叉」。

## 五、翻车预案

演示现场最怕的不是功能弱，是卡住。预案如下：

| 情况 | 处理 |
| --- | --- |
| 端口被占用 | **默认会自动顺延**（8787→8788…），看启动日志里「白板服务已启动 http://localhost:XXXX」的实际地址，URL 跟着改即可。要固定端口：`$env:PORT=9000; node server/index.js`（PowerShell） |
| 页面白屏 | F12 看控制台；多半是缓存了旧的 `main.js`，Ctrl+Shift+R 强刷 |
| 两端不同步 | 看调试面板状态条：若不是「已连接」，点一下浏览器窗口让它获得焦点（会触发 `retryNow`） |
| 画布有上一轮残留 | 点顶栏房间胶囊 →「换个房间 →」回落地页新建一个空房间；或把 URL 改成 `?room=demo2` |
| 断网演示后忘记恢复 | 调试面板「模拟断网」勾选框，一定记得取消 |
| 演示机没有 Chrome | 任何 Chromium 内核浏览器都可以（端到端脚本需要 Chrome，但手动演示不需要） |
| 完全起不来 | 提前录一段 90 秒的屏，作为兜底播放 |

**最重要的一条**：演示前**完整走一遍流程**，特别是「断网 → 继续画 → 恢复」这三步。这一步涉及状态切换，是最容易因为环境差异出问题的地方。
