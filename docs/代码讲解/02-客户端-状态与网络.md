# 02 客户端：状态与网络

上一篇讲的是"规则"，这一篇讲**这些规则被谁执行**。客户端有两个核心对象：

```
store.js   本地文档：所有图形的当前状态、待发队列、撤销栈
net.js     连接：WebSocket 生命周期、心跳、重连、消息分发
main.js    装配：把上面两个和画布、交互、UI 接起来
```

一句话概括它们的分工：

> **store 负责"我认为世界是什么样"，net 负责"让世界变成这样"。**

---

## client/js/store.js（本地文档 + 待发队列 + 撤销栈）

### 它解决什么问题

用户拖一下鼠标，界面上必须**立刻**看到变化。但网络可能需要 50ms、可能断着、可能永远不回。

如果等服务器确认再改界面，拖动会变成"卡一下、跳一下"。所以这里的策略是：

**先改本地（乐观更新），再把改动放进队列慢慢发。**

这个文件要同时管三件事，而且它们必须一致：

| 职责 | 数据结构 | 出错会怎样 |
| --- | --- | --- |
| 当前文档 | `Map<shapeId, shape>` | 界面显示错、刷新白屏 |
| 待发队列 | `Array<op>` | 断网期间的编辑丢失 |
| 撤销栈 | `Array<{label, items}>` | 撤销错乱、退不回去 |

### 代码逐段讲

**构造函数：为什么参数要解构**

```js
export class DocStore {
  constructor({ roomId, clientId, sessionEpoch, clientSeq = 0, onChange, onOp, onLog }) {
```

调用时是这样：

```js
new DocStore({ roomId, clientId, identity.sessionEpoch, onChange: ..., onOp: ... })
```

**为什么不用位置参数？** 因为六个参数里有三个是可选的，位置参数会变成 `new DocStore(roomId, clientId, epoch, 0, null, fn, fn)`——读代码的人完全不知道 `null` 是哪个。解构参数让每个值自带名字，还能只传想传的。

`clientSeq = 0` 是默认值语法：调用方不传就用 0。

**回调的兜底写法**

```js
this.onChange = onChange || (() => {});
```

如果没传 `onChange`，就给一个空函数。这样后面调用 `this.onChange()` 永远不会因为 `undefined is not a function` 崩掉。

**为什么不写成 `if (this.onChange) this.onChange()`？** 因为那要在每个调用点都写判断，漏一处就崩。**兜底一次，处处安全。**

**localStorage 为什么要包 try/catch**

```js
function writeJSON(key, value) {
  try {
    localStorage.setItem(key, JSON.stringify(value));
  } catch (err) {
    console.warn('本地存储写入失败', err);
  }
}
```

`localStorage` 有四种情况会抛异常：

1. Safari 无痕模式：`setItem` 直接抛 `QuotaExceededError`
2. 存储空间满了（默认 5MB）
3. 用户禁用了站点数据
4. 某些浏览器的隐私设置

**如果这里不 catch，一次存储失败就会让整个 `applyLocal` 抛出，画布不再重绘**——用户看到的是"画不出东西了"，而且控制台只有一行看不懂的报错。

**存储 key 为什么写成函数**

```js
const DOC_KEY = (room) => `wb:doc:${room}`;
const QUEUE_KEY = (room) => `wb:queue:${room}`;
```

因为一个浏览器可能同时开着多个房间。key 带上 `roomId`，房间之间互不干扰。

写成箭头函数是"惰性求值"：每次用的时候才拼字符串，而不是启动时算一次。

**`_restore`：启动时恢复**

```js
_restore() {
  const cached = readJSON(DOC_KEY(this.roomId), []);
  for (const raw of cached) {
    const r = normalizeShape(raw);
    if (r.ok) this.shapes.set(r.shape.id, r.shape);
  }
  ...
}
```

注意 `if (r.ok)`：**从 localStorage 读出来的数据也要校验**。因为用户可能手工改过、可能是旧版本代码写的、可能存到一半断电了。一条坏数据不该让整个白板打不开。

**`clientSeq` 为什么要取三个值的最大值**

```js
const savedSeq = Number(localStorage.getItem(SEQ_KEY(this.roomId)) || 0);
const maxQueued = this.pending.reduce((m, op) => Math.max(m, op.clientSeq || 0), 0);
this.clientSeq = Math.max(this.clientSeq, savedSeq, maxQueued);
```

三个来源：传进来的、存盘的、队列里最大的。

**为什么要取最大而不是直接用存盘值？** 因为可能发生这种情况：存盘的 `seq` 是 40，但队列里有一条 `clientSeq=42` 的 op（存盘时机差异）。如果从 40 开始，下一条新 op 会是 41——**和队列里已有的 41 撞号**。

服务端按 `(clientId, sessionEpoch)` 维护高水位，序号必须严格递增，撞号会被判为"重放"而拒绝。

`reduce` 的写法值得看一眼：

```js
arr.reduce((m, op) => Math.max(m, op.clientSeq || 0), 0)
```

`reduce` 是"把数组折叠成一个值"。第一个参数是累积器（初始值 0），每轮拿当前元素更新它。这里就是求最大值。

**`_persistDoc` 为什么要防抖**

```js
_persistDoc() {
  if (this._docTimer) return;
  this._docTimer = setTimeout(() => {
    this._docTimer = null;
    this._writeDoc();
  }, DOC_SAVE_DEBOUNCE);   // 120ms
}
```

拖动时每 60ms 产生一条 op，每次都 `JSON.stringify` 整个文档并写进 localStorage，会明显卡顿（localStorage 是同步 API，会阻塞主线程）。

防抖的意思是：**120ms 内连续调用多次，只执行最后一次。**

实现手法是 `if (this._docTimer) return;`——已经排了一个定时器就不再排。

**`flush` 为什么必须存在**

```js
flush() {
  if (this._docTimer) {
    clearTimeout(this._docTimer);
    this._docTimer = null;
  }
  this._writeDoc();
  this._persistQueue();
}
```

防抖有个致命缺陷：**如果用户在 120ms 内关掉页面，那次写入永远不执行。**

所以 `main.js` 里挂了 `pagehide` 和 `beforeunload` 两个事件，在页面消失前强制落盘。

**`list()`：渲染前必须排序**

```js
list() {
  return [...this.shapes.values()]
    .filter(isVisible)
    .sort((a, b) => {
      const za = flatten(a).z;
      const zb = flatten(b).z;
      if (za !== zb) return za - zb;
      return a.id < b.id ? -1 : a.id > b.id ? 1 : 0;
    });
}
```

三步：转数组 → 过滤墓碑 → 按 `z` 排序。

`[...map.values()]` 是把 Map 的迭代器展开成数组，因为 Map 本身没有 `filter`/`sort`。

**为什么 `z` 相同时还要按 `id` 排？** 因为 `Array.prototype.sort` 在比较函数返回 0 时**不保证稳定顺序**（现代引擎是稳定的，但规范不强制）。如果两个图形 `z` 相同，A 电脑可能先画甲后画乙，B 电脑反过来——**两人看到的重叠顺序不一样**。用 `id` 做兜底比较，两端结果必然相同。

**`_nextOp`：op 是在入队那一刻定型的**

```js
_nextOp({ kind, target, patch, ver, shapeType }) {
  this.clientSeq += 1;
  this._persistSeq();
  const op = {
    opId: uuid(),
    roomId: this.roomId,
    clientId: this.clientId,
    sessionEpoch: this.sessionEpoch,
    clientSeq: this.clientSeq,
    kind, target, ver, patch,
    ts: Date.now(),
  };
  if (kind === OP_KIND.CREATE) op.shapeType = shapeType;
  return op;
}
```

两个细节：

1. `this.clientSeq += 1` 之后**立刻** `_persistSeq()`。如果等到发送成功再存，断网期间序号会倒退。
2. `if (kind === CREATE) op.shapeType = shapeType;` —— 只给 create 加类型字段。`patch` 和 `delete` 不需要（服务端已经知道这个图形是什么类型）。

**为什么 op 一旦生成就不能再改？** 文件头注释写得很清楚：

> 所有 op 的 ver 在「入队那一刻」就冻结，重试不会重算。一旦重算，两端对同一个逻辑操作会得到不同的戳，最终状态就会分叉。

想象一下重发时重算 `ver`：本地认为这条 op 是第 8 版，服务端第一次收到时存的是第 6 版，重发时又变成第 9 版——同一条逻辑操作在两端有不同身份，合并函数就没法正确判断谁新谁旧。

**`createShape`：一次原子操作**

```js
createShape({ type, x, y, w, h, ...style }) {
  const id = uuid();
  const patch = {
    x: Math.round(x), y: Math.round(y),
    w: Math.max(2, Math.round(w)),
    h: Math.max(2, Math.round(h)),
    z: Date.now(),
    deleted: false,
    ...style,
  };
  const op = this._nextOp({ kind: CREATE, target: id, patch, ver: 1, shapeType: type });
  this.shapes.set(id, mergeOp(null, op));
  ...
}
```

**`{ type, x, y, w, h, ...style }` 这个解构很有意思**：前面几个是"我知道的字段"，`...style` 是"剩下的全部打包"。

这样调用方可以传任意样式字段（`fill`、`stroke`、`fontSize`），不用在函数签名里一个个列。新增样式字段时这个函数不用改。

`...style` 后面展开到 `patch` 里，**顺序很重要**：如果写成 `{...style, x: ...}`，那么调用方传的 `x` 会覆盖计算出来的 `x`。现在这样写，样式字段不会覆盖几何字段（因为它们不重名，但如果哪天重名了，`style` 会赢——这是有意的，允许调用方覆盖默认值）。

**`mergeOp(null, op)` 是什么意思？** 第一个参数是"当前图形"，传 `null` 表示"这是一个新图形"。`mergeOp` 内部会走 `applyPatch` 从零创建。

**`applyLocal`：所有修改的唯一入口**

```js
applyLocal(id, patch, { record = true, label = '修改' } = {}) {
  const shape = this.shapes.get(id);
  if (!shape) return null;

  const before = flatten(shape);
  const prevPatch = {};
  for (const key of Object.keys(patch)) prevPatch[key] = before[key];

  const op = this._nextOp({ kind: PATCH, target: id, patch, ver: this._versionOf(id) });
  this.shapes.set(id, mergeOp(shape, op));
  ...
}
```

注意第三个参数 `{ record = true, label = '修改' } = {}`：这是"可选对象参数 + 解构默认值"的组合。调用方可以：

```js
store.applyLocal(id, {x: 100});                          // 全部用默认
store.applyLocal(id, {x: 100}, { record: false });       // 不记撤销
store.applyLocal(id, {x: 100}, { label: '移动' });        // 自定义标签
```

比 `applyLocal(id, patch, false, '移动')` 可读得多——尤其当参数有五个的时候。

**`prevPatch` 为什么要从 `flatten(before)` 里取？**

因为撤销需要"改之前的值"。`flatten` 给的是裸值，正好能直接塞进反向 patch。

如果从 `shape.fields[key].val` 取也可以，但 `flatten` 会补默认值——万一某个字段还不存在，取到的是 `def` 而不是 `undefined`，撤销时能正确恢复成默认值。

**`deleteShape`：删除 = 打墓碑**

```js
deleteShape(id, { record = true } = {}) {
  const shape = this.shapes.get(id);
  if (!shape || !isVisible(shape)) return null;

  const op = this._nextOp({ kind: DELETE, target: id, patch: { deleted: true }, ver: this._versionOf(id) });
  this.shapes.set(id, mergeOp(shape, op));
  ...
}
```

`!isVisible(shape)` 这个判断防的是"重复删除"。已经删过的图形再删一次，会产生一条没意义的 op。

**`_versionOf`：版本号怎么算**

```js
_versionOf(id) {
  const shape = this.shapes.get(id);
  return maxVersion(shape) + 1;
}
```

`maxVersion` 遍历这个图形所有字段的戳，取最大的 `v`，然后 +1。

**为什么不用"图形的版本号"这个字段？** 因为字段级合并下，不同字段的版本可能不一样（A 改颜色到 7，B 改位置到 8）。取最大值 +1 保证新 op 的戳一定比所有已知字段都大。

**撤销栈的两个细节**

```js
_pushUndo(label, items) {
  this.undoStack.push({ label, items });
  if (this.undoStack.length > UNDO_LIMIT) this.undoStack.shift();
  this.redoStack.length = 0;    // ← 关键
}
```

1. `shift()` 淘汰最老的：撤销栈无限增长会吃内存，120 步对用户来说足够。
2. `this.redoStack.length = 0`：**做新操作必须清空重做栈**。否则会出现"撤销 3 步 → 做个新操作 → 重做，结果跳回旧分支"的诡异行为。这是所有编辑器的标准行为。

`length = 0` 是清空数组的惯用法（比 `arr = []` 省一次分配，而且不改变引用）。

**`_applyEntry`：撤销为什么是"造新 op"**

```js
_applyEntry(entry, direction) {
  for (const item of entry.items) {
    const shape = this.shapes.get(item.id);
    if (!shape) continue;

    const spec = item[direction];      // direction 是 'backward' 或 'forward'
    if (!spec) continue;
    const kind = spec.kind === DELETE ? DELETE : PATCH;
    const op = this._nextOp({
      kind, target: item.id,
      patch: { ...spec.patch },
      ver: this._versionOf(item.id),   // ← 当前版本 + 1
    });
    this.shapes.set(item.id, mergeOp(shape, op));
    this._enqueue(op);
  }
  this._persistDoc();
}
```

关键在 `ver: this._versionOf(item.id)`。**撤销不是把旧 op 重放一遍，而是用"当前最大版本 + 1"造一条反向的新 op。**

如果重放旧 op（带着旧版本号），服务端的逐字段 LWW 会直接丢弃它，用户点了撤销毫无反应。

`item[direction]` 这种写法叫**动态属性访问**：`item['backward']` 或 `item['forward']`。用它就不用写两个几乎一样的分支。

`{ ...spec.patch }` 又拷了一次，防止撤销记录里的 patch 被后续修改污染。

**`applyRemote`：远端数据进来**

```js
applyRemote(rawShape) {
  const r = normalizeShape(rawShape);
  if (!r.ok) {
    this.onLog('err', `丢弃非法图形：${r.message}`);
    return false;
  }
  const incoming = r.shape;
  const current = this.shapes.get(incoming.id);
  this.shapes.set(
    incoming.id,
    current ? mergeShape(current, incoming, { authoritative: true }) : incoming,
  );
  ...
}
```

三件事：校验 → 找本地 → 合并。

**注意注释里那句提醒**：

```js
// 注意：这里必须用 mergeShape（图形 vs 图形），不能用 mergeOp（图形 vs op）
```

广播里带的是**完整的带戳图形**，不是 op。用 `mergeOp` 会把整个图形当成一条新 patch 去盖戳，所有字段的版本号都会被改成同一个值——历史就乱了。

**`replaceAll`：重连时的"快照替换"**

```js
replaceAll(rawShapes) {
  const next = new Map();
  let rejected = 0;
  for (const raw of rawShapes) {
    const r = normalizeShape(raw);
    if (r.ok) next.set(r.shape.id, r.shape);
    else rejected += 1;
  }
  this.shapes = next;
  this.replayPendingLocally();
  ...
}
```

先构建一个**全新的 Map**，再整体替换。而不是"清空旧的再往里塞"——万一中途抛异常，旧数据还在（虽然这里不会抛，但这是更安全的习惯）。

`replayPendingLocally()` 是必须的：快照是服务端的状态，不包含本地还没发出去的操作。替换之后如果不把队列叠回去，**用户离线期间画的东西会瞬间消失**（虽然重连后还会重新发上去，但那一下闪烁很难看）。

**`takePending` 为什么排序**

```js
takePending() {
  return [...this.pending].sort((a, b) => a.clientSeq - b.clientSeq);
}
```

`clientSeq` 是同一个客户端的操作顺序。乱序发送会让服务端的高水位检查误判（收到 43 之后再来 42，42 会被当成重放拒绝）。

**`digest`：一致性自检**

```js
digest() {
  const ids = [...this.shapes.keys()].sort();
  return ids.map((id) => {
    const s = this.shapes.get(id);
    const flat = flatten(s);
    return `${id.slice(0, 4)}:${flat.x},${flat.y},${flat.w},${flat.h},${flat.deleted ? 'D' : 'A'}`;
  });
}
```

把整个文档压成一个字符串数组。两个客户端对比这个数组，就能判断"我们是不是看到同一个世界"。

`flat.deleted ? 'D' : 'A'`（Deleted / Alive）比直接输出 `true/false` 短，日志里更好看。

### 语法点

| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `class X { constructor() {} }` | 定义类与构造函数 | 一个 store 实例管理一份文档 |
| `constructor({a, b})` | 解构参数 | 六个参数里有三个可选，位置参数不可读 |
| `a = 0` | 参数默认值 | 调用方不传就用默认 |
| `x \|\| (() => {})` | 短路兜底成空函数 | 回调未传时不会崩 |
| `this.xxx = xxx` | 挂到实例上 | 类的方法里靠 this 访问 |
| `new Map()` | 键值对集合，键可以是任意类型 | `shapeId → shape` 的索引 |
| `map.get/set/has/values` | Map 的读写方法 | 不能用 `map[key]` |
| `[...map.values()]` | 迭代器展开成数组 | Map 没有 filter/sort |
| `arr.filter(fn)` | 过滤出满足条件的元素 | 去掉墓碑 |
| `arr.sort((a,b)=>a-b)` | 自定义比较函数 | 按 z 排序 |
| `arr.reduce((m,x)=>..., 0)` | 折叠成单值 | 求最大 clientSeq |
| `arr.shift()` / `.pop()` | 从头/尾取出元素 | 撤销栈淘汰最老的 |
| `arr.length = 0` | 清空数组 | 清空重做栈 |
| `setTimeout(fn, ms)` | 延迟执行 | 防抖落盘 |
| `clearTimeout(t)` | 取消定时器 | flush 时立刻执行 |
| `try { } catch (e) { }` | 捕获异常 | localStorage 可能抛异常 |
| `` `${a}:${b}` `` | 模板字符串 | 拼 storage key、日志 |
| `obj[key]` | 动态属性访问 | `item[direction]` 二选一 |
| `{ ...a, ...b }` | 对象展开合并 | 样式字段打包 |
| `x ? 'D' : 'A'` | 三元 | 紧凑输出状态 |

### 写错了会怎样

- **去掉 `_persistDoc` 的防抖**：拖动时每 60ms 同步写整个文档，主线程被阻塞，拖动明显掉帧。
- **去掉 `pagehide` 里的 `flush`**：用户拖完立刻关标签页，最后一次编辑丢失（防抖定时器还没到）。
- **`_pushUndo` 不清空 `redoStack`**：撤销两步 → 画个新图形 → 重做，画布跳回旧状态，用户以为程序疯了。
- **撤销重放旧 op 而不重算 ver**：服务端按 LWW 丢弃，用户按 Ctrl+Z 没反应。
- **`applyRemote` 用 `mergeOp` 而不是 `mergeShape`**：整个图形的字段版本被统一改写，之后所有合并都基于错误的版本号。
- **`replaceAll` 后不 `replayPendingLocally`**：重连瞬间，离线画的内容闪一下消失再出现。

## client/js/net.js（连接状态机）

### 它解决什么问题

WebSocket 不是"连上就一直通"。它会因为 Wi-Fi 切换、代理超时、服务端重启、笔记本合盖而断开，而且**断开时不会告诉你原因**。

这个文件要做的，是把"一条会随时断的管子"包装成"上层可以无脑调用"的接口：

- 断了自动重连（还不能太频繁，否则压垮服务器）
- 连上后自动补发离线期间的队列
- 收到乱序/缺口时能发现并自愈
- 上层只需要 `sendOp(op)`，不用关心现在是连着的还是断的

### 代码逐段讲

**状态机：五个状态**

```
idle → connecting → syncing → online ⇄ offline
```

| 状态 | 含义 | 此时能发 op 吗 |
| --- | --- | --- |
| `idle` | 还没开始 | 不能 |
| `connecting` | TCP/握手进行中 | 不能 |
| `syncing` | 连上了，等快照 | 不能（但本地编辑照常进队列） |
| `online` | 正常收发 | 能 |
| `offline` | 断开 | 不能（进队列） |

`syncing` 这个中间态很容易被忽略，但它很关键：**连上的一瞬间不能发 op**，因为服务端还没把快照给你，你的 `ver` 是基于旧状态算的，发上去大概率版本落后。

**`_url`：协议跟着页面走**

```js
_url() {
  const proto = location.protocol === 'https:' ? 'wss:' : 'ws:';
  return `${proto}//${location.host}/ws`;
}
```

HTTPS 页面里必须用 `wss:`（加密的 WebSocket），否则浏览器会以"混合内容"为由直接拒绝连接。

`location.host` 自带端口，所以部署到任何域名都不用改代码。

**`connect` 里的两道防护**

```js
connect() {
  if (this.simulatedOffline) { this._setState('offline'); return; }
  if (this.ws && (this.ws.readyState === WebSocket.OPEN || this.ws.readyState === WebSocket.CONNECTING)) {
    return;
  }
  ...
}
```

第一道：调试面板勾了"模拟断网"就直接不连。

第二道：**已经在连或已连上，就不要重复连**。没有这道判断，一次 `online` 事件 + 一次定时器重连同时触发，会创建两条 WebSocket，服务端看到两个同 `clientId` 的连接，`presence` 会出现两个一样的光标。

**`new WebSocket` 为什么要 try/catch**

```js
try {
  ws = new WebSocket(this._url());
} catch (err) {
  this._log('err', `无法建立连接：${err.message}`);
  this._scheduleReconnect();
  return;
}
```

构造函数在 URL 非法时会同步抛异常（比如页面是 `file://` 打开的）。不 catch 的话，整个 `connect` 中断，重连定时器也不会排上，白板永久卡在"连接中"。

**`onopen`：第一件事是打招呼**

```js
ws.onopen = () => {
  this.retries = 0;
  this._setState('syncing');
  this.lastMessageAt = Date.now();
  this._startTick();
  this._send({
    type: MSG.HELLO,
    roomId: this.roomId,
    clientId: this.identity.clientId,
    sessionEpoch: this.identity.sessionEpoch,
    name: this.identity.name,
    lastSeq: this.lastApplied,
  });
};
```

`this.retries = 0` 是**退避重置**：连上了说明网络恢复了，下次断线应该从最短延迟开始重试，而不是接着上次的 15 秒。

`lastSeq` 告诉服务端"我手上有到第几号的操作"。服务端目前的做法是不管它，直接回全量快照——但带上它是为了将来能做增量同步。

**`onmessage`：两层 try/catch**

```js
ws.onmessage = (ev) => {
  this.recv += 1;
  this.lastMessageAt = Date.now();
  let msg;
  try {
    msg = JSON.parse(ev.data);
  } catch {
    this._log('warn', '收到非 JSON 消息，已丢弃');
    return;
  }
  try {
    this._handle(msg);
  } catch (err) {
    this._log('err', `处理消息异常：${err.message}`);
  }
  this.handlers.onStats?.();
};
```

两层是分开的，因为处理方式不同：

- JSON 解析失败 → 这条消息根本没法用，丢弃
- 处理逻辑抛异常 → 消息是好的，是我们的代码有 bug，记日志但不能让整个连接崩掉

**如果没有第二层 catch**，一个畸形消息就能让 `onmessage` 抛出，后续所有消息都收不到——连接看起来是"活着"的，实际已经聋了。

**`onclose`：为什么要判断 `wasOnline`**

```js
ws.onclose = (ev) => {
  this._stopTick();
  this.ws = null;
  const wasOnline = this.state === 'online' || this.state === 'syncing';
  this._setState('offline');
  if (wasOnline && ev.code !== 1000) {
    this._log('warn', `连接断开（${ev.code}），本地编辑继续，稍后自动重连`);
  }
  if (!this._manualClose && !this.simulatedOffline) this._scheduleReconnect();
  this._manualClose = false;
};
```

`ev.code === 1000` 是"正常关闭"。如果是我们主动调 `disconnect()` 关的，就不该报"连接断开"吓用户。

`_manualClose` 标志位解决了一个经典的坑：**主动关闭也会触发 `onclose`**。如果不设标志，`disconnect()` 之后立刻又被 `onclose` 排上重连，用户点了"断开"却发现自己在重连。

用完立刻 `this._manualClose = false` 复位，避免影响下一次。

**`setSimulatedOffline`：演示用的假断网**

```js
setSimulatedOffline(on) {
  this.simulatedOffline = on;
  if (on) {
    this._manualClose = true;
    this._stopTick();
    this._clearReconnect();
    if (this.ws) {
      try { this.ws.close(4001, 'simulated offline'); } catch { }
      this.ws = null;
    }
    this._setState('offline');
  } else {
    this.retries = 0;
    this.connect();
  }
}
```

`close(4001, ...)` 用的是自定义关闭码（4000-4999 是应用保留区间）。这样服务端日志里能看出"这是客户端主动断的"，不是网络故障。

**这个功能存在的意义**：答辩演示时不可能真去拔网线。有了这个开关，点一下就能复现"离线编辑 → 恢复 → 自动合并"的完整流程。

**`_scheduleReconnect`：指数退避 + 抖动**

```js
_scheduleReconnect() {
  this._clearReconnect();
  const delay = Math.min(MAX_DELAY, BASE_DELAY * 2 ** this.retries) + Math.random() * 300;
  this.retries += 1;
  this._log('info', `${Math.round(delay)}ms 后重连（第 ${this.retries} 次）`);
  this._reconnectTimer = setTimeout(() => {
    this._reconnectTimer = null;
    this.connect();
  }, delay);
}
```

`BASE_DELAY * 2 ** this.retries` 是 `500 × 2ⁿ`：

| 第几次 | 延迟 |
| --- | --- |
| 1 | 500ms |
| 2 | 1s |
| 3 | 2s |
| 4 | 4s |
| 5 | 8s |
| 6+ | 15s（被 `Math.min` 截住） |

**为什么要退避？** 服务端重启时，所有客户端会同时掉线。如果每 100ms 重试一次，几百个客户端会把刚起来的服务端瞬间打挂，然后再次全部掉线——雪崩。

**为什么要加随机抖动？** 因为大家往往是同一时刻掉线的，退避时间也一样。加 0~300ms 随机量，重连就会错开。

`setTimeout` 里再调 `connect()`，而 `connect()` 失败又会调 `_scheduleReconnect`——**这是一个自递归的重试循环**，靠 `retries` 递增控制频率。

**`_startTick`：心跳**

```js
_startTick() {
  this._stopTick();
  this._tickTimer = setInterval(() => {
    if (!this.ws || this.ws.readyState !== WebSocket.OPEN) return;
    const now = Date.now();
    if (now - this.lastMessageAt > STALE_MS) {          // 32 秒没收到任何帧
      this._log('warn', '心跳超时，主动断开以触发重连');
      try { this.ws.close(4000, 'heartbeat timeout'); } catch { }
      return;
    }
    if (now - this.lastPingAt > HEARTBEAT_MS) {          // 15 秒发一次 ping
      this.lastPingAt = now;
      this._send({ type: MSG.PING, t: now });
    }
  }, TICK_MS);   // 每 5 秒检查一次
}
```

**为什么需要应用层心跳？** 因为 TCP 连接可能在"物理上已经断了、但操作系统还没发现"的状态下挂很久（比如拔了网线，没有 FIN 包）。浏览器不会告诉你这件事，`onclose` 也不会触发。只能靠"我发消息你没回"来判断。

**为什么 ping 是 15 秒、判死是 32 秒？** 32 ≈ 2 × 15 + 2 秒余量。允许丢一次 ping，但不允许连续两次都没响应。

注意：浏览器的 WebSocket API **不允许应用层发控制帧**（那是底层的事），所以心跳只能自己定一个 `ping` 消息类型走数据帧。

**`_onWelcome`：重连的核心**

```js
_onWelcome(msg) {
  const epochChanged = this.bootEpoch && msg.bootEpoch !== this.bootEpoch;
  this.bootEpoch = msg.bootEpoch;

  this.lastApplied = msg.serverSeq || 0;
  this.store.replaceAll(msg.shapes || []);
  this._setState('online');

  this.handlers.onMembers?.(msg.members || []);
  this._log('ok', `已同步：${(msg.shapes || []).length} 个图形，serverSeq=${this.lastApplied}`);
  this._flushQueue();
}
```

四步，顺序不能变：

1. 记下 `serverSeq`（后续判断有没有漏消息的基准）
2. **整体替换**本地文档（同时把待发队列叠回去）
3. 切到 online
4. 重发队列

`epochChanged` 的判断：`this.bootEpoch` 为空说明是首次连接，不算"变了"。只有"之前连过、现在变了"才说明服务端重启过。

**`_onOp`：收到广播**

```js
_onOp(msg) {
  if (msg.bootEpoch !== this.bootEpoch) {
    this._forceResync('bootEpoch-mismatch');
    return;
  }
  if (msg.seq <= this.lastApplied) return;      // 旧的/重放的，直接丢
  if (this.lastApplied > 0 && msg.seq !== this.lastApplied + 1) {
    this._forceResync('seq-gap');               // 有缺口
    return;
  }

  this.store.applyRemote(msg.shape);
  this.store.dequeue(msg.opId);
  this.lastApplied = msg.seq;
  this.handlers.onChange?.();
}
```

三道闸门，对应三种异常：

| 检查 | 说明什么 | 处理 |
| --- | --- | --- |
| `bootEpoch` 不同 | 服务端重启过，序号体系已变 | 全量重拉 |
| `seq <= lastApplied` | 重复投递或乱序的旧帧 | 静默丢弃 |
| `seq` 不连续 | 中间漏了消息 | 全量重拉 |

**第三条为什么不能"等等补上"？** 因为漏掉的那条可能改了某个字段，你不知道改成了什么，后续所有合并都基于错误前提。**状态一旦可疑，就重建。**

**`_onAck`：只做一件事**

```js
_onAck(msg) {
  this.store.dequeue(msg.opId);

  if (!msg.accepted) {
    if (msg.shape) this.store.adoptAuthoritative(msg.shape);
    this._log('warn', '离线修改版本落后，已采用服务端状态');
    this.handlers.onConflict?.(msg);
    this.handlers.onChange?.();
    return;
  }
  this.handlers.onChange?.();
}
```

**注意它没有推进 `lastApplied`。** 这是文件头第二条铁律：

```js
// lastAppliedSeq 只由「快照」和「广播 op」推进，绝不由 ack 推进。
// 否则 ack(seq=10) 会把还在途的 seq=9 当成重放丢掉。
```

`accepted: false` 是"服务端收到了但没产生变更"（离线 op 版本落后）。这时服务端会把**当前权威态**带回来，客户端强制覆盖本地——否则本地永远停在自己那个错误的版本上。

**`_forceResync`：自愈**

```js
_forceResync(reason) {
  this.lastApplied = 0;
  this._manualClose = true;
  if (this.ws) {
    try { this.ws.close(4002, 'resync'); } catch { }
    this.ws = null;
  }
  this._stopTick();
  this.retries = 0;
  this._clearReconnect();
  setTimeout(() => {
    if (!this.simulatedOffline) this.connect();
  }, 60);
}
```

先把 `lastApplied` 归零（下次 welcome 会重新设），然后关闭连接、60ms 后重连。

60ms 是个折中：太短可能撞上还没释放的 socket，太长用户能感觉到卡顿。

**`sendOp`：在线才发**

```js
sendOp(op) {
  if (this.state === 'online') {
    this._send({ type: MSG.OP, op });
  }
  this.handlers.onStats?.();
}
```

离线时什么都不做——**但 op 已经进队列了**（在 store 里）。所以断网期间编辑不会丢，只是攒着。

**`_send` 的三重检查**

```js
_send(payload) {
  if (!this.ws || this.ws.readyState !== WebSocket.OPEN) return false;
  try {
    this.ws.send(JSON.stringify(payload));
    this.sent += 1;
    return true;
  } catch (err) {
    this._log('err', `发送失败：${err.message}`);
    return false;
  }
}
```

`readyState` 检查防"往已关闭的连接写"，try/catch 防"缓冲区满了抛异常"。两个都会真实发生。

**`this.handlers.onStats?.()` 里的 `?.` 是什么**

这是**可选链调用**：如果 `onStats` 是 `undefined`，整个表达式返回 `undefined`，不报错。

等价于：

```js
if (this.handlers.onStats) this.handlers.onStats();
```

写起来短很多，而且 `handlers` 里七八个回调大部分时候是不传的。

### 语法点

| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `WebSocket.OPEN` | 连接状态的静态常量（1） | 比记数字 1 可读 |
| `ws.readyState` | 当前连接状态 | 发消息前必须检查 |
| `ws.onopen/onmessage/onclose/onerror` | 四个事件回调属性 | 浏览器原生 API，不是 addEventListener |
| `ev.data` | 收到消息的载荷（字符串） | 需要自己 JSON.parse |
| `ev.code` | 关闭码 | 1000 表示正常关闭 |
| `location.protocol` / `location.host` | 当前页面的协议与主机 | 自动拼出 ws 地址 |
| `2 ** n` | 幂运算（ES2016） | 指数退避 500×2ⁿ |
| `Math.min(a, b)` | 取较小值 | 退避封顶 15s |
| `Math.random() * 300` | 0~300 的随机数 | 抖动，避免同时重连 |
| `setInterval(fn, ms)` | 每隔一段时间执行 | 心跳检查 |
| `clearInterval(t)` | 停止定时器 | 断线时停心跳 |
| `a?.b()` | 可选链调用：a 为空就跳过 | handlers 里大部分回调没传 |
| `switch (msg.type)` | 多分支匹配 | 消息分发 |
| `try/catch` 两层 | 分别处理解析错误与逻辑错误 | 一个畸形消息不该让连接失聪 |
| `return;` 提前返回 | 守卫子句 | 少写嵌套 if |
| `Number.isFinite` / `msg.seq \|\| 0` | 兜底默认值 | 服务端可能没给 serverSeq |

### 写错了会怎样

- **让 ack 推进 `lastApplied`**：连续快速操作时偶尔丢一个图形，日志出现"seq 缺口"，而且极难复现。
- **`onclose` 里不判断 `_manualClose`**：用户点"断开"，立刻又被自动重连，看起来像点了没反应。
- **重连不退避（固定 100ms）**：服务端重启时几十个客户端同时轰炸，服务端起不来。
- **不加抖动**：所有客户端在同一毫秒重连，形成周期性尖峰。
- **`_onOp` 允许 `seq` 跳号继续应用**：漏掉的那条改动永久丢失，两端状态静默分叉。
- **`connect` 不检查 `readyState`**：同时开两条 WebSocket，`presence` 里出现两个自己。

## client/js/main.js（装配）

### 它解决什么问题

前面的模块互相需要对方：

```
store 产生 op → 要交给 net 发出去
net 收到广播 → 要交给 store 合并
tools 改数据 → 要用 store
canvas 画图 → 要从 store 读
ui 点按钮 → 要调 store / net / tools
```

**这是循环依赖**：store 需要 net，net 需要 store。

ES Module 的 `import` 是静态的，循环 import 会拿到 `undefined`。所以这里用了一个很朴素的办法：**先声明变量，再逐个 new，最后统一接线。**

### 代码逐段讲

**先声明，后赋值**

```js
let store;
let net;
let board;
let interactions;
let presence;
let ui;

store = new DocStore({ ... onOp: (op) => net?.sendOp(op) ... });
board = new Board(canvasEl, { getShapes: () => store.list(), ... });
interactions = new Interactions({ canvasEl, board, store, net: null, ui: null, ... });
net = new Net({ ..., store, ... });
presence = new Presence({ ..., onSend: (pt) => net.sendPresence(pt) });
ui = new UI({ store, net, interactions, board, ... });

interactions.ui = ui;      // ← 回填
interactions.net = net;    // ← 回填
```

注意两处"延迟绑定"：

1. `onOp: (op) => net?.sendOp(op)` —— 箭头函数体里才读 `net`，创建 store 时 `net` 还是 `undefined`，但调用时已经有值了。
2. `interactions.ui = ui` —— 因为 `ui` 在 `interactions` 之后才创建，只能先传 `null` 再回填。

**这就是"闭包"的实用价值**：函数记住了变量名，而不是当时的值。

**`pickRoom`：房间号从 URL 来**

```js
function pickRoom() {
  const params = new URLSearchParams(location.search);
  const raw = (params.get('room') || '').trim();
  if (raw && isValidRoomId(raw)) return raw;
  return DEFAULT_ROOM;
}
```

`new URLSearchParams('?room=demo')` 把查询串解析成可查询对象。`params.get('room')` 拿到 `'demo'`。

**为什么要校验？** 因为房间号会变成文件名（`data/demo.jsonl`）。如果允许 `?room=../../etc/passwd`，服务端就会去写系统文件——这叫**路径穿越**。`isValidRoomId` 只允许字母数字下划线横线，把这条路堵死。

**`loadIdentity`：三种存储的分工**

```js
let clientId = sessionStorage.getItem('wb:clientId');
if (!clientId || !/^[a-z0-9-]{6,40}$/.test(clientId)) {
  clientId = `c-${shortId(10)}`;
  sessionStorage.setItem('wb:clientId', clientId);
}

let sessionEpoch = localStorage.getItem(`wb:epoch:${roomId}`);
...
let name = localStorage.getItem('wb:name');
```

三者的区别是本文件最值得学的一处设计：

| 数据 | 存哪 | 为什么 |
| --- | --- | --- |
| `clientId` | **sessionStorage** | 每个标签页独立。双开时两个窗口必须是"两个人" |
| `sessionEpoch` | localStorage | 刷新后接着用，避免被当成新会话 |
| `clientSeq` | localStorage | 刷新后序号接着涨，不会重号 |
| `name` | localStorage | 用户改了昵称，换标签页还是这个名字 |

**如果 `clientId` 也放 localStorage**：同一个浏览器的两个窗口会有相同的 `clientId`，于是它们发出的 op 戳完全一样（`v` 相同、`c` 相同），只剩 `opId` 不同——裁决结果就变成"比 uuid 大小"，等于随机。演示时会出现"我在这边拖，那边没反应"的诡异现象。

**`onChange` 回调：改完就重画**

```js
store = new DocStore({
  ...
  onChange: () => {
    board?.render();
    ui?.refresh();
    ui?.updateSelection();
  },
});
```

这是**单向数据流**的雏形：状态变了 → 通知视图 → 视图重画。视图不直接改状态，状态也不直接操作 DOM。

**`Board` 的依赖注入**

```js
board = new Board(canvasEl, {
  getShapes: () => store.list(),
  getPreview: () => interactions?.preview || new Map(),
  getSelection: () => interactions?.getSelection() || new Set(),
  getDraft: () => interactions?.draft || null,
  getMarquee: () => interactions?.marquee || null,
});
```

`Board` 不持有 store 和 interactions 的引用，只拿到五个**取值函数**。

这叫**依赖倒置**：`Board` 不需要知道数据从哪来，只要"我调用 `getShapes()` 能得到一个数组"。

好处是 `Board` 可以独立测试——塞几个假函数进去就能跑，不用真的建 store。

**事件监听：三个恢复时机**

```js
window.addEventListener('online', () => net.retryNow());
window.addEventListener('offline', () => ui.log('warn', '浏览器网络已断开，进入离线模式'));
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible') net.retryNow();
});
```

- `online`：浏览器认为网络恢复了 → 立刻重连，不等退避
- `offline`：只记日志，不做处理（因为 op 本来就会进队列）
- `visibilitychange`：用户切回标签页 → 立刻重试。**为什么需要？** 因为浏览器会节流后台标签页的定时器，重连可能被推迟很久。用户切回来那一刻是"最希望立刻可用"的时刻。

**离开页面前的最后一道保险**

```js
window.addEventListener('pagehide', () => store.flush());
window.addEventListener('beforeunload', () => store.flush());
```

两个都挂是因为浏览器兼容性：`beforeunload` 在移动端不可靠，`pagehide` 在旧浏览器上可能不触发。**两个都挂，谁先来谁生效，`flush` 本身是幂等的。**

**`window.__board`：留给调试的钩子**

```js
window.__board = { store, net, board, interactions, ui, presence, roomId, identity };
```

把内部对象挂到 `window` 上，F12 里就能直接：

```js
__board.store.stats()        // { total: 12, visible: 10, pending: 0 }
__board.net.stats()          // { state: 'online', lastApplied: 37, ... }
__board.store.digest()       // 当前文档指纹
```

对比两个窗口的 `digest()`，就能验证"我们是不是同一个世界"。

### 语法点

| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `let x;` 先声明后赋值 | 变量提升到模块顶层 | 解决循环依赖 |
| `() => net?.sendOp(op)` | 闭包 + 可选链 | 创建时 net 还不存在，调用时才有 |
| `new URLSearchParams(location.search)` | 解析查询串 | 取 `?room=` 参数 |
| `sessionStorage` vs `localStorage` | 标签页级 vs 站点级存储 | 决定"是不是同一个人" |
| `/^[a-z0-9-]{6,40}$/.test(s)` | 正则校验格式 | 防止脏 id 进系统 |
| `a?.b` / `a?.()` | 可选链 | 对象可能还没创建 |
| `x \|\| new Map()` | 短路兜底 | 预览为空时给个空 Map |
| `addEventListener('x', fn)` | 注册事件监听 | 网络状态、页面可见性、卸载 |
| `document.visibilityState` | 当前页面是否可见 | 切回标签页立刻重连 |
| `window.__xxx = obj` | 挂到全局 | 调试用，生产环境通常会删 |

### 写错了会怎样

- **直接 `import` 形成循环**：`net` 或 `store` 拿到 `undefined`，启动即报 `Cannot read property of undefined`。
- **`clientId` 用 localStorage**：双开标签页被当成同一个人，两人同时编辑时裁决结果随机。
- **不校验 `roomId`**：`?room=../../server/index` 可以覆盖服务端文件。
- **不挂 `visibilitychange`**：笔记本合盖再打开，白板要等十几秒才恢复（后台定时器被节流）。
- **不挂 `pagehide`**：关标签页丢最后一次编辑。

---

## 这一篇的三个结论

1. **store 是唯一的状态源**，所有修改都走它；乐观更新让界面永不等待网络。
2. **net 是一个状态机**，五种状态各有含义；`lastApplied` 只能由快照和广播推进。
3. **main 只做接线**，用"先声明后赋值 + 闭包"解决循环依赖，用依赖注入让 Board 与 store 解耦。
