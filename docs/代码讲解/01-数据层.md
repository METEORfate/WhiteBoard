# 01 数据层：id、字段规格、合并函数

这一篇讲三个文件，它们都在 `shared/` 目录下——**浏览器和 Node 同时引用同一份**。

```
shared/ids.js       造身份证（uuid、短 id、会话 epoch）
shared/protocol.js  定规矩（哪些字段能改、什么值合法、越界怎么办）
shared/merge.js     定裁决（两个版本撞上了，听谁的）
```

顺序不能换：先有 id 才能指认一个图形，先有字段规格才知道"改什么"，最后才谈"两个改动怎么合"。

这三个文件都是**纯函数 + 常量**，没有网络、没有 DOM、没有文件系统。所以它们能被单独测试——`tests/merge.test.js` 就是直接 import 进来跑的，不需要起服务。

## shared/ids.js（造唯一标识符）

### 它解决什么问题

整个系统的地基是一句话：**每一条操作、每一个图形，都要有一个全宇宙唯一的编号。**

为什么必须唯一？回想"两人同时改颜色"那个场景：如果两条 op 没有各自的编号，合并时就没法判断"这两条是不是同一条"，也就没法去重。服务端的幂等去重（`opId` 见过就跳过）完全建立在"编号唯一"这个前提上。

这个文件只干三件事：生成 uuid、生成短随机串、生成会话 epoch。难点不在算法，在**兼容性**——同一份代码要在浏览器和 Node 里都能跑。

### 代码逐段讲

**为什么不能直接用 `crypto.randomUUID()`**

```js
export function uuid() {
  const c = globalThis.crypto;
  if (c && typeof c.randomUUID === 'function') return c.randomUUID();
  // ↓ 走不通时的兜底
  const b = randomBytes(16);
  ...
}
```

`crypto.randomUUID()` 有一个隐藏前提：**安全上下文**。`https://` 和 `localhost` 算安全上下文，`http://192.168.1.5:8787` 不算。

这个项目要能在局域网里演示（手机连电脑的热点打开白板），这时候 `crypto.randomUUID` 是 `undefined`。如果代码直接调它，会抛 `TypeError: crypto.randomUUID is not a function`——而且是在"用户画第一个图形"的时候抛，整个同步链路当场崩掉。

所以先做**能力检测**：`typeof c.randomUUID === 'function'`。有就用，没有就走后面的兜底实现。

> 这个模式叫"特性检测（feature detection）"，比判断浏览器版本号可靠得多。

**`globalThis` 是什么**

```js
const c = globalThis.crypto;
```

`globalThis` 是"当前环境的全局对象"。在浏览器里它等于 `window`，在 Node 里等于 `global`。写 `globalThis.crypto` 就不用关心自己跑在哪——这也是这个文件能同时被两端引用的原因。

**兜底的 uuid 生成**

```js
const b = randomBytes(16);
b[6] = (b[6] & 0x0f) | 0x40; // version 4
b[8] = (b[8] & 0x3f) | 0x80; // variant 10
```

uuid v4 是一个 16 字节（128 位）的随机数，但其中 6 个 bit 不是随机的，而是**标记位**，用来声明"我是 v4 版本、我用的是 RFC 4122 变体"。

拆开看这两行：

| 写法 | 作用 |
| --- | --- |
| `b[6] & 0x0f` | `0x0f` 是 `00001111`，按位与之后**高 4 位清零、低 4 位保留** |
| `\| 0x40` | `0x40` 是 `01000000`，按位或之后**把第 7 位设成 1**，即版本号 = 4 |

`b[8]` 同理，`& 0x3f` 保留低 6 位，`| 0x80` 把最高两位置成 `10`（这就是"variant 10"）。

**为什么要费这个劲？** 因为有些库会校验 uuid 的版本位。不设的话生成出来的是"格式不对的 uuid"，`normalizeShape` 里的正则 `UUID_RE` 会直接拒掉。

```js
for (let i = 0; i < 16; i += 1) h.push(b[i].toString(16).padStart(2, '0'));
```

- `toString(16)`：转成十六进制字符串。`255` → `"ff"`，但 `5` → `"5"`（只有一位）。
- `padStart(2, '0')`：左边补零到 2 位。`"5"` → `"05"`。**少了这一步，拼出来的 uuid 长度会变，正则就匹配不上了。**

最后用 `slice + join` 按 `8-4-4-4-12` 切成五段：

```js
return `${h.slice(0, 4).join('')}-${h.slice(4, 6).join('')}-...`;
```

**短 id 为什么用 `& 0x0f` 取字符**

```js
export function shortId(len = 10) {
  const b = randomBytes(len);
  let s = '';
  for (let i = 0; i < len; i += 1) s += HEX[b[i] & 0x0f];
  return s;
}
```

`HEX` 是 16 个字符的字符串，下标 0-15。`b[i]` 是 0-255 的随机字节，`& 0x0f` 只留低 4 位 → 结果必然是 0-15 → 正好能当下标。

这样每个字节换一个十六进制字符，`len=10` 得到 10 个字符。**注意它只有 4 bit 熵/字符**，所以只能用在 clientId、房间名这类"不需要抗碰撞"的地方，不能用来当 opId。

**会话 epoch 为什么用 36 进制**

```js
export function newSessionEpoch() {
  return `${Date.now().toString(36)}-${shortId(6)}`;
}
```

`Date.now()` 是毫秒时间戳，十进制有 13 位，36 进制只要 8 位（`toString(36)` 用 0-9a-z）。**短、可读、还天然按时间递增**。

前面是时间，后面是随机后缀——防止两个标签页在同一毫秒打开时撞号。

### 语法点

| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `export function foo()` | 把这个函数暴露给别的文件 import | 整个项目用 ES Module，没有全局变量 |
| `globalThis` | 当前环境的全局对象（浏览器=`window`，Node=`global`） | 同一份代码跑两端 |
| `typeof x === 'function'` | 判断某个能力是否存在 | 特性检测，避免旧环境直接抛错 |
| `new Uint8Array(n)` | 定长 n 的字节数组，每项 0-255 | 生成随机字节，比普通数组省内存 |
| `c.getRandomValues(out)` | 用系统熵源填充字节数组 | 比 `Math.random()` 更随机，且不阻塞 |
| `a & 0x0f` | 按位与，保留低 4 位 | 清高位、取版本位 |
| `a \| 0x40` | 按位或，把某位置 1 | 写入 uuid 的版本标记 |
| `n.toString(16)` | 转十六进制字符串 | 拼 uuid |
| `.padStart(2, '0')` | 左边补字符到指定长度 | 保证每段固定 2 位 |
| `` `${a}-${b}` `` | 模板字符串，`${}` 里可以放表达式 | 拼 uuid / epoch，比 `+` 拼接可读 |
| `len = 10` | 函数默认参数，不传就用 10 | `shortId()` 和 `shortId(6)` 都合法 |
| `slice(0, 4)` / `join('')` | 截取子数组 / 把数组拼成字符串 | 按 8-4-4-4-12 分段 |

### 写错了会怎样

- **去掉 `padStart(2,'0')`**：uuid 长度不固定，`UUID_RE` 校验失败，服务端返回 `BAD_OP_ID`，所有编辑都被拒，白板看起来"只能自己画、别人收不到"。
- **直接调 `crypto.randomUUID()` 不做检测**：局域网 http 打开时抛异常，`createShape` 里生成 opId 那一步炸掉，用户点击画布毫无反应。
- **短 id 用 `b[i]` 而不是 `b[i] & 0x0f`**：下标越界得到 `undefined`，拼出 `"undefinedundefined..."`，clientId 正则校验失败，连不上房间。

## shared/protocol.js（定义"什么可以改、什么值合法"）

### 它解决什么问题

网络那头可能是一个恶意客户端。F12 打开控制台，任何人都能往 WebSocket 里灌这样的消息：

```json
{"type":"op","op":{"patch":{"x":99999999999,"fill":"javascript:alert(1)"}}}
```

如果不校验，这个值会进入文档、广播给所有人、写进磁盘，然后所有人的画布都画不出来。

`protocol.js` 就是那道门：**定义白名单（哪些字段可改）、定义每个字段的合法范围、定义越界时是拒绝还是截断。**

它还有一个更隐蔽的职责：**客户端和服务端必须用完全相同的规则**。客户端在本地先改（乐观更新），服务端再校验一遍。如果两边规则不一致——比如客户端允许 `x=250000`，服务端截断成 `100000`——那么本地显示的和别人看到的不一样，而且永远不会自动修正。

所以这个文件放在 `shared/`，两端 import 同一份。

### 代码逐段讲

**用常量对象当枚举**

```js
export const MSG = Object.freeze({
  HELLO: 'hello',
  WELCOME: 'welcome',
  OP: 'op',
  ACK: 'ack',
  PRESENCE: 'presence',
  RESYNC: 'resync',
  ERROR: 'error',
  PING: 'ping',
  PONG: 'pong',
});
```

这就是 JS 里最朴素的"枚举"。没有 `enum` 关键字（那是 TypeScript 的），用 `Object.freeze` 冻结一个对象来模拟。

**`Object.freeze` 到底防什么**

```js
MSG.OP = 'xxx';   // 静默失败（严格模式下抛 TypeError）
MSG.NEW = 'new';  // 同样失败
```

冻结之后对象不能再增删改属性。**为什么重要？** 因为 `MSG.OP` 这个字符串散落在服务端和客户端的十几个 `switch` 里。如果某处不小心写了 `MSG.OP = 'operation'`，所有 `case MSG.OP` 的分支会同时失效——而且不报错，只是消息全部走到 `default` 分支被当成"未知类型"。这种 bug 能查一整天。

**字段规格：整个系统最核心的一张表**

```js
export const FIELD_SPEC = Object.freeze({
  x:    { type: 'number', min: -100000, max: 100000, def: 0, integer: true },
  fill: { type: 'color', def: '#ffffff' },
  text: { type: 'string', maxLen: 2000, def: '' },
  deleted: { type: 'boolean', def: false },
  ...
});
```

每一项声明四件事：**类型、范围、默认值、要不要取整**。

有了这张表，三件事自动成立：

1. 渲染时字段缺失不用写 `if (shape.x === undefined)`——`flatten` 会拿 `def` 补上；
2. 校验时不用写十几个 if——`normalizeField` 遍历规格统一处理；
3. 加一个新字段只需要在这里加一行，校验、默认值、渲染全部自动支持。

**`PATCH_FIELDS` 是从规格表推出来的**

```js
export const PATCH_FIELDS = Object.freeze(Object.keys(FIELD_SPEC));
```

`Object.keys()` 拿键名数组，`Object.freeze` 防止有人 `push` 进去。**这是"单一真相源"的典型用法**：字段列表不手写第二遍，永远从规格表推导，不可能不同步。

**校验函数为什么返回 `{ok, value}` 而不是抛异常**

```js
function fail(code, message) {
  return { ok: false, code, message };
}
function ok(value) {
  return { ok: true, value };
}
```

调用处是这样用的：

```js
const r = normalizeField(name, raw);
if (!r.ok) return r;
out[key] = r.value;
```

**为什么不用 `throw`？** 因为"用户发了个非法值"不是程序 bug，是**预期内的正常情况**。用异常处理正常流程，会让调用方到处写 try/catch，而且容易漏。返回一个带 `ok` 标记的对象，调用方必须显式判断——漏了就会在类型检查时暴露（`r.value` 是 undefined）。

这个模式叫"结果对象（result object）"，在解析器、校验器里非常常见。

**数字字段：截断而不是拒绝**

```js
if (spec.type === 'number') {
  if (typeof raw !== 'number' || !Number.isFinite(raw)) {
    return fail('BAD_NUMBER', ...);
  }
  let v = raw;
  if (spec.integer) v = Math.round(v);
  if (v < spec.min) v = spec.min;
  if (v > spec.max) v = spec.max;
  return ok(v);
}
```

注意这里的**两种态度**：

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| `NaN` / `Infinity` / 字符串 | 拒绝 | 无法可靠解释，留着会污染整个文档 |
| 超出 ±100000 | 截断到边界 | 截断是**幂等**的：截一次和截十次结果一样 |

第二条是关键。如果越界就拒绝，那么客户端本地已经改了（乐观更新），服务端却拒了，用户会看到"图形跳回去了"。

而截断的话，客户端和服务端执行同样的 `clamp`，得到同样的结果——本地值和权威值一致，用户什么都感觉不到。

> 一句话总结这个取舍：**能用幂等操作修正的，就修正；修正不了的，才拒绝。**

**`Number.isFinite` 而不是 `isFinite`**

```js
!Number.isFinite(raw)
```

全局的 `isFinite('123')` 会先把字符串转成数字再判断，返回 `true`。`Number.isFinite('123')` 直接返回 `false`（因为它不是 number 类型）。

**这就是为什么前面还要先判 `typeof raw !== 'number'`——两个条件其实是重复的，但写出来意图更清楚。**

**颜色字段：只认 `#rrggbb`**

```js
const COLOR_RE = /^#[0-9a-f]{6}([0-9a-f]{2})?$/;
```

- `^` / `$`：整串匹配，防止 `"#ff0000; background:url(...)"` 这种注入
- `{6}`：6 位十六进制，`([0-9a-f]{2})?`：可选的 2 位（支持带透明度的 8 位色）
- `v.trim().toLowerCase()`：先规整再判断，避免 `"#FF0000"` 和 `"#ff0000"` 被当成两个不同值

**字符串字段：按码点计长**

```js
if ([...raw].length > spec.maxLen) {
  return fail('STRING_TOO_LONG', ...);
}
```

`raw.length` 数的是 UTF-16 编码单元。一个 emoji（比如 🎉）在 UTF-16 里占 2 个单元，所以 `"🎉".length === 2`。用 `[...raw]` 展开成字符数组，`length` 才是"人眼看到的字符数"。

**如果不改会怎样？** 用户输入 1000 个 emoji，`length` 是 2000，正好卡在上限——但他明明只打了 1000 个字符。更糟的是不同浏览器对代理对的处理可能不同，导致两端算出的长度不一致。

**`normalizeOp`：一条 op 的完整体检**

```js
export function normalizeOp(raw) {
  if (!raw || typeof raw !== 'object' || Array.isArray(raw)) return fail('NOT_OBJECT', ...);
  const opId = typeof raw.opId === 'string' ? raw.opId.toLowerCase() : '';
  if (!isUuid(opId)) return fail('BAD_OP_ID', ...);
  ...
}
```

逐项检查，任何一项不过就立刻返回。顺序是有讲究的：

1. 先判"是不是对象"——后面所有 `.opId` 访问都建立在它是对象上
2. 再判 id 格式——uuid 是后续一切索引的键
3. 再判房间/客户端/序号——这些是"谁发的"
4. 最后判 `patch` 内容——这个最贵（要遍历字段）

**便宜的先判，贵的后判**，这是一切校验器的通用优化。

注意 `typeof raw.opId === 'string' ? raw.opId.toLowerCase() : ''` 这个写法：先确认是字符串再调方法。如果直接写 `raw.opId.toLowerCase()`，遇到 `opId: 123` 就抛 `TypeError` 了。

**`create` 和 `delete` 的字段强制覆盖**

```js
if (kind === OP_KIND.CREATE) {
  for (const f of REQUIRED_ON_CREATE) {
    if (!(f in patch)) return fail('MISSING_GEOMETRY', ...);
  }
  patch.deleted = false;   // ← 强制
}
if (kind === OP_KIND.DELETE) {
  patch.deleted = true;    // ← 强制
}
```

这两行是**语义兜底**。有人可能构造一条 `create` 但 `deleted: true` 的 op，或者 `delete` 但 `deleted: false` 的 op。不强制的话，文档里会出现"创建出来就是删除状态"的幽灵数据。

**`REQUIRED_ON_CREATE = ['x','y','w','h']`** 的存在理由类似：没有几何字段的图形画不出来，但也删不掉（因为看不见），会变成永久垃圾。

**`normalizeShape`：为什么客户端也要校验服务端**

```js
/**
 * 客户端同样要对远端数据做这一步：不信任服务端，也不信任其他客户端。
 */
```

这句话值得单独说。直觉上"服务端的数据肯定是对的"，但：

- 服务端可能被攻击、可能跑着旧版本代码
- 快照是从磁盘读的，磁盘上的文件可能被手工改过
- 中间可能隔着代理/网关

多校验一次的成本是几微秒，收益是"坏数据进不了渲染层"。这在安全上叫**纵深防御**。

**`presenceColor`：为什么用哈希而不是随机**

```js
export function presenceColor(clientId) {
  let h = 0;
  for (let i = 0; i < clientId.length; i += 1) {
    h = (h * 31 + clientId.charCodeAt(i)) >>> 0;
  }
  return `hsl(${h % 360} 72% 46%)`;
}
```

`h * 31 + code` 是 Java 里 `String.hashCode()` 的经典算法。`>>> 0` 把结果转成无符号 32 位整数（否则乘着乘着会溢出成负数）。

**为什么要确定性？** 因为同一个人刷新页面后 `clientId` 不变（存在 sessionStorage 里），颜色也应该不变。如果随机取色，每次刷新光标颜色都变，队友会以为来了个新人。

`hsl(色相 72% 46%)` 里，色相取 `h % 360` 铺满整个色环，饱和度/亮度固定——保证**任何颜色都够鲜艳、在白色画布上都看得清**。

### 语法点

| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `Object.freeze(obj)` | 冻结对象，禁止增删改属性 | 防止常量被意外改写（且不报错，最难查） |
| `const X = Object.freeze({...})` | 用对象模拟枚举 | JS 没有原生 enum |
| `/^#[0-9a-f]{6}$/` | 正则字面量，`^$` 锚定整串 | 颜色校验，同时防注入 |
| `re.test(s)` | 测试字符串是否匹配 | 比 `match` 轻，只关心真假 |
| `typeof x === 'number'` | 类型判断 | 校验第一道关 |
| `Number.isFinite(x)` | 是有限数字（排除 NaN/Infinity） | 防止脏数字进文档 |
| `Array.isArray(x)` | 判断是不是数组 | 数组也是 object，必须单独排除 |
| `Math.round(v)` | 四舍五入取整 | 坐标只存整数，避免浮点误差累积 |
| `if (v < min) v = min` | 手写 clamp | 截断是幂等的，两端结果必然一致 |
| `x ? a : b` | 三元表达式 | 一行内做条件取值 |
| `a?.b` | 可选链：a 为空就返回 undefined，不报错 | `raw.ts` 可能不存在 |
| `[...str]` | 把字符串按码点展开成数组 | 正确统计 emoji 长度 |
| `Object.keys(obj)` | 拿所有键名组成数组 | 从规格表推导字段列表 |
| `Object.entries(obj)` | 拿 `[键, 值]` 二元组数组 | 遍历字段时同时要名字和值 |
| `for...of` | 遍历可迭代对象（数组/Set/Map） | 比 `for(i=0;i<n;i++)` 少写索引 |
| `x in obj` | 判断属性是否存在（含原型链） | 检查 `patch` 里有没有某个字段 |
| `s.trim().toLowerCase()` | 去首尾空格 + 转小写 | 归一化输入，避免同值不同写法 |
| `>>> 0` | 无符号右移 0 位，效果是转成 uint32 | 哈希结果保持非负 |
| `hsl(色相 72% 46%)` | CSS 颜色函数 | 从哈希值映射到看得清的颜色 |

### 写错了会怎样

- **去掉 `Object.freeze`**：某处笔误 `MSG.OP = 'operation'`，所有消息进 `default` 分支，白板"能画但不联网"，且控制台没有任何报错。
- **越界改成"拒绝"而不是"截断"**：把图形拖到很远的地方，本地显示正常，一刷新位置跳回去，用户以为数据丢了。
- **字符串用 `raw.length` 计长**：输入 1000 个 emoji 被判超长，用户打不出想要的内容；不同浏览器还可能表现不一致。
- **颜色只判 `typeof === 'string'` 不判正则**：`fill: "url(javascript:...)"` 直接进 Canvas，虽然 Canvas 不执行脚本，但会画出异常内容且污染文档。
- **`normalizeOp` 里先判 `patch` 后判 `opId`**：一个 `opId` 非法的消息也会走完昂贵的字段校验，限流场景下白白消耗 CPU。

## shared/merge.js（决定"两个版本撞上了听谁的"）

### 它解决什么问题

这是整个项目的心脏。前面两个文件都在为它做准备：id 用来标识，规格用来校验，而**这个文件决定最终状态**。

它要回答一个问题：

> A 说这个字段是红色（第 7 版），B 说是蓝色（第 8 版），我该信谁？

答案必须满足一个苛刻的条件：**不管这两条消息以什么顺序到达、重复多少次，全世界所有副本算出来的答案必须一样。**

### 代码逐段讲

**数据结构回顾**

```js
// 一个字段 = 一个值 + 一个戳
{ val: '#ff0000', v: 7, c: 'c-aaa', o: 'op-9' }
```

`v` 是版本号，`c` 是客户端 id，`o` 是 opId。三个一起叫"戳（stamp）"。

**`cmpStamp`：为什么必须是三个数**

```js
export function cmpStamp(a, b) {
  if (a.v !== b.v) return a.v < b.v ? -1 : 1;
  if (a.c !== b.c) return a.c < b.c ? -1 : 1;
  if (a.o !== b.o) return a.o < b.o ? -1 : 1;
  return 0;
}
```

这是一个**字典序比较**，跟比较版本号 `1.2.3 < 1.3.0` 是一个道理：先比第一位，第一位相同比第二位，以此类推。

为什么三层？因为每一层都在解决上一层解决不了的问题：

| 只比到第几层 | 会出现什么问题 |
| --- | --- |
| 只比 `v` | A 和 B 都在第 5 版基础上改，各自发出 `v=6`，**并列** |
| 比到 `v` + `c` | 同一个客户端的两条操作可能 `v` 相同（比如撤销和重做），`c` 也相同，还是并列 |
| 比到 `v` + `c` + `o` | `opId` 是 uuid，两条不同的操作不可能有相同的 opId，**永不并列** |

**并列为什么致命？** 因为并列意味着"结果取决于到达顺序"。A 的电脑上 A 先到，B 的电脑上 B 先到，两台机器算出不同结果，白板永久不一致，而且刷新也修不好（刷新只是重拉快照，各自的本地值还会继续覆盖）。

**`mergeField`：三行逻辑**

```js
export function mergeField(local, remote, opts = {}) {
  if (!local) return remote ? { ...remote } : local;
  if (!remote) return { ...local };
  const cmp = cmpStamp(remote, local);
  if (cmp > 0) return { ...remote };
  if (cmp === 0 && opts.authoritative) return { ...remote };
  return { ...local };
}
```

逐行：

1. 本地没有 → 直接用远端的（新图形第一次到达）
2. 远端没有 → 保留本地的
3. 远端戳更大 → 用远端
4. 戳相等且 `authoritative` → 用远端
5. 否则 → 保留本地

**`opts.authoritative` 是干什么的？** 它只在"远端是服务端发来的"时候为 true。作用是吸收服务端的归一化结果：

```
客户端本地：x = 250000.7（拖动时的原始值）
服务端归一化后：x = 100000（clamp + 取整）

两个戳完全一样（同一条 op），但值不同。
如果不让服务端赢，本地永远显示 250000.7，别人显示 100000 —— 分叉。
```

所以规则是：**戳相同的时候，谁更"权威"听谁的。**

**为什么每个分支都 `{ ...remote }` 而不是直接 `return remote`**

```js
if (cmp > 0) return { ...remote };
```

`{ ...remote }` 是**浅拷贝**，创建一个新对象。

如果直接 `return remote`，那么本地文档里的字段对象和网络消息里的字段对象就是**同一个引用**。之后任何一方修改它，另一方会跟着变——而这种"看不见的共享"是最难查的 bug。

> 一条铁律：**函数返回的对象，不要和入参共享引用。**

**`mergeShape`：逐字段合并**

```js
export function mergeShape(local, remote, opts = {}) {
  if (local.id !== remote.id) {
    throw new Error(`mergeShape: id 不一致 ${local.id} vs ${remote.id}`);
  }
  const next = { id: local.id, type: local.type || remote.type, fields: {} };
  const names = new Set([...Object.keys(local.fields), ...Object.keys(remote.fields)]);
  for (const name of names) {
    const merged = mergeField(local.fields[name], remote.fields[name], opts);
    if (merged) next.fields[name] = merged;
  }
  return next;
}
```

**`new Set([...a, ...b])` 这一行的作用**：两边的字段名可能不完全一样（本地有 `fill`，远端还没有），取并集才不会漏。

`Set` 自动去重，所以同一个字段名不会合并两次。展开成数组再传给 `Set` 是标准写法。

**这里抛异常是合理的**：`id` 不一致说明调用方传错了参数，这是**程序 bug**，不是预期情况。程序 bug 就该炸出来，不该静默处理。

**`mergeOp`：把 op 变成"候选图形"再合并**

```js
export function mergeOp(shape, op, opts = {}) {
  const stamp = { v: op.ver, c: op.clientId, o: op.opId, target: op.target, type: op.shapeType };
  const candidate = applyPatch(shape, op.patch, stamp);
  return mergeShape(shape, candidate, opts);
}
```

这是**最关键的一段设计**，值得慢慢看。

它没有"直接把 op 的字段写进图形"，而是：

1. 拿当前图形 + op 生成一个**候选图形**（`applyPatch`）
2. 再让当前图形和候选图形**合并**（`mergeShape`）

**为什么要绕这一圈？** 因为要保证幂等和抗乱序。

假设直接写：

```js
shape.fields.x = { val: op.patch.x, v: op.ver, ... };  // ❌ 直接覆盖
```

那么一条陈旧的 op（`ver=3`，当前已经是 `ver=8`）会把新值冲掉。

而走"候选 + 合并"的路径，`mergeField` 会比较戳：候选的 `v=3` 小于当前的 `v=8`，直接丢弃。**陈旧 op 被自然吸收，不需要任何特判。**

**这就是"合并函数满足交换律/结合律/幂等"的实际收益**：你不用写"如果 op 太旧就跳过"这种逻辑，数学性质自动帮你处理了。

**`flatten`：给渲染层用的扁平视图**

```js
export function flatten(shape) {
  const out = { id: shape.id, type: shape.type };
  for (const name of PATCH_FIELDS) {
    const cell = shape.fields[name];
    out[name] = cell === undefined ? FIELD_SPEC[name].def : cell.val;
  }
  return out;
}
```

两个作用：

1. **拆包**：把 `{val, v, c, o}` 变成裸值，画图时不用写 `shape.fields.x.val`
2. **补默认值**：字段缺失时用 `FIELD_SPEC[name].def` 填上

第 2 点很重要。一个刚 `create` 的图形可能只有 `x/y/w/h`，没有 `fill`。渲染时 `flat.fill` 会自动变成 `'#ffffff'`，不用在 `_drawShape` 里写一堆 `??` 兜底。

**为什么必须遍历 `PATCH_FIELDS` 而不是 `Object.keys(shape.fields)`？**

因为要保证**所有字段都存在**。遍历 `PATCH_FIELDS`（完整规格表），缺失的补默认值；遍历 `shape.fields`（实际有的），缺失的就没有——渲染时会拿到 `undefined`。

**`isVisible`：墓碑的读取方式**

```js
export function isVisible(shape) {
  if (!shape) return false;
  const cell = shape.fields.deleted;
  return cell === undefined ? true : cell.val !== true;
}
```

注意 `cell === undefined ? true : ...`：**没有 `deleted` 字段的图形默认是可见的**。老数据（还没引入墓碑时创建的）也能正常显示。

这种"新字段对旧数据友好"的写法叫**向后兼容**，在会长期运行的系统里是必需的。

**`shapesEqual`：判断服务端是否真的改了状态**

```js
export function shapesEqual(a, b) {
  const ka = Object.keys(a.fields).sort();
  const kb = Object.keys(b.fields).sort();
  ...
  if (x.val !== y.val || x.v !== y.v || x.c !== y.c || x.o !== y.o) return false;
}
```

**为什么要 `.sort()`？** 因为 `Object.keys()` 的顺序理论上不保证（虽然现代引擎对字符串键是按插入序）。先排序再逐个比，才能保证"同样的内容一定判等"。

**为什么连戳也要比？** 因为值相同但戳不同，意味着"有人用更高的版本写了同样的值"。这种情况下服务端仍然要广播（其他人需要更新自己的戳），所以不能判等。

**`opFingerprint`：为什么去重表要存内容指纹**

```js
export function opFingerprint(op) {
  const keys = Object.keys(op.patch).sort();
  const parts = keys.map((k) => `${k}=${JSON.stringify(op.patch[k])}`);
  return `${op.kind}|${op.target}|${op.shapeType || ''}|${op.ver}|${parts.join(',')}`;
}
```

把 op 的内容压成一个字符串。服务端存 `opId → 指纹`：

```js
if (seenFp !== fingerprint) {
  return { ok: false, code: 'OPID_CONFLICT' };  // 同 id 不同内容
}
```

**为什么不存 `opId → true` 就够？** 因为"同一条消息重复到达"和"同一个 id 被塞了不同内容"是两回事：

- 前者是正常网络行为，应该静默去重
- 后者说明客户端有 bug 或有人伪造，必须报错

**`.sort()` 又是为了顺序无关**：`{x,y}` 和 `{y,x}` 是同一个 patch，指纹必须相同。

### 语法点

| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `{ ...obj }` | 展开运算符，浅拷贝对象 | 避免返回值和入参共享引用 |
| `new Set([...a, ...b])` | 用数组构造集合，自动去重 | 求两边字段名的并集 |
| `for...of` + `Set` | 遍历集合 | 顺序无关的遍历 |
| `Object.values(obj)` | 拿所有值组成数组 | 求图形内最大版本号 |
| `Object.keys(obj).sort()` | 拿键名并排序 | 保证比较/指纹与顺序无关 |
| `arr.map(fn)` | 每个元素映射成新值 | 拼指纹 |
| `arr.join(',')` | 用分隔符拼成字符串 | 指纹拼接 |
| `JSON.stringify(v)` | 值转 JSON 字符串 | 让字符串/数字/布尔有统一表示 |
| `a === b ? -1 : 1` | 三元表达式 | 比较函数返回 -1/1 |
| `opts = {}` | 参数默认空对象 | 调用方可以完全不传 |
| `throw new Error()` | 抛异常中断执行 | id 不一致属于程序 bug，必须炸出来 |
| `x \|\| y` | 短路或：x 为假值时取 y | `local.type \|\| remote.type` 兜底 |
| `cell === undefined ? true : ...` | 显式判断 undefined | 新字段对旧数据向后兼容 |

### 写错了会怎样

- **`cmpStamp` 只比 `v`**：两人同时改，戳并列，两端结果不同，白板永久不一致，刷新也修不好。
- **`mergeField` 直接 `return remote`（不拷贝）**：本地文档和网络消息共享同一个对象，一处修改处处生效，出现"改 A 图形结果 B 图形也变了"的灵异现象。
- **`mergeOp` 直接覆盖字段而不走候选合并**：离线期间产生的旧 op 会把在线端的新值冲掉，用户看到"我的编辑被自己弄没了"。
- **`flatten` 遍历 `shape.fields` 而不是 `PATCH_FIELDS`**：新建图形没有 `fill` 字段时，`flat.fill` 是 `undefined`，Canvas 的 `fillStyle = undefined` 会保留上一次的颜色，画出颜色错乱的图形。
- **`shapesEqual` 不排序键名**：字段插入顺序不同的两个等价图形被判为不等，服务端每次都认为"有变更"，产生大量无意义的广播。

## 这一篇的三个结论

1. **id 唯一**，是去重和指认的前提；生成时要考虑非安全上下文（局域网 http）。
2. **字段规格单一真相源**，校验、默认值、渲染全从一张表推导，两端共用同一份代码。
3. **合并函数靠数学性质收敛**，不靠服务端裁决；能幂等修正的就修正（clamp），修正不了的才拒绝。
