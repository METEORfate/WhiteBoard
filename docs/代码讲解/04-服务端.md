# 04 服务端：静态资源 + 房间状态 + 手写 WebSocket

服务端 6 个文件、零 npm 依赖。主线：`index.js` 把普通请求交给 `static.js`，把 Upgrade 交给 `ws.js` 拆帧，再交给 `room.js` 改状态、`store.js` 落盘、广播回所有人。

---

## server/config.js（把路径和阈值集中成一份只读常量）

### 它解决什么问题

路径（项目根、静态目录、数据目录）和阈值（hello 几秒内到、空闲多久算死）如果散在各文件里，改一个端口要翻五处，还容易出现两处数字不一致。这里启动时算一次，之后谁要谁拿。

### 代码逐段讲

**从模块自身位置推出项目根**
```js
const here = dirname(fileURLToPath(import.meta.url));

export const ROOT_DIR = resolve(here, '..');
```
`import.meta.url` 是本模块的地址，形如 `file:///D:/project/Tec/WB/whiteboard/server/config.js`。ES Module 里没有 `__dirname`，只能从它反推：`fileURLToPath` 转成 `D:\...`，`dirname` 取目录，`resolve(here, '..')` 上跳一级。关键是**不依赖启动目录**：用 `process.cwd()` 的话，`cd docs && node ../server/index.js` 会把根算成 `docs`，静态文件全 404。

**配置对象**
```js
export const CONFIG = Object.freeze({
  port: Number(process.env.PORT || 8787),
  host: process.env.HOST || '0.0.0.0',
  dataDir: process.env.DATA_DIR || resolve(ROOT_DIR, 'data'),
  /** 挂载点 → 磁盘目录，只有这两个目录对外可见 */
  mounts: {
    '/client/': resolve(ROOT_DIR, 'client'),
    '/shared/': resolve(ROOT_DIR, 'shared'),
  },
  helloTimeoutMs: 10_000,
  idleTimeoutMs: 60_000,
```
`process.env` 里全是字符串或 `undefined`，`||` 给默认值。`Number()` 不能省：`listen('8787')` 会把字符串当命名管道名，报的错和端口毫无关系。`'0.0.0.0'` 监听所有网卡，局域网可访问；`'127.0.0.1'` 只有本机。`mounts` 是安全边界：磁盘上其他目录（`server/`、`data/`）没有对应 URL，`static.js` 也只在这两个目录里做校验。`10_000` 的下划线是数字分隔符，等于 `10000`。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `import { x } from 'node:url'` | 具名导入，`node:` 前缀是内置模块 | 一眼看出没有 npm 依赖 |
| `import.meta.url` + `fileURLToPath(u)` | 当前模块 URL，转成 `D:\a.js` | ESM 没有 `__dirname` |
| `dirname` / `resolve(a,'..')` | 取父目录 / 拼绝对路径并处理 `..` | 算项目根，不受启动目录影响 |
| `process.env.PORT` | 读环境变量，没有则 `undefined` | 部署时不改代码换端口 |
| `a \|\| b` / `Number(s)` | 假值兜底 / 字符串转数字 | 默认端口，`listen` 要数字 |
| `Object.freeze(o)` | 冻结对象（**浅冻结**） | 防运行中被偷改端口 |

### 写错了会怎样

- **忘了 `Number()`**：`PORT=9000` 时报 `EACCES` 或卡住，错误信息里看不出是类型问题。
- **`ROOT_DIR` 用 `process.cwd()`**：从别的目录启动整站 404，而从项目根启动一切正常。

## server/store.js（追加写 JSONL + 启动重放 + 原子压缩）

### 它解决什么问题

"每次改完把整个房间序列化一遍"在几千图形时改一个像素就要写全量，几秒能把磁盘写满。这里用**追加日志**（JSONL，一行一个 JSON，每行是"某刻某图形变成了什么样"）：写一笔只追加几十字节，成本与房间大小无关；重启时从头读、按顺序覆盖就还原。不用数据库是因为要零依赖（SQLite 要原生编译），而"一个房间一个文件、`cat` 能看懂"对调试更有价值。代价是没有索引和事务，但只有一个写者（Node 单线程），日志天然串行。

### 代码逐段讲

**文件命名与内存计数**

文件名是 `${roomId}.jsonl`，`roomId` 已被 `shared/protocol.js` 的 `/^[A-Za-z0-9_-]{1,64}$/` 卡死，不含 `/`、`..`，拼路径不会穿越。构造时还有 `mkdirSync(dir, { recursive: true })`（等于 `mkdir -p`，已存在不报错）和 `this.lineCounts = new Map()`：内存里记每个房间的行数，只用于判断"该不该压缩"，否则每次追加都去读文件数换行，复杂度 O(n²)。

**逐行解析，坏行跳过**
```js
    for (const raw of text.split('\n')) {
      const line = raw.trim();
      if (!line) continue;
      let rec;
      try {
        rec = JSON.parse(line);
      } catch {
        truncated += 1; // 崩溃时可能留下半行
        continue;
      }
```
文件末尾有换行，`split` 多出一个空串，`if (!line)` 跳过。核心是 `try/catch`：`appendFileSync` 写的是 `{...}\n`，进程在写 `{` 后被杀就留下 `{"seq":41,"sha`。这种行永远解析不了，抛异常就计数跳过——没有校验和，靠"JSON 必须完整才解析得出来"。读到 `{snapshot:true, seq, shapes}` 时先 `shapes.clear()` 再整批 `set`，因为它代表"此刻的完整状态"，之前的行全被取代；普通行 `{seq, shape}` 直接 `set`，同一 id 后写覆盖先写。

**为什么 seq 取最大值而不是行数**

两者只在"每行严格 +1 且从 1 开始"时相等，而这个前提会被打破：压缩后只剩 1 行但 seq 可能是 4317；半行被跳过后序号有空洞。按行数算，重启后 `serverSeq` 从 4317 掉回 1，客户端手里 `lastAppliedSeq=4317`，会把之后所有广播判成过期丢掉，表现为"重启后大家还能画，但互相看不见"。

**半行之后立刻重写**
```js
    if (truncated > 0) {
      // 崩溃留下的半行会与下一次 append 粘成一行新的坏数据，
      // 因此加载后立刻用内存态重写文件（原子 rename）。
      this.compact(roomId, [...shapes.values()], seq);
```
只跳过坏行不够：结尾是 `{"seq":41,"sha`（无换行），下次 append 接上 `{"seq":42,...}\n`，得到一行坏数据，把第 42 条也吃掉。

**追加写：为什么宁可阻塞**
```js
  append(roomId, record) {
    appendFileSync(this.fileOf(roomId), `${JSON.stringify(record)}\n`);
    const next = (this.lineCounts.get(roomId) || 0) + 1;
    this.lineCounts.set(roomId, next);
```
每次 `open(O_APPEND)` → `write` → `close`，慢，但**同步**：返回时数据已交给操作系统。`room.js` 是"先 append 再广播"，改成异步 `fs.appendFile(cb)` 的话，append 立刻返回、广播先发出去，进程在回调执行前崩溃——客户端已确认的 op 磁盘上没有。同步写把"存在"和"广播"绑成不可分割的先后；单条几百字节，且令牌桶把连接限到 60 op/秒，阻塞不会堆积。

**原子压缩**
```js
  compact(roomId, shapes, seq) {
    const payload = `${JSON.stringify({ snapshot: true, seq, shapes })}\n`;
    const tmp = `${this.fileOf(roomId)}.tmp`;
    writeFileSync(tmp, payload);
    renameSync(tmp, this.fileOf(roomId));
```
直接覆盖正式文件，写一半崩溃就截断，几千条历史全丢。所以先写 `.tmp`，写完再 `rename`——`rename` 在同一文件系统内是**原子**的：要么看到旧文件，要么看到新文件，没有中间态。崩溃在 rename 前正式文件完好；在之后就是完整快照。所以 `.tmp` 必须放同目录，不能放 `/tmp`。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `class` / `constructor` | 类与构造，`new` 时执行 | 一个实例服务所有房间 |
| `new Map()` / `[...map.values()]` | 键值表 / 迭代器摊成数组 | 按 id 存图形，JSON 存不了 Map |
| `split('\n')` / `trim()` | 切行 / 去首尾空白（含 `\r`） | Windows 换行是 `\r\n` |
| `try {} catch {}`（无参数） | 捕获异常但不用异常对象 | 只关心"失败了" |
| `Array.isArray(x)` | 是否数组 | `typeof []` 也是 `'object'` |
| `appendFileSync` / `writeFileSync` | 追加写 / 覆盖写 | 日志只往后加；tmp 整份重写 |
| `renameSync(a,b)` | 重命名，同分区原子 | 压缩不能出现半个文件 |
| `JSON.stringify/parse` | 对象↔字符串，后者非法即抛 | 半行检测靠它 |

### 写错了会怎样

- **`append` 改成异步**：`kill -9` 一下，最后几条 op 只存在客户端内存里，重启后永远同步不出去。
- **`compact` 直接覆盖正式文件**：压缩几千图形时断电，文件截断成半行，下次启动只恢复前一半，用户看到白板"少了一半"且无报错。

## server/ws.js（手写 RFC 6455：把 TCP 字节流切成 WebSocket 帧）

### 它解决什么问题

普通 HTTP 是一问一答：客户端发请求、服务端回响应，响应写完就结束。就算 keep-alive 复用连接，还是"客户端问、服务端答"，服务端没法主动塞消息。白板要的正好相反：A 画一笔，服务端立刻推给 B、C、D，而它们什么都没问。

**WebSocket 就是在同一条 TCP 连接上做全双工**：握手后两边随时都能发。起点仍是一次普通 HTTP 请求，多了几个头，请求"把这根连接从 HTTP 语义里摘出来，之后按我规定的格式发字节"；服务端回 `101 Switching Protocols` 表示同意，此后连接上跑的不再是 HTTP 报文，而是一帧一帧的二进制。

浏览器只会说 WebSocket，Node 的 `http` 只会解析 HTTP，中间这层要么装 `ws` 包，要么自己写。项目要零依赖、`node server/index.js` 直接能跑，所以自己写。

### 代码逐段讲

**握手：一个常量加一次 SHA1**
```js
const GUID = '258EAFA5-E914-47DA-95CA-C5AB0DC85B11';

export function computeAccept(key) {
  return createHash('sha1').update(key + GUID).digest('base64');
}
```
`key` 是客户端在 `Sec-WebSocket-Key` 里发的值，本质是随机 16 字节的 base64（24 字符）。服务端把 key 这个**字符串**（不是解码后的字节）和 GUID 拼接、算 SHA1、把 20 字节摘要做 base64 放回 `Sec-WebSocket-Accept`。为什么这么绕：服务端要证明"我真的是 WebSocket 服务端，不是碰巧返回 101 的普通服务"。GUID 是 RFC 写死的，所有实现都背下来了；客户端自己算一遍比对，对不上就断开。SHA1 在这里**不是安全机制**（key 明文传输，谁都能算），只是协议约定的校验和，用来挡住代理、缓存和把升级请求当普通请求处理的中间件。GUID 末尾是 `C5AB0DC85B11`。写成别的值，自己写的客户端和服务端会"自洽"地跑通（两边同一个错值），但真实浏览器一律拒绝——所以测试用 RFC 官方向量把它钉死。

**帧头怎么编码**
```js
  const len = payload.length;
  const maskBit = masked ? 0x80 : 0x00;

  if (len < 126) {
    header = Buffer.alloc(2);
    header[1] = maskBit | len;
  } else if (len < 65536) {
    header = Buffer.alloc(4);
    header[1] = maskBit | 126;
    header.writeUInt16BE(len, 2);
  } else {
    header = Buffer.alloc(10);
    header[1] = maskBit | 127;
    header.writeBigUInt64BE(BigInt(len), 2);
  }
  header[0] = (fin ? 0x80 : 0x00) | opcode;
```
第 1 字节是 `FIN(1) | RSV(3) | opcode(4)`：`0x80` 是 `1000 0000`，置最高位表示"消息最后一帧"，`| opcode` 填低 4 位，两者不冲突（opcode 最大 15）。第 2 字节是 `MASK(1) | len(7)`。7 位最大 127，但 126/127 被征用成转义标记，于是正好对应 7/16/64 位三档：0~125 直接写这 7 位（帧头 2 字节）；126~65535 写 `126` 后跟 2 字节大端（帧头 4 字节）；≥65536 写 `127` 后跟 8 字节大端（帧头 10 字节）。`Buffer.alloc(n)` 会清零，必须用：没写到的位（比如 RSV）要保证是 0。`Buffer.allocUnsafe(n)` 不清零，快但可能读到旧数据，只用于每字节都会被写满的载荷。`writeBigUInt64BE(BigInt(len), 2)` 的 64 位超出 JS 安全整数范围，Node 要求传 `BigInt`。

**具体字节：一个 5 字节的文本帧**

服务端给客户端发 `"hi!"`：
```
 81 03 68 69 21
```
| 字节 | 值 | 二进制 | 含义 |
| --- | --- | --- | --- |
| 0 | `81` | `1000 0001` | FIN=1，opcode=1（文本） |
| 1 | `03` | `0000 0011` | MASK=0，长度=3 |
| 2 | `68` | `0110 1000` | `h` |
| 3 | `69` | `0110 1001` | `i` |
| 4 | `21` | `0010 0001` | `!` |

长度 200 的帧头变 4 字节：`81 7E 00 C8`（`0xC8=200`）。长度 70000（`0x11170`）变 10 字节：`81 7F 00 00 00 00 00 01 11 70`。

**客户端发同样内容，多 4 字节掩码**
```
 81 82 37 fa 21 3d 5f 93
```
| 字节 | 值 | 含义 |
| --- | --- | --- |
| 0 | `81` | FIN=1，opcode=1 |
| 1 | `82` | MASK=1，长度=2 |
| 2~5 | `37 fa 21 3d` | 4 字节随机掩码 |
| 6 | `5f` | `'h'(0x68) ^ 0x37` |
| 7 | `93` | `'i'(0x69) ^ 0xFA` |

**为什么客户端必须掩码、服务端必须不掩码**

RFC 6455 §5.1 硬性规定：客户端帧 MASK 必须为 1，服务端帧必须为 0；收错方向立即断开。原因不是加密（掩码明文写在帧头里），而是**防代理缓存投毒**。假设攻击者能完全控制自己发出的字节，若允许不掩码，他就能构造一段"看起来像 HTTP 请求"的载荷，骗代理把 `GET /admin` 的响应缓存给下一个用户。强制掩码后，**攻击者无法控制线路上出现的字节**——掩码随机，异或之后是什么他事先不知道，拼不出想要的报文。服务端是可信的一端，不需要防这个，所以服务端帧不掩码，省一次异或。代码里由两个开关控制：服务端 `requireMask: true` / `sendMasked: false`，测试客户端反过来。

**掩码的编解码**
```js
  const mask = randomBytes(4);
  const body = Buffer.allocUnsafe(len);
  for (let i = 0; i < len; i += 1) body[i] = payload[i] ^ mask[i & 3];
```
**每一帧都重新生成掩码**，绝不复用——复用会让攻击者对比两帧反推出掩码，重新获得控制字节的能力。`i & 3` 等于 `i % 4`（3 是 `011`，按位与就是取最低两位），位运算更快，意图也更明确："取掩码的第几个字节"。异或自反：`(a^k)^k === a`，所以编解码是同一个操作。

**连接对象与 socket 事件**
```js
export class WSConnection extends EventEmitter {
  constructor(socket, opts = {}) {
    super();
    this.requireMask = opts.requireMask !== false;
    this.sendMasked = opts.sendMasked === true;
    this.buffer = EMPTY;
    this.fragments = [];
```
`extends EventEmitter` 白拿 `on`/`emit`/`off`；`super()` 必须先调，否则 `this` 不可用。`!== false` 是"默认 true"，`=== true` 是"默认 false"。`buffer` 存"收到了但还凑不成完整帧"的字节，`fragments` 用于分片重组。`socket` 是 `net.Socket`，一条 TCP 连接。`'data'` 给的 `chunk` **长度和边界完全由网络决定**：可能 3 字节，也可能 100KB——这是后面所有缓冲区逻辑的根源。`setNoDelay(true)` 关掉 Nagle，否则白板的小包会被攒 40ms 再发，手感明显变卡。`#emitClose` 的 `#` 是私有方法，类外调用是语法错误；里面用 `closeEmitted` 保证 `'close'` 只发一次，因为 `'error'`、`'close'`、`#fail`、`destroy` 都可能触发它。

**半包与粘包**
```js
  #onData(chunk) {
    this.lastSeen = Date.now();
    this.buffer = this.buffer.length === 0 ? chunk : Buffer.concat([this.buffer, chunk]);
    this.#parse();
  }
```
这是处理**半包**的第一层：新字节拼到旧缓冲区后面，缓冲区空时直接用 `chunk`，省一次拷贝。一次 TCP 读取可能只有半个帧，也可能有三个完整帧——下面的循环负责把"能拆的都拆掉"。
```js
  #parse() {
    for (;;) {
      const buf = this.buffer;
      if (this.closed || buf.length < 2) return;

      const b0 = buf[0];
      const b1 = buf[1];
      const fin = (b0 & 0x80) !== 0;
      const rsv = b0 & 0x70;
      const opcode = b0 & 0x0f;
      const masked = (b1 & 0x80) !== 0;
      let len = b1 & 0x7f;
      let offset = 2;
```
`for (;;)` 是无限循环，靠内部 `return` 退出。为什么无限：一次 `'data'` 可能带来**三个完整帧**（粘包），必须拆到拆不动为止。`buf.length < 2` 连帧头都不够，返回等下一批。这一段全是位运算取位：`& 0x80`（`1000 0000`）只留最高位 → FIN、MASK，`!== 0` 转布尔；`& 0x70`（`0111 0000`）留中间三位 → RSV，保留数字以便判断"是否全 0"；`& 0x0f`（`0000 1111`）留低 4 位 → opcode；`& 0x7f`（`0111 1111`）留低 7 位 → 长度。`offset` 记帧头已占字节数，用来定位掩码和载荷。
```js
      if (len === 126) {
        if (buf.length < 4) return;
        len = buf.readUInt16BE(2);
        offset = 4;
      } else if (len === 127) {
        if (buf.length < 10) return;
        const big = buf.readBigUInt64BE(2);
        if (big > BigInt(this.maxPayload)) {
          return this.#fail(CLOSE_CODE.MESSAGE_TOO_BIG, '帧超出上限');
        }
        len = Number(big);
        offset = 10;
      }
```
`buf.length < 4` 是**半包的第二种情况**：帧头本身没收全，此时一个字节都不能消费。`readUInt16BE(2)` 从第 2 字节读 2 字节按大端解释，`readBigUInt64BE(2)` 读 8 字节返回 `BigInt`。127 分支**先用 BigInt 比较再转 Number**：先 `Number(big)` 的话，恶意构造的 `0xFFFFFFFFFFFFFFFF` 会变成 `1.8e19`，精度已丢；BigInt 比较精确，能在转换前拒绝。长度检查在**分配内存之前**，否则一个声称"我要发 4GB"的帧头就能让服务端当场 OOM——这叫长度字段炸弹。
```js
      if (this.requireMask && !masked) {
        return this.#fail(CLOSE_CODE.PROTOCOL_ERROR, '客户端帧必须掩码');
      }

      const isControl = (opcode & 0x08) !== 0;
      if (isControl && (len > 125 || !fin)) {
        return this.#fail(CLOSE_CODE.PROTOCOL_ERROR, '控制帧不可分片且载荷 ≤125');
      }
```
`& 0x08` 一次区分控制帧和数据帧（8/9/a 的第 3 位都是 1）。控制帧两条限制：载荷 ≤125，这样长度永远塞得进那 7 位，帧头固定 2 字节，中间设备不用为了读一个 ping 去等 8 字节长度字段；不能分片，因为 ping/pong/close 都要立刻处理，允许拆帧的话接收方得攒完才能回应，心跳就失去意义。反过来说，**数据帧分片中间可以插控制帧**——这正是分片存在的意义之一：大消息传到一半，对端可以插个 ping 说"我还活着"。
```js
      const maskOffset = offset;
      if (masked) offset += 4;
      if (buf.length < offset + len) return; // 半包，等更多数据

      let payload = buf.subarray(offset, offset + len);
      if (masked) {
        const mask = buf.subarray(maskOffset, maskOffset + 4);
        const copy = Buffer.allocUnsafe(len);
        for (let i = 0; i < len; i += 1) copy[i] = payload[i] ^ mask[i & 3];
        payload = copy;
      }

      this.buffer = buf.subarray(offset + len);
```
`buf.length < offset + len` 是**半包的第三种情况**：帧头齐了载荷没齐，同样一个字节不动。这个判断是整套缓冲区逻辑的关键。`subarray(a, b)` 返回**原 Buffer 的视图**（共享内存、不拷贝），切载荷几乎零成本。但解码必须拷贝到新 Buffer 再异或：`buf` 就是 `this.buffer` 的底层内存，原地改会毁掉原始字节，需要重新解析时再也读不回来。`this.buffer = buf.subarray(offset + len)` 把处理完的字节切掉，剩下的（下一帧开头，或什么都没有）留给下一轮。

**控制帧**

收到 close 要**回一个 close**，这是关闭握手，不回应的话对端会等到超时；close 帧可以完全不带载荷（"关了，没原因"），此时用默认 1000，`socket.end()` 只发 FIN、不立刻销毁，让内核缓冲区里的 close 帧能真正发出去。`PING` 分支回 `PONG` 并把载荷**原样带回**（RFC 要求）；浏览器不允许 JS 主动发 ping/pong 帧，所以真实心跳走应用层 `{type:'ping'}`。

**分片重组与 UTF-8 校验**
```js
        if (opcode === OPCODE.TEXT && this.fragments.length > 0) {
          return this.#fail(CLOSE_CODE.PROTOCOL_ERROR, '分片未结束又来新消息');
        }
        if (opcode === OPCODE.CONT && this.fragments.length === 0) {
          return this.#fail(CLOSE_CODE.PROTOCOL_ERROR, '孤立的 continuation 帧');
        }
        this.fragmentSize += payload.length;
        this.fragments.push(payload);
        if (!fin) return;
```
规则：消息第一帧 opcode 是 1（TEXT），后续续帧全是 0（CONT），最后一帧 FIN=1。两种非法情况必须拒绝：上一条消息没结束又来 TEXT；或没开始就来 CONT。不检查的话 `fragments` 会混进两条消息的片段，拼出来是乱码。`fragmentSize` 累加**所有分片总长**：单帧已卡过上限，但 100 个 64KB 分片能拼出 6.4MB，所以"单帧上限"和"消息上限"要分别卡。
```js
const decoder = new TextDecoder('utf-8', { fatal: true });
```
模块顶部这一行。`fatal: true` 是关键：默认行为是遇到非法字节替换成 `�`（U+FFFD）**且不报错**，`fatal` 让它抛异常。为什么必须严格：JS 字符串是 UTF-16，`"a"` 和 `"a\uFFFD"` 是两个不同的字符串。非法字节被静默替换时，浏览器解码器、Node 解码器、不同版本可能给出不同结果，同一条 op 在不同端算出不同文本，状态永久分叉。**宁可断开，也不要静默产生分歧。** 用 1007 而不是 1002：1002 是"帧结构不对"，1007 是"结构没问题但载荷不是合法 UTF-8"。

**发送与关闭**

`send(data)` 接受字符串或对象，`Buffer.from(text, 'utf8')` 是**编码**，和前面的解码互为逆操作；`socket.write` 返回 `false` 表示内核缓冲区满（背压），**不是失败**，数据仍会发出去，只是调用方该等 `'drain'`。`close()` 先写 close 帧、再 `end()` 发 FIN，然后**延迟 50ms 才 emit close**（`setTimeout(...).unref?.()`）。立刻 emit 的话，上层可能在 close 帧还在内核缓冲区时就清理（甚至关进程），对端只看到"连接被重置"；`unref` 让这个定时器不阻止进程退出。`destroy()` 是兜底：直接掐 TCP、不发 close 帧，回 1006（异常关闭，只用于本地报告，永不写上线）。

**升级处理**
```js
  if (!key || Buffer.from(key, 'base64').length !== 16) {
    return rejectUpgrade(socket, 400, 'Bad Sec-WebSocket-Key'), null;
  }
  if (version !== '13') return rejectUpgrade(socket, 426, 'Unsupported WebSocket Version'), null;

  const accept = computeAccept(key);
  socket.write(
    'HTTP/1.1 101 Switching Protocols\r\n' +
      'Upgrade: websocket\r\n' +
      'Connection: Upgrade\r\n' +
      `Sec-WebSocket-Accept: ${accept}\r\n\r\n`,
  );

  const conn = new WSConnection(socket, opts);
  conn.feed(head);
```
`acceptUpgrade` 由 `index.js` 的 `server.on('upgrade')` 调用——那是 Node 在 HTTP 解析器读到 `Upgrade` 头后触发的事件，普通 `request` 回调收不到它。拒绝时 `socket` 是裸 TCP，`http` 已不接管，只能手写 HTTP 报文（`rejectUpgrade` 里用 `Buffer.byteLength` 算 `Content-Length`，用 `body.length` 会让中文少算）。`Buffer.from(key,'base64').length !== 16` 既是格式校验，也顺手挡掉超长 key。101 的三个头少一个浏览器都会断开，`\r\n\r\n` 表示头结束。`head` 是**握手请求之后已读到缓冲区、但还没被 HTTP 解析器消费的字节**。客户端发完握手可能立刻发第一条消息，两批字节一起到达；解析器在 `\r\n\r\n` 处停下，剩下的通过 `head` 交出来。不 `feed(head)` 的话第一批消息永远卡在外面，表现为"连上了但第一条消息丢了"。

**测试客户端**：`agent: false` 不能省——全局 HTTP agent 会剥掉 `Connection`、`Upgrade` 这些**逐跳头**，请求退化成普通 `GET /ws`，服务端直接 404；客户端也必须校验 accept，否则连到假的 101 也会当成功。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `class A extends B` / `super()` | 继承；不调 `super` 不能用 `this` | 白拿 `on`/`emit`/`off` |
| `#method()` | 私有方法，类外访问是语法错误 | 拆帧细节不对外暴露 |
| `get isOpen()` | 属性式读取，访问时现算 | 反映 socket 最新状态 |
| `Buffer.alloc(n)` / `Buffer.allocUnsafe(n)` | 分配并清零 / 分配不清零 | 帧头没写的位必须是 0；载荷每字节都会写满 |
| `Buffer.from(s, 'utf8'/'base64')` | 字符串↔字节 | 发送编码 / 校验 key |
| `buf.subarray(a,b)` | 切一段，**共享内存不拷贝** | 零成本取载荷、消费缓冲区 |
| `readUInt16BE` / `readBigUInt64BE` | 按大端读 2 / 8 字节 | 16 / 64 位长度 |
| `writeUInt16BE` / `writeBigUInt64BE` | 按大端写 2 / 8 字节 | 关闭码、64 位长度 |
| `BigInt(x)` / `Number(b)` | 大整数↔普通数字 | 先精确比较再转换 |
| `& 0x80 / 0x7f / 0x0f / 0x70 / 0x08` | 按位与，只保留指定位 | 取 FIN/MASK/长度/opcode/RSV |
| `a \| b` / `a ^ b` | 按位或拼位 / 按位异或（自反） | 合成帧头字节、掩码编解码 |
| `i & 3` | 取最低两位，等于 `i % 4` | 掩码 4 字节循环 |
| `x >>> 0` | 转无符号 32 位（见下） | 本文件未用，见 `protocol.js:289` |
| `??` / `?.()` | 空值合并 / 可选调用 | 默认值；`unref` 不一定存在 |
| `for (;;)` | 无限循环 | 一包数据里可能有多个帧 |
| `return this.#fail(...)` | 借返回值提前结束 | 少写一个 `return;` |
| `switch` + `case A: { }` | 多分支，case 加大括号 | 让 `const` 不串作用域 |
| `new TextDecoder('utf-8',{fatal:true})` | 严格解码器 | 非法字节抛错而不是替换 |
| `createHash('sha1').update(s).digest('base64')` | 算摘要并输出 base64 | 一行完成握手计算 |
| `randomBytes(4)` | 密码学安全随机字节 | 掩码必须不可预测 |

**关于 `>>> 0`**：本文件没用到，但和上面同族，`shared/protocol.js:289` 有典型用法 `h = (h * 31 + clientId.charCodeAt(i)) >>> 0;`。JS 数字是 64 位浮点，`h * 31` 反复累加会超过 2^32 变成丢精度的大浮点；`>>> 0` 的语义是"按 ToUint32 截断到 0~2^32-1 再当无符号数读回"，等价于取模 2^32，这样 `h % 360` 才能得到稳定颜色。不能用 `>> 0`：它是带符号右移，最高位当符号位，`-1 >> 0` 还是 `-1`，`% 360` 会出负角度。

### 写错了会怎样

- **GUID 写错一个字符**：自写客户端照样能连（两边同一个错值），浏览器直接 `WebSocket connection failed`，控制台没有细节。
- **删掉 `if (buf.length < offset + len) return;`**：载荷没齐时 `subarray` 返回短 Buffer，JSON 解析报错；更糟的是消费时把还没到的字节也切掉，之后帧边界全错，表现为"偶尔丢消息、偶尔乱码"。

## server/room.js（单房间的权威状态：序列化点、幂等去重、归一化权威）

### 它解决什么问题

多个客户端同时改同一块白板，消息顺序不定、可能重复、可能迟到。逐字段 max 合并本身能收敛，但还需要一个**所有人都认同的参照点**，否则没人知道"我是不是落后了""这条我是不是处理过"。`Room` 就是这个参照点，扮演三个角色：**序列化点**（op 串行处理，给每条真正改变状态的 op 盖单调 `serverSeq`）、**幂等去重**（`opId` 见过就回放上次结果）、**归一化权威**（越界值在这里 clamp，广播的是归一化后的全量图形）。它不负责"算对"——一致性靠客户端逐字段合并，它只保证"同一个 op 序列，所有客户端算出同一个结果"。

### 代码逐段讲

**五张表**

`shapes`（id → 带戳图形）存**每字段带 `{val,v,c,o}` 的结构**而不是扁平值，合并需要版本号；删除的图形也留着（墓碑，`deleted` 为 true），否则一条迟到的 `patch` 会把已删图形当新图形建回来。`hwm` 的 key 是 `clientId:sessionEpoch` 而不是只用 `clientId`：标签页刷新后 `sessionEpoch` 变了，新会话的 `clientSeq` 从 1 开始，不能拿旧高水位卡它。`members` 按连接，`presence` 按人（同一个人的两个标签页只显示一个光标）。

**加入房间：joined / pending 防的竞态**
```js
  join(conn) {
    conn.joined = false;
    conn.pending = [];
    this.members.set(conn.id, conn);

    conn.send({
      type: MSG.WELCOME,
      serverSeq: this.serverSeq,
      shapes: [...this.shapes.values()],
      members: this.memberList(),
    });

    conn.joined = true;
    const buffered = conn.pending || [];
    conn.pending = null;
    for (const frame of buffered) conn.send(frame);
```
顺序不能改，这是全文最微妙的一段。`joined = false` + `pending = []` 是给 `broadcast` 的信号："我的快照还没发完，先存 pending 里"。防的竞态：`WELCOME` 带的是**此刻**的全量快照，几十 KB，会分成多个 TCP 段。如果发快照期间有 op 被广播，而它先于快照到达客户端，客户端会先应用它、再收到快照、然后被快照整个覆盖——那条 op 就丢了。更隐蔽的是它的 `seq` 比快照里的 `serverSeq` 大，客户端 `lastAppliedSeq` 已经前进，自己都不知道丢了东西。`joined = true` 后再补发 pending，保证客户端收到"完整快照 → 之后的所有变更"，`seq` 严格递增。`pending = null` 是"缓冲期结束"的标记。pending 有上限（2000）：客户端握手后一直不读数据（TCP 窗口满），`WELCOME` 发不出去，`joined` 永远 false，广播全堆进 pending——不设上限就是内存泄漏，超了用 1008 踢掉重连。

**第 1、2 步：校验与身份**
```js
    const parsed = normalizeOp(rawOp);
    if (!parsed.ok) {
      return { ok: false, code: parsed.code, message: parsed.message };
    }
    const op = parsed.op;

    if (op.roomId !== this.id) {
      this.stats.rejected += 1;
      return { ok: false, code: 'ROOM_MISMATCH', message: 'op.roomId 与当前房间不一致' };
    }
    if (op.clientId !== conn.clientId) {
      this.stats.rejected += 1;
      return { ok: false, code: 'CLIENT_MISMATCH', message: 'op.clientId 与连接身份不一致' };
    }
```
第一步永远校验。`normalizeOp` 来自 `shared/protocol.js`，**浏览器和 Node 引同一份文件**，保证 clamp/取整一致；各写一份的话，服务端取整成 100、客户端算成 100.4，就永久差 0.4。校验失败直接返回，不碰状态，后面才能假设字段类型合法。op 自带的 `clientId` 可能和连接身份不一致。不检查的话谁都能伪造别人发 op，制造"某人删了你的图形"的假象，还能污染 `hwm` 让别人被误判。

**为什么顺序是"校验 → 身份 → 去重"**：去重放最前面的话，攻击者能用伪造 `opId` 探测"这个 id 是否存在"，还能往 `seen` 里塞垃圾把真记录挤掉。身份检查必须在任何查表之前。

**第 3 步：幂等（存指纹而不是 true）**
```js
    const fingerprint = opFingerprint(op);
    const seenFp = this.seen.get(op.opId);
    if (seenFp !== undefined) {
      if (seenFp !== fingerprint) {
        return { ok: false, code: 'OPID_CONFLICT', message: '同一 opId 携带了不同内容', resync: true };
      }
      return { ok: true, accepted: true, duplicate: true, shape: this.shapes.get(op.target) || null, seq: null };
    }
```
存 `opId → 指纹` 而不是 `opId → true`。因为 UUID 撞车、客户端 bug 重用 id、故意伪造都会产生"同 opId 不同内容"：存指纹才能区分——一样是正常重传，直接回上次结果；不一样是严重问题，拒绝并要求重连。`opFingerprint` 把 `kind|target|shapeType|ver|排序后的字段` 拼成字符串，排序是为了让 `{x,y}` 和 `{y,x}` 得到同一指纹（JSON 键顺序不保证）。`seq: null` 表示"没产生新序号"，客户端据此不推进 `lastAppliedSeq`（上次已推进过）。

**第 4 步：clientSeq 高水位**
```js
    const hwmKey = `${op.clientId}:${op.sessionEpoch}`;
    const hwm = this.hwm.get(hwmKey) || 0;
    if (op.clientSeq <= hwm) {
      return { ok: false, code: 'SEQ_RESET', message: `clientSeq ${op.clientSeq} 不大于高水位 ${hwm}`, resync: true };
    }
```
正常重传的 `clientSeq` 也 `<= hwm`，但它在第 3 步就被 `opId` 挡住了，走不到这里。能到这里的"低序号"意味着：**一个没见过的 opId 配了不该出现的序号**——只能是客户端发送队列被清空、计数器归零，它内存里的状态和序号已经对不上。继续接受会让服务端被"重放"的旧操作污染（比如把已删图形画回来），所以不是忽略，而是 `resync: true` 强制全量重拉。**去重必须在高水位之前**：反过来，所有正常重传都会命中 `SEQ_RESET`，每次网络抖动都触发全量重同步。

**第 5、6 步：存在性与合并**

`patch`/`delete` 一个服务端没有的图形（`!current && op.kind !== OP_KIND.CREATE`），说明客户端认为有、服务端没有——两边已分叉，回 `UNKNOWN_SHAPE` 并要求重同步；同一个 id 换类型（`current.type !== op.shapeType`）是客户端 bug，回 `TYPE_CONFLICT`。房间上限 5000 只在新建时查，遍历所有图形数"活着的"是 O(n)，但只在 `!current` 时跑，微秒级。
```js
    const next = mergeOp(current, op);
    const changed = !shapesEqual(current, next);

    this.seen.set(op.opId, fingerprint);
    this.hwm.set(hwmKey, op.clientSeq);
    if (this.seen.size > this.config.seenOpLimit) {
      const oldest = this.seen.keys().next().value;
      this.seen.delete(oldest);
    }

    if (!changed) {
      return { ok: true, accepted: false, duplicate: false, shape: current, seq: null };
    }
```
`mergeOp` 对每个字段取"戳最大者"。一条迟到 op（`ver` 更小）在每个字段上都输，结果和 `current` 一模一样，`shapesEqual` 返回 true。

**这就是"陈旧 op 不需要特判"的原因**：不靠"比时间戳然后 if 跳过"，而靠合并函数本身的幂等性——应用一条旧 op 等于什么都没做。任何 `if (op.ver < current.ver) return` 式的特判在"部分字段新、部分字段旧"时都会误判（一个 op 可能只改颜色，版本号却比几何字段低）。

`changed === false` 时仍要记 `seen` 和 `hwm`（这条确实处理过了，下次重传要命中去重），但**不分配 seq、不落盘、不广播**，只回 `shape: current` 让客户端的乐观值自我修正。`seen` 满了删最早插入的：`Map` 保证插入顺序，`keys().next().value` 就是第一个键。

**第 7 步：先落盘再广播**
```js
    const seq = this.serverSeq + 1;
    this.store.append(this.id, { seq, shape: next });
    this.serverSeq = seq;
    this.shapes.set(op.target, next);
    ...
    this.broadcast({ type: MSG.OP, seq, bootEpoch: this.bootEpoch, shape: next, opId: op.opId });
```
顺序是"算 seq → 落盘 → 改内存 → 广播"。反过来会怎样：广播先发，进程在两步之间崩溃，客户端已收到并确认（`lastAppliedSeq` 前进），磁盘上没有。重启后服务端比所有客户端都旧，客户端发来的下一条 op 会被接受，但它本地多出来的图形永远不会被服务端知道。**已确认的写入不能丢。** `this.serverSeq = seq` 放在 append 之后：append 抛异常（磁盘满）时序号不前进，重试拿到的还是同一个 seq，不会出现"序号跳了一个但日志里没有"的空洞。

**广播为什么要包含发起者**：发起者在本地已"乐观应用"过，但算出的值可能和归一化后的不同（坐标被 clamp、小数被取整）。`OP` 广播带的是 `next`（权威全量图形）和 `seq`，发起者收到后覆盖本地、推进 `lastAppliedSeq`。

`ACK` 里虽然也有 `shape` 和 `seq`，但它的语义是"这条从待发队列摘掉"，走单播、可能和广播乱序。若让 ACK 推进 `lastAppliedSeq`，ACK 先到、广播后到时，客户端会认为广播是旧消息而丢弃，别人的修改就丢了。分工是：**广播负责状态，ACK 负责队列**。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `constructor(id, { store, log })` | 参数解构，按名取 | 依赖多，按名传不会错位 |
| `map.values()/keys()` / `[...it]` | 迭代器 / 摊成数组 | 遍历、取最早的键，Map 不能直接序列化 |
| `Math.max/min/round` | 取大小 / 四舍五入 | clamp 到 ±1e6 并取整 |
| `return { ok:false, code }` | 返回结果对象而非抛异常 | 调用方按 code 分类处理 |
| `resync: true` | 结果里带"要重同步"标记 | `index.js` 据此多发一条 RESYNC |

### 写错了会怎样

- **append 挪到 broadcast 之后**：`kill -9` 一下，客户端刷新后少最后几笔，且那条 op 的 `opId` 不在 `seen` 里，重发会被当新 op 接受，但它引用的图形可能已被删，结果是个"幽灵图形"。
- **`seen` 存 `opId → true`**：同 opId 不同内容无法发现，服务端回"重复，跳过"而客户端以为成功。表现是"某个图形怎么改都改不动，刷新一下又好了"。

## server/static.js（只暴露两个目录的静态服务，带路径校验与 ETag）

### 它解决什么问题

浏览器要下载 `index.html`、CSS、几十个 JS 模块，而 `http` 只给一个 `req.url` 字符串，不会帮你找文件、猜 MIME、处理缓存。比"能返回文件"更重要的是**不能返回不该返回的文件**：`req.url` 完全由客户端控制，`GET /client/../../../etc/passwd` 必须被挡住。

### 代码逐段讲

**路径校验**
```js
  let decoded;
  try {
    decoded = decodeURIComponent(urlPath.split('?')[0].split('#')[0]);
  } catch {
    return null; // 非法百分号编码
  }
  if (decoded.includes('\0')) return null;

  const root = resolve(rootDir);
  const target = resolve(join(root, normalize(decoded)));
  if (target !== root && !target.startsWith(root + sep)) return null;
```
**先解码再校验**，顺序反了就是漏洞：`%2e%2e%2f` 未解码时不含 `..`，能过检查；解码后是 `../`，直接穿越。`decodeURIComponent` 遇到 `%zz` 抛 `URIError`，`try/catch` 返回 null。`\0`（空字节）单独挡：某些系统调用在 `\0` 处截断字符串，`a\0.png/../../etc/passwd` 可能骗过检查而底层只看到 `a`。

三步落地：`normalize` 规范化 `a/../b`、`a//b`；`join` + `resolve` 拼成绝对路径并处理掉所有 `..`（此时 `/client/../../etc/passwd` 已变成 `D:\project\Tec\etc\passwd`，跑到 root 外面）；最后用 `startsWith` 检查还在不在 root 里。`root + sep` 里的 `sep` 是系统分隔符。不写 `+ sep` 的话，root 为 `D:\app\client` 时 `D:\app\client-evil\secret` 也满足 `startsWith(root)`，能读兄弟目录。`target !== root` 是例外：请求 `/client/` 时正好等于 root，合法（虽然后面会因不是文件而 404）。

**handler**：`createStaticHandler` 返回的函数遍历 `Object.entries(mounts)`，用 `urlPath.startsWith(prefix)` 匹配前缀，再 `slice(prefix.length)` 去掉前缀交给 `resolveSafe`（`/client/js/main.js` → `js/main.js`）；前缀带斜杠，所以 `/clientX/foo` 不会误匹配。返回 `true` 表示"我处理了"，`false` 表示"不归我管，上层去 404"，`index.js` 就是 `if (serveStatic(req, res)) return;`。非 GET/HEAD 直接回 405，HEAD 的响应头和 GET 一样但不带 body。

**ETag 与 304**
```js
  const etag = `W/"${stat.size.toString(16)}-${Math.floor(stat.mtimeMs).toString(16)}"`;
  if (req.headers['if-none-match'] === etag) {
    res.writeHead(304, { ETag: etag, 'Cache-Control': 'no-cache' });
    res.end();
```
ETag 是"文件内容的指纹"，这里是**弱 ETag**（`W/` 前缀），由"大小 + 修改时间"拼成，都转十六进制省字符。不读内容所以很快，缺点是同毫秒内改出同样大小的文件会撞车（开发时几乎不可能）。浏览器第二次请求带 `if-none-match`，相等就回 `304`、**没有 body**，省掉整个文件传输，对几十个 JS 模块很可观。`Cache-Control: no-cache` 不是"不缓存"，而是"可以缓存但每次用前必须问服务器"（配 ETag 就是一次 304 往返）；真正不缓存是 `no-store`。

**返回文件**：`Content-Type` 由扩展名查表，查不到用 `application/octet-stream`；`X-Content-Type-Options: nosniff` 禁止浏览器猜类型（否则内容像 HTML 的 `.txt` 可能被当 HTML 执行）。用 `createReadStream` + `pipe` 而不是 `readFileSync`：内存占用固定（默认 64KB 一块）；`stream.on('error')` 里 `res.destroy()`，因为文件在 `stat` 之后被删时响应头已发出，没法再回 404。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `return function handle(...)` | 返回闭包 | 把 `mounts` 配置记住 |
| `decodeURIComponent(s)` / `s.includes('\0')` | 百分号解码 / 是否含某子串 | 必须先解码再校验；挡空字节截断 |
| `path.normalize/resolve/join` | 规范化 / 转绝对 / 拼接 | 得到真实磁盘路径 |
| `path.sep` / `s.startsWith(p)` | 分隔符 / 是否以 p 开头 | 拼 `root + sep` 判断"还在目录里" |
| `statSync(p)` / `isFile()` | 同步取元数据 / 是否普通文件 | 只需元数据；目录不能返回 |
| `createReadStream(p).pipe(res)` | 流式读并接到响应 | 自动处理背压，不占内存 |

### 写错了会怎样

- **先检查再解码**：`GET /client/%2e%2e/%2e%2e/server/index.js` 能读到服务端源码，再往上就是整个磁盘。
- **边界写成 `startsWith(root)`**（漏 `+ sep`）：`D:\app\client-backup` 共享前缀，能读到备份目录里的旧代码和 `.env`。

## server/index.js（把 HTTP、WebSocket、限流、超时、端口重试接在一起）

### 它解决什么问题

前面几个文件各管一件事：`static.js` 会回文件但不懂 WebSocket，`ws.js` 会拆帧但不懂房间，`room.js` 会改状态但不知道怎么发。这个文件是装配车间：普通请求交给静态服务，`Upgrade` 交给 WebSocket，再把连接和房间绑起来。它还管三件进程级的事：限制单连接发送频率（防一个客户端刷爆服务端）、清理死连接（防 fd 泄漏）、端口被占用时自动换一个（"上次的进程没关干净"是最常见的启动失败）。

### 代码逐段讲

**一个端口，两种协议**
```js
const server = http.createServer((req, res) => {
  if (serveStatic(req, res)) return;
  res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('Not Found');
});

server.on('upgrade', (req, socket, head) => {
```
`http.createServer` 的回调**只处理普通 HTTP 请求**。带 `Upgrade: websocket` 的请求不进来，而是触发服务器对象的 `'upgrade'` 事件。这是 Node 的设计：HTTP 解析器读到 `Upgrade` 头就知道"接下来这条连接不再是 HTTP"，于是**停止解析**，把裸 socket 和已读到的多余字节（`head`）一起交出来。没人监听 `'upgrade'` 时 Node 默认直接销毁 socket——所以不写这个监听，浏览器握手会立刻断开。同一个端口能同时服务两种协议，因为它们在**同一个 TCP 监听**上，靠请求头区分，不需要开两个端口或加反向代理。不是 `/ws` 就手写 404 并断开（裸 socket，不能用 `res`）；是的话按 `requireMask: true` / `sendMasked: false` 交给 `acceptUpgrade`。

**令牌桶限流**
```js
function takeToken(conn) {
  const now = Date.now();
  const elapsed = Math.max(0, now - conn.bucket.last) / 1000;
  conn.bucket.tokens = Math.min(LIMITS.RATE_BURST, conn.bucket.tokens + elapsed * LIMITS.RATE_PER_SEC);
  conn.bucket.last = now;
  if (conn.bucket.tokens < 1) {
    conn.violations += 1;
    if (conn.violations >= LIMITS.MAX_PROTOCOL_VIOLATIONS) {
      conn.close(CLOSE_CODE.POLICY_VIOLATION, 'rate limit exceeded');
    }
    return false;
  }
  conn.bucket.tokens -= 1;
  return true;
}
```
桶最多装 120 个令牌（`RATE_BURST`），每秒补 60 个（`RATE_PER_SEC`）。`elapsed` 是"距上次取令牌过了几秒"，乘速率就是该补多少；`Math.max(0, ...)` 兜住系统时间被往回调整（负 elapsed 会让令牌倒扣）。`Math.min(RATE_BURST, ...)` 是容量上限：空闲 10 分钟不能攒下几万个令牌一口气发完，否则限流形同虚设。`tokens < 1` 时**不是立刻断开**，只丢这一条、`violations` 加一；连续违规 20 次才用 1008 关闭，这样一次拖拽产生几十条 op 的突发不会误杀。为什么不用"每秒最多 60 条"的固定窗口：固定窗口在边界会有 2 倍突发（第 1 秒最后 10ms 发 60 条 + 第 2 秒最初 10ms 又 60 条），令牌桶是平滑的。

**hello 超时**
```js
  const helloTimer = setTimeout(() => {
    if (!conn.room) conn.close(CLOSE_CODE.POLICY_VIOLATION, 'hello timeout');
  }, CONFIG.helloTimeoutMs);
  helloTimer.unref?.();

  conn.on('close', () => {
    clearTimeout(helloTimer);
    connections.delete(conn);
    if (conn.room) conn.room.leave(conn);
  });
```
握手后 10 秒内必须发 `hello`，否则踢掉——没有它，任何人写脚本连上来不发消息就能白占 socket 和内存。`if (!conn.room)` 是二次确认，定时器触发时可能已正常加入。`'close'` 里清理三样：定时器、全局连接集合、房间成员，漏任何一个都是泄漏。`handleMessage` 里**先扣令牌再 `JSON.parse`**：解析本身也耗 CPU，只在合法消息上扣的话，攻击者可以发垃圾 JSON 免费消耗资源。外层 `setupConnection` 用 `try/catch` 包住它：一个 bug 抛出去就是 `uncaughtException`，能让所有人的白板掉线。

`hello` 里三个 id 都过正则才落地。`roomId` 会被拼进文件名（`store.js` 的 `fileOf`），不校验就是路径穿越；`clientId` 会进 `Map` 的 key 和 `hwm` 拼接，不校验可以塞超长字符串撑爆内存。重复 hello 不报错也不换房间，只回一个 `duplicateHello: true` 的快照，这样网络抖动重发 hello 不会把自己踢出去。

`applyOp` 返回结果对象而不是抛异常，所以 `handleOp` 用 `if (!result.ok)` 分支；`resync: true` 时多发一条 `RESYNC`——`ERROR` 只是"这条失败"，`RESYNC` 是"你整个人都不可信了"，客户端收到后清空本地重走 hello。

**空闲清扫**
```js
const sweeper = setInterval(() => {
  const now = Date.now();
  for (const conn of connections) {
    if (now - conn.lastSeen > CONFIG.idleTimeoutMs) {
      conn.close(CLOSE_CODE.GOING_AWAY, 'idle timeout');
    }
  }
}, 20_000);
```
`lastSeen` 在 `ws.js` 的 `#onData` 里每收到字节就更新。客户端每 15s 发一次应用层 ping，60s 没收到任何帧就判死。扫描间隔 20s 远小于 60s：最坏一个死连接多活 20s，但不用给每个连接起一个定时器。

为什么要主动扫：对端断电、拔网线时 TCP **不会立刻感知**，内核要等重传超时（可能十几分钟），这期间 socket 占着 fd、房间成员表里也留着它，别人看到的光标一直"在线"。

**端口顺延**
```js
export function start(port = CONFIG.port) {
  const strict = process.env.STRICT_PORT === '1';
  const maxTries = strict || port === 0 ? 1 : PORT_FALLBACK_ATTEMPTS;

  return new Promise((resolve, reject) => {
    let candidate = port;
    let tries = 0;

    const onListenError = (err) => {
      tries += 1;
      if (err.code === 'EADDRINUSE' && tries < maxTries) {
        const next = candidate + 1;
        candidate = next;
        server.listen(candidate, CONFIG.host);
        return;
      }
      server.removeListener('error', onListenError);
      err.attempted = { from: port, to: candidate, tries };
      reject(err);
    };
```
`EADDRINUSE` 时**不新建 server 实例**，直接对同一个实例再 `listen` 下一个端口。`listen` 失败后 server 不会停在 listening 态，可以继续重试；新建实例反而泄漏 fd。`maxTries` 为 10，所以最多试 8787~8796；`STRICT_PORT=1` 或 `port === 0` 时只试一次（前者部署要固定端口，顺延会让反向代理失效；后者由系统分配，不存在冲突）。

`once('listening')` 而不是 `on`：成功只该触发一次，重试过程不会重复 resolve。`err.attempted` 给错误对象挂自定义属性，把"从哪试到哪"带给上层拼提示。真实端口用 `server.address().port` 而不是 `candidate`——`port: 0` 时只有它知道。

**是不是被直接运行**
```js
const isMain =
  Boolean(process.argv[1]) && import.meta.url === pathToFileURL(process.argv[1]).href;
```
`process.argv` 是 `[node 路径, 脚本路径, ...]`，所以 `argv[1]` 是被执行的脚本。`import.meta.url` 是**当前模块**的 URL：`node server/index.js` 时两者相等；测试 `import { start } from '../server/index.js'` 时 `argv[1]` 是测试文件，不等。

`pathToFileURL` 不能省：`argv[1]` 是系统路径（`D:\...`），`import.meta.url` 是 URL（`file:///D:/...`），直接比较永远不相等。没有这个判断，测试一 import 就会真去监听端口，跑完进程还不退出。

**优雅关闭**：先 `clearInterval(sweeper)`（否则关闭过程中还会踢连接），再给所有连接发 `1001 Going Away`（客户端据此知道不是自己网络坏了，会重连），最后 `server.close`。外面还套了一个 `setTimeout(resolve, 500)` 兜底：`server.close` 的回调要等所有连接真正断开，有连接卡住进程就永不退出。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `http.createServer(fn)` | 建 HTTP 服务器，`fn` 处理请求 | 一个端口服务所有 HTTP |
| `server.on('upgrade', fn)` | 监听协议升级 | WebSocket 握手入口 |
| `(req, socket, head)` | 请求对象、裸 socket、已读多余字节 | 升级后 HTTP 层不再管连接 |
| `new URL(s, base)` | 解析 URL，相对路径需要 base | 只取 pathname |
| `Math.min/max` | 上下限 | 令牌桶封顶、时间差兜底 |
| `setInterval/setTimeout` | 周期 / 延迟执行 | 空闲清扫、hello 超时 |
| `.unref()` | 定时器不阻止进程退出 | 后台任务不该拖住 exit |
| `new Promise((res, rej) => ...)` | 手动控制异步结果 | `start()` 要知道最终端口 |
| `server.once('listening', fn)` | 只触发一次的监听 | 重试时不重复 resolve |
| `err.code === 'EADDRINUSE'` | 系统错误码 | 区分"端口被占"和其他原因 |
| `process.argv[1]` / `import.meta.url` | 脚本路径 / 模块 URL | 判断是否直接运行 |
| `pathToFileURL(p).href` | 路径转 `file://` URL | 两种表示统一才能比较 |

### 写错了会怎样

- **删掉 `isMain` 判断**：任何 `import` 这个文件的测试都会真去监听端口，跑完进程不退出，CI 卡到最后超时；还会和手动启动的服务抢端口。
- **`EADDRINUSE` 不重试直接 reject**："上次进程还在后台"就变成启动失败，用户得自己去 `Get-NetTCPConnection` 找 PID。
- **令牌桶去掉 `Math.min`**：断网 10 分钟再重连，桶里攒了几万令牌，重连瞬间把几千条离线 op 一次打进来，服务端几十毫秒内做几千次同步磁盘写，所有连接一起卡住。
