# 03 客户端：画布与交互
本篇只讲「看得见、点得着」的一层，数据合并、撤销栈、重连策略在别的篇目。

一条数据流：`鼠标事件 → tools.js 换算坐标 → store 改数据 → canvas.js 重画`，同时 `store → net 发出去 → 别人收到 → 别人的 store 改数据 → 别人的 canvas 重画`。

## client/index.html（页面骨架，所有 JS 靠 id 在这里抓节点）
### 它解决什么问题
这个项目没有 React/Vue，页面上每个按钮、输入框都是手写的。JS 不创建布局，只负责「找到已经存在的元素，挂上事件」。

所以这个文件的职责很单纯：把所有需要被 JS 操作的节点提前声明出来，并给一个稳定的 id。`ui.js` 里那张 `el` 字典、`main.js` 里几行 `getElementById`，能工作完全依赖这里 id 拼写正确。

### 代码逐段讲
**脚本加载**
```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1" />
<title>协作白板 · 支持离线与多人实时同步</title>
<meta name="description" content="支持多人在线实时协作、断网离线编辑与自动重连合并的白板" />
<link rel="stylesheet" href="/client/css/style.css" />
```

末尾再用 `<script type="module" src="/client/js/main.js"></script>` 引入入口。
`viewport` 让手机按设备宽度布局、禁掉页面双指缩放（双指要留给画布）；路径用 `/client/...` 绝对路径，因为服务端把项目根目录当静态根。

`type="module"` 有两个副作用：按 ES Module 规则解析 `import`；**默认延迟执行**（等价 `defer`），一定在 DOM 解析完之后才跑。这就是 `main.js` 里可以直接 `getElementById('board')` 而不用包 `DOMContentLoaded` 的原因。

**画布四层**
```html
<canvas id="board"></canvas>
<div class="presence-layer" id="presence-layer" aria-hidden="true"></div>
<div class="text-editor-wrap" id="text-editor-wrap" hidden>
  <textarea id="text-editor" rows="1" spellcheck="false" placeholder="输入文本…"></textarea>
</div>
```
顺序就是层叠顺序：`#board` 画所有图形（`main.js:58` 抓它传给 `Board` 和 `Interactions`）；`#presence-layer` 是别人光标层（`main.js:61` 传给 `Presence`）；`#text-editor-wrap` 是文本浮层，默认带 `hidden`（等价 `display:none`），双击文本时 `tools.js` 把它 `hidden = false` 并定位到图形上。

第三层是 `<textarea>` 而不是 `contenteditable` 的 div：两者的输入法、选中、方向键都由浏览器负责，但 textarea 的 `value` 就是普通字符串，`tools.js` 里 `value.replace(/\r/g, '')` 一行拿到纯文本；contenteditable 得递归读子节点，还得防用户粘进来一堆 `<span>`。

**工具栏与各处 id**
```html
<div class="room-bar">
  <label for="room-input">房间</label>
  <input id="room-input" type="text" spellcheck="false" maxlength="64" autocomplete="off" />
  <button id="copy-link" class="ghost-btn" title="复制当前房间链接">复制链接</button>
</div>
```
工具按钮那边则是 `<button class="tool is-active" data-tool="select" ...>` 这样的写法：没有各自 id，只有 `data-tool`。`ui.js` 用事件委托：点工具栏任意位置，向上找最近的 `[data-tool]`，读 `dataset.tool` 交给 `interactions.setTool()`，加第五个工具不用改 JS。

`#room-input` 被 `main.js` 填房间名、被 `ui.js` 监听回车切房间；`#members` 是空容器，`ui.setMembers()` 往里塞头像；`#status` 的 `data-state="connecting"` 是初值，之后 `setState()` 只改这个属性，颜色全由 CSS 决定。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `id="board"` | 全文档唯一标识，`getElementById` 靠它找节点 | JS 抓节点的唯一约定，拼错就 null |
| `class="tool is-active"` | 一个元素多个 class，空格分隔 | `tool` 管基础样式，`is-active` 管选中态 |
| `data-tool="rect"` | 自定义数据属性，`el.dataset.tool` 读出来是字符串 | 四个按钮共用一套委托逻辑 |
| `data-state="connecting"` | 同上，但纯粹给 CSS 用 | CSS 用 `[data-state="online"]` 选它 |
| `hidden` | HTML 布尔属性，等价 `display:none` | 浮层和调试面板默认隐藏 |
| `type="module"` | 按 ES Module 解析，且默认 defer | 让 `import` 生效，同时保证 DOM 就绪 |
| `<label for="x">` | 点标签等于点 `id="x"` 的控件 | 无障碍 + 大点击区域，零 JS |
| 内联 `<svg>` + `currentColor` | 矢量图标，颜色跟随父元素文字色 | 不引图标库，改 `color` 就换色 |

### 写错了会怎样
- **`id="board"` 写成 `id="Board"`**。`main.js:58` 拿到 `null`，`new Board(null, ...)` 第一句 `canvas.getContext` 抛 `TypeError`，整页白屏，控制台只有一行报错，看不出是 id 写错。
- **`#text-editor-wrap` 漏掉 `hidden`**。页面一打开画布左上角就浮着虚线空输入框，用户以为白板坏了。
- **`<script>` 挪进 `<head>` 并去掉 `type="module"`**。脚本在 DOM 解析前执行，`getElementById` 全是 null，直接崩。

## client/css/style.css（布局与视觉状态，画布能撑满靠它）
### 它解决什么问题
HTML 只是把元素按顺序排下来，真正决定「工具栏在左、画布居中、面板在右」的是 CSS。canvas 尤其特殊：它是替换元素，**没有 CSS 给宽高时，显示尺寸就是属性宽高（默认 300×150）**。另一个职责是状态可视化：连接状态、工具选中态，JS 只改一个 class 或 `data-*`。

### 代码逐段讲
**设计变量**
```css
  --brand: #2563eb;
  --brand-soft: #dbeafe;
  --ok: #16a34a;
  --warn: #f59e0b;
  --danger: #dc2626;
```
`--brand` 这种双横线写法是 CSS 自定义属性（CSS 变量），它们都写在 `:root { ... }` 里，也就是 `<html>` 上，所以全文档可用，用的时候写 `var(--brand)`。主色在这个文件里出现十几次（按钮背景、选中框、阴影的 rgba），硬编码换配色要改十几处、容易漏，用变量只改一行。

**高度链与主区域**

主区域用 `.stage { position: absolute; inset: 56px 0 0 0; display: flex; }` 钉在顶栏下面。百分比高度要求父元素有确定高度，所以要从 `html` 一路传到 `body`。少了 `html` 那条，`body` 的 100% 退化成内容高度，画布撑不满；`body` 上的 `overflow: hidden` 则禁止整页滚动，否则页面滚动会和白板平移打架。

`inset` 是 `top/right/bottom/left` 的简写，上边空 56px（顶栏高度）、其余贴边，省掉 `calc(100vh - 56px)`；`display: flex` 让三个子元素横排——`.toolbar` 固定 56px、`.canvas-wrap` 用 `flex: 1` 吃满剩余、`.inspector` 固定 216px。

**画布容器与 canvas**
```css
#board {
  display: block;
  width: 100%;
  height: 100%;
  touch-action: none;
  cursor: default;
}
```
容器 `.canvas-wrap` 上的 `position: relative` 是关键：它让内部的 `#presence-layer`、`.text-editor-wrap` 这些 `position: absolute` 元素**以它为参照**。没有这行，别人光标会跑到页面左上角。

`min-width: 0` 是 flex 的经典坑：子项默认 `min-width: auto`（不小于内容宽度），canvas 的内容宽度可能是它上次的像素宽度，结果窗口缩小时画布不缩、反而撑破布局。

`#board` 三件事：`display: block` 消除 inline 元素底部的基线空隙（约 4px 白边）；`width/height: 100%` 让**显示尺寸**跟随容器（这只是 CSS 尺寸，绘图缓冲区由 `canvas.js` 里的 `canvas.width` 控制）；`touch-action: none` 告诉浏览器这块区域的手势自己处理，否则手机上拖动会变成页面滚动，`pointermove` 被抢走。

**光标层与状态条**
```css
.presence-layer {
  position: absolute;
  inset: 0;
  pointer-events: none;
  overflow: hidden;
}
```
`pointer-events: none` 是光标层能存在的前提：它盖在 canvas 上，若接收鼠标事件，用户永远点不到画布；设成 none 后事件「穿透」到下层。而 `.remote-cursor { position: absolute; will-change: transform; transition: transform 0.08s linear; }` 靠 `transform` 移动——transform 不触发重排，只走合成层，几十个光标同时动也不卡。

状态条同理：`.status[data-state="online"]` 配绿色、`.status[data-state="syncing"] .dot` 配呼吸动画。`ui.setState()` 只做 `el.dataset.state = state`，JS 里没有一行 `style.background`。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `:root { --brand: ... }` | 在根元素上定义自定义属性 | 全文档可用，改一处全站生效 |
| `var(--brand)` | 读取变量，可带兜底 `var(--x, red)` | 同一个颜色不散落十几处 |
| `inset: 56px 0 0 0` | `top/right/bottom/left` 简写 | 比写四个属性短 |
| `position: relative` | 自身在普通流，同时成为子元素绝对定位的参照 | 浮层和光标层以画布为坐标系 |
| `flex: 1` | `grow:1; shrink:1; basis:0%` | 画布吃掉左右固定宽度之外的空间 |
| `min-width: 0` | 覆盖 flex 子项默认的 `min-width:auto` | 不加则缩窗口时撑破布局 |
| `display: block`（canvas） | 变成块级元素 | 消除行内元素底部空隙 |
| `pointer-events: none` | 不接收鼠标事件，穿透到下层 | 光标层盖着却不挡点击 |
| `[data-state="online"]` | 属性选择器 | JS 只改数据属性，样式在 CSS |
| `#board.tool-rect` | 复合选择器：id 且 class 同时满足 | 工具名与光标样式的映射 |

### 写错了会怎样
- **`#board` 少了 `width/height: 100%`**。canvas 退回默认 300×150 显示尺寸，而 `canvas.js` 的 `resize()` 会按容器去设 `style.width`，两边打架，表现为「只有左上角一小块能画」。
- **`.presence-layer` 少了 `pointer-events: none`**。别人一进房间，你就再也点不中画布上任何图形——一个铺满的透明 div 挡在最上面，页面上什么都看不见，极难自查。
- **`.canvas-wrap` 少了 `position: relative`**。文本浮层的 `left/top` 相对整个页面算，双击文本时输入框出现在页面左上角。

## client/js/canvas.js（把数据画成像素，并把像素点翻译回数据）
### 它解决什么问题
这个文件是「数据 → 图像」和「鼠标位置 → 图形」两个方向的翻译官。

方向一：store 里存的是 `{ id, type, x, y, w, h, fill }` 这样的纯数据，得用 Canvas 2D 一笔笔画出来，而且**每次数据变化都要整屏重画**——canvas 是一块位图，没有「局部更新」这回事。方向二：用户点了一下屏幕，你拿到的是「屏幕上第 512 个像素」，但图形位置存在「世界坐标」里，当前缩放 200% 时屏幕 512 对应世界 256，直接拿 512 去做命中测试就会点偏。

### 代码逐段讲
**尺寸适配，高分屏不糊的关键**
```js
const rect = host.getBoundingClientRect();
this.dpr = Math.min(window.devicePixelRatio || 1, 2);
this.width = Math.max(1, Math.floor(rect.width));
this.height = Math.max(1, Math.floor(rect.height));
this.canvas.width = Math.floor(this.width * this.dpr);
this.canvas.height = Math.floor(this.height * this.dpr);
this.canvas.style.width = `${this.width}px`;
this.canvas.style.height = `${this.height}px`;
```
`getBoundingClientRect()` 拿到元素的实际显示尺寸（CSS 像素）。`devicePixelRatio` 是「一个 CSS 像素对应几个物理像素」：普通屏 1，Retina 2 或 3。

关键在两组赋值，它们是**两套完全不同的东西**：`canvas.width/height` 决定绘图缓冲区有多少像素点（物理像素，决定清晰度），`canvas.style.width/height` 决定元素在页面上占多大（CSS 像素）。

只设 style 不设 width：缓冲区还是默认 300×150，被拉伸到 1200×800 显示，等于把小图放大 4 倍，线条糊、锯齿明显。只设 width 不设 style：缓冲区 2400×1600，元素也显示成 2400×1600，撑爆布局。两个都设且 `width = 显示宽度 × dpr`，就得到「缓冲区物理像素数 = 屏幕物理像素数」，一个绘图单位正好落在一个物理像素上。

`Math.min(dpr, 2)` 是性能上限：4K 屏 dpr 可能 3，缓冲区面积 9 倍，重绘开销翻 9 倍，收益几乎看不出。`Math.max(1, ...)` 防止容器还没布局完时宽高为 0——`canvas.width = 0` 会让后续所有绘制静默失效。尺寸变化同时监听 `window.resize` 和 `ResizeObserver`：前者只管窗口，后者管容器（面板隐藏、工具栏换行也会变）。

**两套坐标互转**
```js
screenToWorld(pt) {
  return {
    x: (pt.x - this.viewport.x) / this.viewport.scale,
    y: (pt.y - this.viewport.y) / this.viewport.scale,
  };
}

worldToScreen(pt) {
  return {
    x: pt.x * this.viewport.scale + this.viewport.x,
    y: pt.y * this.viewport.scale + this.viewport.y,
  };
}
```
`this.viewport = { x, y, scale }` 是坐标系中心：`x/y` 是世界原点在屏幕上的位置（平移量），`scale` 是缩放倍数。

`worldToScreen` 是「世界 → 屏幕」：先乘缩放再加平移。`screenToWorld` 是逆运算：先减平移再除缩放。**顺序不能反**，因为变换的应用顺序是「先缩放后平移」，逆运算必须倒过来。

为什么必须转？假设世界 (100,100) 有个矩形，缩放 200%、平移 (50,0)，它画在屏幕 (250,200)。用户点 (250,200)，不转换就直接拿 250 和矩形的 100 比，判定「没点中」；转换后 `(250-50)/2 = 100` 才对得上。`eventPoint(ev)` 则先把 `clientX/clientY` 减掉 canvas 左上角偏移——画布有 12px 边距、上面还有 56px 顶栏，不减所有点击都会偏。

**以光标为中心缩放（`zoomAt`）**
```js
const next = Math.min(MAX_SCALE, Math.max(MIN_SCALE, this.viewport.scale * factor));
if (next === this.viewport.scale) return;
const world = this.screenToWorld(screenPt);
this.viewport.scale = next;
this.viewport.x = screenPt.x - world.x * next;
this.viewport.y = screenPt.y - world.y * next;
```
`zoomAt(screenPt, factor)` 是滚轮缩放调用的方法，最反直觉的地方是：用户希望「光标指着哪个点，哪个点就不动」。只改 scale 的话画布以左上角为原点缩放，光标下的内容会往边上跑。所以分三步：**先算**——用旧 scale 把光标转成世界坐标 `world`，这是用户正指着的内容；**改**——更新 scale；**反推**——既然 `screen = world * scale + viewport`，那 `viewport = screen - world * scale`。把新 scale 代进去，viewport 就自动调整成「让这个世界点仍落在同一个屏幕位置」。

**命中测试（`hitTest`）**
```js
const tolerance = 3 / this.viewport.scale;
for (let i = shapes.length - 1; i >= 0; i -= 1) {
  const flat = this.viewOf(shapes[i]);
  if (flat.deleted) continue;
  if (flat.type === 'ellipse') {
    const cx = flat.x + flat.w / 2;
    const cy = flat.y + flat.h / 2;
    const rx = flat.w / 2 + tolerance;
    const ry = flat.h / 2 + tolerance;
    if (rx <= 0 || ry <= 0) continue;
    const dx = (worldPt.x - cx) / rx;
    const dy = (worldPt.y - cy) / ry;
    if (dx * dx + dy * dy <= 1) return shapes[i].id;
```
**倒序遍历**（`i = length - 1; i >= 0`）。`shapes` 的顺序就是绘制顺序，下标越大越晚画、越在上层。用户看到的是「上层压住下层」，点击时也该先问上层。正序遍历的话，点在两个重叠矩形的交界处会选中底下那个——视觉和操作不一致。

**`tolerance = 3 / this.viewport.scale`**。3 是「屏幕上 3px」的容差，让细线、小图形也好点。但命中测试用世界坐标：缩放到 400% 时屏幕上 3px 只对应世界 0.75，若容差固定写 3，判定区会变成屏幕上 12px 宽，点旁边空白也会选中；缩到 20% 时又只剩 0.6px，边框根本点不中。除以 scale 就是把「屏幕容差」换算成「当前缩放下的世界容差」，无论怎么缩放，判定区在屏幕上始终 3px。

**椭圆用归一化判断**。数学上判断点在椭圆内是 `(x-cx)²/rx² + (y-cy)²/ry² <= 1`。代码先算 `dx = (worldPt.x - cx) / rx`，相当于把椭圆拉伸成单位圆，然后 `dx*dx + dy*dy <= 1` 就是「到圆心的距离平方 ≤ 半径平方」。

为什么不写 `Math.sqrt(dx*dx+dy*dy) <= 1`？开方单调，两边平方不改变大小关系，省一次 `Math.sqrt`。更实际的理由是：矩形和椭圆用了同一种形式（都是平方和），读代码不用切换思维；而且这里本来就不能用勾股定理算欧氏距离再跟半径比——椭圆有两个半径，跟哪个比都是错的，必须先把 x、y 分别按 rx、ry 归一化。

**预览叠加与渲染节流**

store 里的图形是 CRDT 结构，字段存在 `shape.fields` 里带版本戳，不能直接读 `shape.x`，`viewOf()` 先用 `flatten()` 摊平成普通对象，再把 `tools.js` 存在 Map 里的 preview 补丁 `Object.assign` 上去。这样画布画的是最新视觉状态，而 store 里的数据还是旧的——零延迟手感的来源就在这。

```js
render() {
  if (this._raf) return;
  this._raf = requestAnimationFrame(() => {
    this._raf = null;
    this._draw();
  });
}
```
`if (this._raf) return;` 是整个节流的核心。一次拖动里 `render()` 会被调几百次（每个 `pointermove` 一次）。如果每次都 `requestAnimationFrame`，会排队几百个回调，浏览器一帧里全跑完，等于把同一份数据画几百遍。

这行的意思是「已经有一个待执行的重绘了，别再排」。第一次调用 `_raf` 是 null，排进去；后续发现 `_raf` 有值，直接返回。等下一帧回调执行，`_raf` 先清成 null，再真正画。

关键点：**被跳过的那几百次并不会丢数据**。`_draw()` 读的是 `getShapes()` 的当前值，不是排队时的快照。不管合并了多少次，画出来的永远是最新状态。这叫「合并请求」，不是「丢请求」。

**每帧重置变换**
```js
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
ctx.clearRect(0, 0, w, h);
```
`setTransform(dpr, 0, 0, dpr, 0, 0)` 设置的是**基础变换矩阵**：把绘图坐标整体放大 dpr 倍。参数 `(a,b,c,d,e,f)` 对应矩阵 `[a c e; b d f]`，这里就是「x 方向 ×dpr，y 方向 ×dpr，不平移」。之后所有绘制都按 CSS 像素写，浏览器自动映射到物理像素。

为什么要每帧开头重设？canvas 的变换是**累积**的，`translate/scale/rotate` 都往当前矩阵上叠。虽然 `save/restore` 能配对还原，但只要有一处没配上（比如某个异常路径提前 return），变换就会一直叠下去，下一帧画的东西越来越偏、越来越小。每帧强制 `setTransform` 到已知状态，等于给每帧一个干净起点，把这类 bug 变成不可能。`clearRect` 里的 `w/h` 是 CSS 像素，因为此时变换已带 dpr，实际清掉的是 `w*dpr × h*dpr` 个物理像素。

**save / restore 在保存什么**
```js
ctx.save();
ctx.translate(this.viewport.x, this.viewport.y);
ctx.scale(this.viewport.scale, this.viewport.scale);

for (const shape of this.getShapes()) {
  this._drawShape(this.viewOf(shape));
}

const draft = this.getDraft();
if (draft) this._drawShape({ ...draft, fill: draft.fill || 'rgba(37,99,235,0.08)', stroke: '#2563eb' });

ctx.restore();
```
`ctx.save()` 保存的是**整个绘图状态**：当前变换矩阵、`fillStyle`、`strokeStyle`、`lineWidth`、`font`、`textAlign`、虚线设置、裁剪区域，全部压进一个栈；`ctx.restore()` 把它们全弹回来。

所以这段的意思是：「接下来我在『世界坐标系』里画所有图形，画完请把坐标系和所有样式恢复原样」。之后 `_drawSelection()` 用的是屏幕坐标，两者互不干扰。没有这一对，`translate/scale` 会一直留在上下文里，选中框坐标被二次变换，位置完全错乱。

**网格、图形与选中框**

网格在**屏幕坐标**里画（没有 save/scale），所以点距要先乘 scale；`step < 9` 时直接不画，否则缩小时点会密到糊成一片灰。偏移量用 `((a % b) + b) % b`：JS 的 `%` 对负数返回负数，`-5 % 24` 是 `-5`，直接当起点会画到屏幕外，加 b 再取模才能绕回正区间。

图形按 `flat.type` 分支：矩形走 `_roundRect` + `_fillAndStroke`，椭圆走 `ctx.ellipse(cx, cy, w/2, h/2, 0, 0, Math.PI * 2)`，文本用 `fillText` 逐行画（canvas 没有多行 API），按 `\n` 切开；`textBaseline = 'top'` 让 `y` 表示文字顶部而非基线，否则文本 y 会和矩形 y 差一个字体高度，选中框对不上。

```js
const a = this.worldToScreen({ x: flat.x, y: flat.y });
const b = this.worldToScreen({ x: flat.x + flat.w, y: flat.y + flat.h });
ctx.strokeRect(Math.round(a.x) + 0.5, Math.round(a.y) + 0.5, Math.round(b.x - a.x), Math.round(b.y - a.y));
```
选中框是在 `ctx.restore()` **之后**画的，此时变换已回到屏幕坐标，所以先 `worldToScreen` 手动转换。好处是 `lineWidth = 1` 就是屏幕上的 1px，不随缩放变粗；放在世界坐标里画的话，缩放 400% 时选中框会变成 4px 粗线。

`Math.round(a.x) + 0.5` 是画 1px 线的经典技巧。canvas 的坐标 (10,10) 指的是**像素边界**（左上角那个角点）。一条 1px 宽的线从 10 画到 11，正好跨在两个像素中间，各占 0.5，抗锯齿把它渲染成两条 50% 灰度的线——看起来发虚、变粗。把坐标挪到 10.5，线中心正好落在像素 10 的正中间，1px 覆盖 10 到 11，实心锐利。宽高不需要 +0.5，只有起点要对齐到像素中心。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `class Board { }` / `new Board()` | 类与实例，状态挂在实例上 | 一个画布一个实例，viewport 不能全局 |
| `constructor(a, { b, c })` | 参数解构，直接从对象取字段 | 五个回调不用按顺序传 |
| `x \|\| (() => null)` | 逻辑或兜底 | 可选回调给安全默认值 |
| `() => {}` | 箭头函数，`this` 沿用外层 | 事件回调里要访问 `this.resize()` |
| `get zoomText()` | getter，读属性时自动调函数 | `board.zoomText` 比 `getZoomText()` 简洁 |
| `this._ro?.disconnect()` | 可选链，左边为空就不往下执行 | 老浏览器没有 ResizeObserver |
| `[...selection]` | 展开可迭代对象成数组 | Set 不能用下标 |
| `{ ...draft, fill: x }` | 对象展开，浅拷贝并覆盖字段 | 造新草稿对象，不改原对象 |
| `new Set()` / `new Map()` | 集合 / 键值表 | 选中 id 去重、预览按 id 存 |
| 倒序 `for` 循环 | 从后往前遍历 | 命中测试从最上层往下找 |
| `ctx.save()/restore()` | 压栈/出栈整个绘图状态 | 世界坐标和屏幕坐标隔离 |
| `ctx.setTransform(a,b,c,d,e,f)` | 直接设置变换矩阵（非叠加） | 每帧重置 dpr，防累积 |

### 写错了会怎样
- **`resize()` 里只设 `canvas.style.width` 不设 `canvas.width`**。缓冲区停在 300×150 被拉伸到整块画布，所有线条毛边、文字糊、网格变灰雾。逻辑完全正确，只是「画质差」，极难定位。
- **`hitTest` 改成从 0 正序遍历**。两个矩形重叠时，点上层矩形会选中下层那个，选中框出现在「不是你想选的那个」上面。
- **`tolerance` 写成固定 `3`**。缩放到 400% 后判定区变成屏幕上 12px，点旁边空白也会选中；缩到 20% 时只剩 0.6px，细边框根本点不中。

## client/js/tools.js（把鼠标动作翻译成「画一个矩形」）
### 它解决什么问题
`canvas.js` 只会画，不会理解。用户按下鼠标往右下拖，这串 `pointerdown → pointermove × N → pointerup` 本身没有含义，是 `tools.js` 把它解释成「正在画一个矩形，从 (100,100) 拖到 (300,250)」。

它要处理四类交互，且共用同一套指针事件：选择（点中、拖走、拉手柄、框选）、矩形/椭圆（拖出新图形）、文本（点一下弹输入框）、任何工具下的空格/中键平移和滚轮缩放。所以用**状态机**：一个 `this.drag` 对象记住「当前在干什么」，move/up 只看它的 `mode` 分支。它还要解决一个矛盾：拖动要**零延迟**，网络**扛不住**几百条 op，解法是「预览 + 节流提交」。

### 代码逐段讲
**状态字段**
```js
this.tool = 'select';
this.selection = new Set();
this.preview = new Map(); // shapeId → patch（拖动预览）
this.draft = null; // 正在绘制的新图形
this.marquee = null;
this.drag = null;
this.spaceDown = false;
```
`tool` 是当前工具名，`setTool()` 是唯一修改入口；`selection` 是选中的 id 集合；`preview` 是拖动中的临时几何，**还没进 store**；`draft` 是正在拖出来的新图形，松手才真正创建；`drag` 是状态机核心，`null` 表示没在拖；`spaceDown` 表示空格按住，此时左键也当平移。

构造函数里还有 `this._measureCtx = document.createElement('canvas').getContext('2d')`——一个离屏 canvas，从不显示，只用它的 `measureText()` 算文字宽度（`measureText` 需要上下文，所以得先造一个）。

**指针事件**
```js
el.addEventListener('pointerdown', (e) => this._onPointerDown(e));
el.addEventListener('pointermove', (e) => this._onPointerMove(e));
el.addEventListener('pointerup', (e) => this._onPointerUp(e));
el.addEventListener('pointercancel', (e) => this._onPointerUp(e));
```
另外还绑了 `dblclick`、`wheel`（带 `{ passive: false }`）和 `contextmenu`（直接 `preventDefault()`）。用 `pointerdown/move/up` 而不是 `mousedown/mousemove/mouseup`，是因为 Pointer Events 把鼠标、触摸、触控笔统一成一套事件。手机上手指按下也触发 `pointerdown`，代码一行都不用改；用鼠标事件的话触摸屏完全没反应。`pointercancel` 也绑到 `_onPointerUp`：浏览器中途取消手势（来电、系统手势）时必须把状态收干净，否则 `drag` 永远不为 null，后续操作全卡住。

`{ passive: false }` 是必须的。浏览器默认把 `wheel` 当被动监听器（为了滚动性能，回调里不许 `preventDefault`），不加这个参数 `preventDefault()` 会失效并打印警告，结果是滚轮既缩放又滚动页面。

**输入框与全局快捷键的隔离**
```js
this.editor.addEventListener('keydown', (e) => {
  if (e.key === 'Escape') {
    e.preventDefault();
    this._closeTextEditor(true);
  } else if (e.key === 'Enter' && !e.shiftKey) {
    e.preventDefault();
    this._commitText();
  }
  e.stopPropagation();
});
```
`e.stopPropagation()` 放在 if 外面，不管按什么都阻止冒泡到 `window`——因为 `window` 上挂着全局快捷键，在输入框里打字母 `r` 不阻止冒泡就会切到矩形工具，正打着字工具就变了。全局那边还有第二道闸：`_onKeyDown` 开头 `const typing = target && (target.tagName === 'INPUT' || target.tagName === 'TEXTAREA' || target.isContentEditable);`，为真就直接 return。没有这行，在房间号输入框里打 `r`、`v`、`t` 会不停切工具。

**按下：状态机入口**
```js
try {
  this.canvasEl.setPointerCapture(e.pointerId);
} catch {
  // 合成事件（自动化测试）没有活跃指针，捕获失败不影响后续逻辑
}
const sp = this.board.eventPoint(e);
const wp = this.board.screenToWorld(sp);

if (e.button === 1 || this.spaceDown) {
  e.preventDefault();
  this.drag = { mode: 'pan', last: sp };
```
`setPointerCapture` 让后续的 `pointermove/pointerup` 全发给这个 canvas，**即使鼠标已移出画布**。没有它，用户从画布拖到工具栏再松手，`pointerup` 发给工具栏，画布永远收不到，`drag` 卡住不释放。空 `catch` 是因为自动化测试里的合成事件没有真实指针，`setPointerCapture` 会抛 `NotFoundError`。

`sp` 是屏幕坐标，`wp` 是世界坐标，**两个都要留**：平移用 `sp`（平移量是屏幕像素，与缩放无关），画图形用 `wp`（图形存在世界坐标里）。`e.button === 1` 是中键，`spaceDown` 是空格按住，两者都进平移分支并 return。

**选择工具的判定顺序**
```js
const handle = this.board.handleAt(sp);
if (handle) {
  this._startResize(handle, wp);
  return;
}
const hit = this.board.hitTest(wp);
if (hit) {
  if (e.shiftKey) {
    if (this.selection.has(hit)) this.selection.delete(hit);
    else this.selection.add(hit);
  } else if (!this.selection.has(hit)) {
    this.selection = new Set([hit]);
  }
```
**先问手柄，再问图形，最后才是空白**。手柄画在图形边缘上，若先 `hitTest`，用户想拉手柄改尺寸，结果变成拖动整个图形——手柄永远点不中。

`handleAt(sp)` 传屏幕坐标，`hitTest(wp)` 传世界坐标。看起来不一致，其实是有意的：手柄是固定 8px 的视觉元素，判定按屏幕像素算（缩放后手柄在屏幕上大小不变）；图形大小是世界坐标里的，判定必须按世界坐标算。

`else if (!this.selection.has(hit))` 这个条件：点中的图形**已在**选中集合里时，不加 shift 也不重置选择——为了支持「多选后拖动整体」。无条件 `new Set([hit])` 的话多选永远拖不动。

**移动与节流提交**
```js
const dx = wp.x - this.drag.start.x;
const dy = wp.y - this.drag.start.y;
if (Math.abs(dx) < 0.2 && Math.abs(dy) < 0.2 && !this.drag.moved) return;
this.drag.moved = true;
this.preview.clear();
for (const [id, origin] of this.drag.origins) {
  this.preview.set(id, { x: Math.round(origin.x + dx), y: Math.round(origin.y + dy) });
}
this.board.render();
this._throttleCommit();
```
`dx/dy` 是「相对按下时的总位移」，每次从 `origin` 加总位移，而不是累加，这样即使中间有取整误差也不会越拖越偏。`Math.abs(dx) < 0.2` 是死区，鼠标微抖不算拖动，配合 `!this.drag.moved` 保证「只点一下没拖」不产生任何 op。`this.preview.clear()` 后重填，因为 preview 是「当前帧的临时状态」，每次整体重算。

平移用**增量**（当前位置 - 上次位置），不用「当前位置 - 按下位置」，因为改 viewport 会影响坐标转换，用绝对偏移容易算错。悬停时（`!this.drag`）只更新光标形状：有手柄用 `CURSORS` 表里的箭头，命中图形用 `move`，否则 `default`。

`_throttleCommit()` 里是 `const now = performance.now(); if (now - this._lastCommit < COMMIT_INTERVAL) return;`，`COMMIT_INTERVAL = 60`，即最快 16 次/秒。所以拖动过程中**画布每帧都在重画（走 preview，零延迟），但 store 每 60ms 才更新一次**——这就是「手感 vs 网络流量」的平衡：60ms 内的位移用户感觉不到，op 数量从「每秒几百条」降到「每秒 16 条」。提交时调的是 `applyLocal(id, patch, { record: false })`。

**松手：补提交与合并撤销**
```js
const drag = this.drag;
this.drag = null;
const patches = new Map(this.preview);
this.preview.clear();
this._commitPatches(patches);

if (drag.moved && drag.originsFlat) {
```
上面这段之后是拼 `items`（每个图形的 forward/backward 补丁）并调 `this.store.recordUndo({ label: mode === 'resize' ? '缩放' : '移动', items })`。

**为什么松手要补一次提交**：`_throttleCommit` 有 60ms 时间窗，用户可能在最后一次移动后 10ms 就松手了，那次移动没赶上提交窗口，只存在于 preview 里。不补这一下，preview 被清空，图形会「弹回」到 60ms 前的位置。

**为什么撤销要在这里合并成一条**：拖动过程中用的是 `{ record: false }`，表示「改数据、发 op，但不往撤销栈里塞记录」。不这样的话，一次拖动产生 10 条中间 op，撤销栈就有 10 条，用户按一次 Ctrl+Z 只退回一小段，得按 10 次才回原位。

所以拖动期间一律不记撤销，松手时算一条「原始位置 → 最终位置」的完整记录：`backward` 是按下时的 `drag.originsFlat[id]`，`forward` 是现在的 `flat`。按一次 Ctrl+Z 整段位移一起回退。中间那个 `if (fwd[key] !== back[key]) changed = true` 过滤「点了但没动」，避免撤销栈塞空记录。

**创建图形与文本浮层**

`_onPointerUp` 的 create 分支里，`MIN_DRAG = 3`：宽或高小于 3 世界单位判定为「单击而非拖动」，此时用默认尺寸 160×110，并以点击点为中心（`x - w/2`），因为用户点那一下应该是图形中心。创建完还会 `setTool('select')`，画完自动切回选择工具。

**为什么用 DOM 浮层而不是在 canvas 里画光标**：在 canvas 里自己画闪烁竖线、处理输入法候选框、选中高亮、方向键、复制粘贴，等于重新实现一个文本编辑器，工作量巨大且永远有 bug（尤其中文输入法的候选词定位）。用原生 textarea，这些浏览器全帮你做了，代码只需把框摆到正确位置、字号跟着缩放（`fontSize * scale`），所见即所得。

`requestAnimationFrame(() => this.editor.focus())`：刚把 `hidden` 设成 false，元素这一刻可能还没完成布局，同步调 `focus()` 在某些浏览器上会失败，等下一帧才可靠。

`_commitText` 开头是 `const state = this._editorState; if (!state) return;`——防重入的关键。`_closeTextEditor` 里把 `_editorState` 置 null 并隐藏浮层，隐藏会让 textarea 失焦、触发 `blur`、又调 `_commitText`，第二次进来时 `state` 已是 null，直接返回，不会重复创建图形。

滚轮缩放用 `const factor = Math.exp(-e.deltaY * 0.0016)`。用指数而不是线性加减：滚一格放大 1.18 倍，往回滚一格就是 `1/1.18`，**严格对称**，来回滚不会漂移；线性加减（`scale += 0.1`）会让「放大再缩小」回不到原位。

**画笔：为什么存点，而不是存一条 SVG 路径**

画笔图形在协议里多了一个 `pts` 字段——把采样点按 `[x0, y0, x1, y1, …]` 平铺成一维数组，而不是存 `M10 20 Q…` 这样的路径字符串。原因有三个：

1. **缩放要能跟着走**。图形的 `w/h` 是包围盒，选中后拖把手改的是 `w/h`。存点的话，渲染时按 `x + (px - minX) * (w / origW)` 换算即可，笔迹会自然拉伸；存路径字符串就得解析、变换、再序列化，还得处理精度损失。
2. **归一化要能校验**。`shared/protocol.js` 里对 `pts` 逐个 clamp 到坐标范围并取整，和矩形、椭圆走同一套白名单。字符串没法这么校验。
3. **合并要能比较**。字段级 LWW 比较的是「值是否相等」，数组可以直接比，路径字符串的等价形式太多（`M0 0L1 1` 和 `M0,0 L1,1` 是同一条线但字符串不同）。

代价是体积：一条 200 点的笔迹，数组约 1.6KB，路径字符串约 0.8KB。所以采样有两道闸——`PEN_MIN_DIST` 过滤掉太近的点（否则 60Hz 鼠标会画出几千个几乎重合的点），`LIMITS.MAX_POINTS` 兜底上限，保证单条笔迹不会撑爆消息。

`_penDraft` 里还要算 `stroke` 之外的包围盒：先扫一遍所有点取 `minX/minY/maxX/maxY`，宽高至少给 1（一条水平直线的 `h` 是 0，`w/h` 为 0 的图形既画不出来也点不中）。命中测试对画笔用包围盒而不是精确描边距离——用户点到笔迹附近就该选中，要求像素级精确反而难用。

**空状态面板的坑**：`.empty-state.is-hidden` 一开始只写了 `opacity: 0`。元素虽然看不见，但仍然占据布局、内部按钮仍然可以命中，于是画布正中央约 300×200 的区域变成死区——画笔、框选、双击在那里全部失效。这类问题单元测试永远抓不到，只有真的在浏览器里点一下才会暴露。修法是补上 `visibility: hidden`（退出命中测试）和 `pointer-events: none`，并用 `transition: … visibility 0s linear 0.25s` 让淡出动画先走完。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `this.drag = { mode: 'pan', last: sp }` | 用普通对象当状态机 | 读 `mode` 就分支，不用一堆布尔标志 |
| `{ world, shapeId = null }` | 解构 + 默认值 | 调用方只传关心的字段 |
| `for (const [id, origin] of map)` | for-of 里解构 Map 的每一项 | 同时拿键和值 |
| `{ record: false }` | 参数对象里的开关 | 明确「改数据但不记撤销」 |
| `e.target.closest(...)` | 从目标向上找最近匹配祖先 | 事件委托 |
| `e.button === 1` | 鼠标键编号：0 左 1 中 2 右 | 中键平移 |
| `target.tagName === 'INPUT'` | 元素标签名（大写） | 判断焦点是否在输入控件里 |
| `case 'Delete': case 'Backspace':` | switch 的 fallthrough | 两键共用一段逻辑 |
| `this.ui?.syncTool()` | 可选链调用，null 就跳过 | 构造期 ui 还没接上 |
| `try { } catch { }` | 不绑定错误变量的 catch | 只关心「失败就算了」 |
| `{ passive: false }` | 声明这个监听器会 `preventDefault` | 否则 wheel 里禁止不了默认滚动 |
| `Math.exp(x)` | e 的 x 次方 | 缩放因子来回对称 |
| `performance.now()` | 高精度毫秒时间戳 | 60ms 节流计时 |

### 写错了会怎样
- **去掉 `_throttleCommit` 的时间判断，每次 move 都提交**。1 秒拖动产生 100 多条 op，每条都要序列化、走 WebSocket、进服务端、广播给所有人。别人看到图形一顿一顿地跳，自己 CPU 飙高。
- **松手时不补最终提交**。快速拖一下马上松手，图形「弹回」几十毫秒前的位置。只在快速操作时出现，慢速拖动完全正常，极难复现。
- **`_onPointerDown` 去掉 `setPointerCapture`**。鼠标拖到右侧面板上松手，`pointerup` 被面板接走，`drag` 永远是 move，之后鼠标在画布上随便一动图形就跟着跑。

## client/js/presence.js（别人的光标）
### 它解决什么问题
看到「小王的光标在这儿」比看到「小王改了这个矩形」更即时，它传达的是「有人在看这块区域」，能避免两个人同时改同一个图形。

但光标有个特殊性质：**每秒变几十次，而且过期就毫无价值**。三秒前的位置没有保留意义。如果光标也走 op 通道（带版本号、进文档状态、落盘、参与冲突合并），文档里会塞满几万条「光标移动」，每次移动都要走一遍一致性协议，离线重连还得把历史光标全重放一遍。所以光标走一条**完全独立的、不保证送达**的通道：丢了就丢了，下一条马上就来。

### 代码逐段讲
**节流上报**
```js
this._pending = worldPt;
const now = performance.now();
const elapsed = now - this._lastSent;
if (elapsed >= CURSOR_THROTTLE) {
  this._flush();
  return;
}
if (this._timer) return;
this._timer = setTimeout(() => {
  this._timer = null;
  this._flush();
}, CURSOR_THROTTLE - elapsed);
```
`CURSOR_THROTTLE = 80`，即最多 12.5 次/秒。人眼对光标平滑的感知大约在这个量级，再密看不出差别，流量却翻倍。

这是「首次立即发 + 尾部补发」的节流，比简单的时间窗丢弃更好：每次把最新位置写进 `_pending`（覆盖旧的）；距上次发送已超过 80ms 就立刻发；否则设定时器，在「距上次发送满 80ms」时补发一次。`if (this._timer) return` 防止设多个定时器，只保留最早那个。

关键在 `_pending` 是**被覆盖**而不是排队：鼠标快速划过时，中间几十个位置全被覆盖，最后发出去的永远是最新那个，既不积压也不发过期位置。如果没有尾部补发，用户快速移动后停下，最后一次移动可能落在时间窗内被丢弃，别人的光标会停在你 80ms 前的位置，看起来像「光标卡住了」。

`this.onSend?.(this._pending)` 是 `main.js:137` 传进来的 `(pt) => net.sendPresence(pt)`，走独立的 presence 消息类型，不经过 op 队列——这就是光标不走 op 通道的落地方式：它连 store 都不碰。

**重排**
```js
for (const peer of this.peers.values()) {
  if (!peer.cursor) {
    peer.el.style.display = 'none';
    continue;
  }
  const p = this.board.worldToScreen(peer.cursor);
  peer.el.style.display = 'block';
  peer.el.style.transform = `translate(${Math.round(p.x)}px, ${Math.round(p.y)}px)`;
```
光标存的是**世界坐标**，因为画布会平移缩放——存屏幕坐标的话，别人一平移所有光标就全飘走了。每次渲染用当前 viewport 转成屏幕坐标。

这个方法有两个调用时机：收到新光标时，以及**本地视口变化时**（`main.js:154-157` 的 `onViewportChange` 里调 `presence.render()`）。后者很重要：别人没动，但我滚了一下滚轮，别人的光标也得跟着移动，否则看起来像粘在屏幕上。

**DOM 只创建一次**
```js
if (!clientId) return null;
let peer = this.peers.get(clientId);
if (peer) return peer;

const el = document.createElement('div');
el.className = 'remote-cursor';
el.innerHTML = ARROW_SVG;
const label = document.createElement('span');
label.textContent = name || '访客';
label.style.background = color || '#64748b';
```
`if (peer) return peer` 是「已存在就复用」。**DOM 只创建一次**，后续只改 `transform` 和文字。每条消息都重建 DOM 的话，光标会不停闪烁（元素被移除再插入，浏览器来不及合成），垃圾回收压力也大。`innerHTML = ARROW_SVG` 只在创建时执行一次；之后内容更新全用 `textContent`，因为名字是用户可控的，用 `innerHTML` 拼名字有 XSS 风险。

**颜色由 clientId 派生**

`color` 是服务端算好下发的：`shared/protocol.js` 的 `presenceColor(clientId)` 把 clientId 的字符逐个 `h * 31 + charCode` 再取模 360，得到 `hsl(h 72% 46%)`。

为什么不用随机数？随机的话每次刷新都变，同一个人今天红明天绿，其他人根本记不住「红色光标是谁」。用 clientId 派生，同一个 id 永远得到同一个色相；而 clientId 存在 `sessionStorage`（见 `main.js` 注释），同一标签页刷新后还是同一个 id，颜色就稳住了。客户端只负责用服务端给的颜色，`color || '#64748b'` 是兜底。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `new Map()` + `get/set/delete/has` | 键值表 | 按 clientId 索引 peer |
| `[...this.peers.keys()]` | Map 的键摊成数组 | 边遍历边删会出问题 |
| `document.createElement` | 动态建元素 | 每个远端光标一个 DOM |
| `el.innerHTML = STRING` | 把字符串当 HTML 解析 | 一次性插入固定 SVG |
| `el.textContent = str` | 只设纯文本，不解析 HTML | 昵称是用户输入，防注入 |
| `` `translate(${x}px, ${y}px)` `` | 模板字符串 | 拼 transform 值 |
| `'currentColor'`（SVG） | 引用当前 `color` 的值 | 一个属性同时管图标和文字颜色 |
| `?.()` | 可选调用，函数不存在就短路 | `onSend` 可能没传 |
| `setTimeout(fn, ms)` | 延迟执行一次 | 节流的尾部补发 |
| `hsl(h 72% 46%)` | 色相/饱和度/亮度 | 只改色相就得到一组协调颜色 |

### 写错了会怎样
- **去掉 80ms 节流**。鼠标快速划过画布每秒产生 100-200 条消息，服务端要广播给房间所有人。10 个人时广播量 2000 条/秒，WebSocket 堵住，连 op 都发不出去——表现是「人一多就卡」。
- **`render()` 不转坐标，直接把 `peer.cursor` 当屏幕坐标**。别人不动，你滚一下滚轮，所有人的光标瞬间错位到奇怪的角落，越缩放偏得越远。
- **颜色改成 `Math.random()`**。同一个人每次刷新颜色都变，多人协作时分不清谁是谁。

## client/js/ui.js（按钮和状态条，只碰 DOM 不碰数据）
### 它解决什么问题
页面上有二十多个可交互元素。如果处理逻辑散落各处，会变成「点撤销直接改 store，点工具栏直接改 canvas」——同一条业务规则两份实现，改一处忘一处。

`ui.js` 的边界很硬：**只读 DOM、只写 DOM，任何改变状态的动作都转手交给 `interactions` / `store` / `net`**。它不自己 `store.undo()` 再去改 canvas，而是调 `interactions.doUndo()`，让那边统一处理「撤销 + 清选中 + 重画 + 刷新按钮 + 弹提示」。好处是：想换一套 UI（比如做成右键菜单），只需重写这个文件，业务逻辑一行不动。

### 代码逐段讲
**元素字典**
```js
this.$ = (id) => document.getElementById(id);

this.el = {
  status: this.$('status'),
  statusText: this.$('status-text'),
  members: this.$('members'),
  toolbar: this.$('toolbar'),
  undo: this.$('undo-btn'),
```
`this.$` 是挂在实例上的箭头函数。箭头函数不绑定自己的 `this`，这里的 `this` 就是构造时的实例，所以在任何地方 `this.$(...)` 都指向同一个 `document`。集中成一张表的好处：改 id 时只改一处，而不是在三十个地方找。

**工具栏委托**
```js
el.toolbar.addEventListener('click', (e) => {
  const btn = e.target.closest('[data-tool]');
  if (btn) interactions.setTool(btn.dataset.tool);
});
```
只在一个父元素上挂一个监听器，靠 `closest` 找「被点的到底是哪个按钮」。为什么不用 `e.target` 直接判断？因为按钮里套着 `<svg>` 和 `<path>`，用户真正点中的往往是 path，它身上没有 `data-tool`。`closest` 从 path 往上找，找到 `button[data-tool]` 就返回。少了这一步，点图标中心没反应、点按钮空白 padding 才有反应，用户会觉得「这个按钮时灵时不灵」。

**样式面板与状态条**

用 `input` 而不是 `change`：`input` 在拖滑块过程中连续触发，颜色能实时预览；`change` 只在松手时触发一次。回调里要写 `Number(el.strokeWidth.value)`——`input.value` 永远是**字符串**，直接传给 store 的话 `strokeWidth + 1` 会变成 `"21"`。

`setState(state)` 里只做 `el.dataset.state = state` 和 `statusText.textContent = STATE_LABEL[state] || state`。改属性后 CSS 的 `[data-state="online"]` 规则自动生效，JS 里没有一行 `style.background`；`|| state` 兜底，万一出现表里没有的状态就显示原始码而不是 `undefined`。

**选中信息与面板回填**
```js
const active = document.activeElement;
const editingPanel = active && active.tagName === 'INPUT' && active.closest('.inspector');
if (editingPanel) return;

if (flat.fill && flat.fill !== 'transparent') this.el.fill.value = flat.fill;
if (flat.stroke && flat.stroke !== 'transparent') this.el.stroke.value = flat.stroke;
this.el.strokeWidth.value = String(flat.strokeWidth ?? 2);
```
这是「面板回填」：选中红色矩形，取色器要跳到红色，滑块要跳到它的线宽。

但有个陷阱：用户拖取色器时 `input` 事件 → 改 store → store 触发 `onChange` → `updateSelection()` → 又去改 `el.fill.value`。程序把值写回去，取色器会「弹回」，手感断裂。所以先检查 `document.activeElement`：焦点在 `.inspector` 的 INPUT 上说明用户正在操作面板，直接 return。

`flat.strokeWidth ?? 2` 用的是空值合并：只有 null/undefined 才取 2。不能用 `||`——线宽真的是 0（用户拖到最左）时，`0 || 2` 会变成 2，永远显示不出 0。这是 `??` 和 `||` 最典型的区别。

**调试数字**

`updateStats()` 里定义了一个 `set(id, v)` 小函数，避免七行都写 `getElementById(...).textContent = ...`。两个数据源：`net.stats()` 给网络相关，`store.stats()` 给文档相关。

- **serverSeq**（`dbg-seq` → `s.lastApplied`）：本地已经应用到的服务端序号，每收到一条广播的 op 就往前推。它和 `bootEpoch` 一起用来判断「我是不是漏了消息」——收到的 op 的 seq 不是 `lastApplied + 1`，说明中间断了，需要全量重拉。
- **待发队列**（`dbg-queue` → `d.pending`）：本地已生成但还没被服务端确认的 op 条数。断网时这个数一直涨（本地照常编辑，op 全排队），重连成功后迅速归零。**它是判断「有没有数据没同步出去」最直观的指标**。
- **图形 / 可见**（`dbg-shapes`）：`total` 是 Map 条目数（含墓碑），`visible` 是 `deleted` 不为 true 的。两个数不一样说明有删除过的图形还占着位置，这是 CRDT 墓碑机制的正常现象。

**日志与 Toast**

写日志时把时间戳包成 `<span class="t">`、正文过一遍 `escapeHtml`，拼成一行写进 `line.innerHTML`，再 `host.appendChild(line)`；接着用 `while (host.childElementCount > LOG_LIMIT) host.removeChild(host.firstElementChild)` 裁掉最老的。数组和 DOM 两边都限长（`_logs.shift()` 和 `removeChild`），只限一边会导致内存和 DOM 不同步。

`escapeHtml(message)` 是必须的。`innerHTML` 会解析 HTML，如果 message 里含用户昵称（有人把名字改成 `<img src=x onerror=alert(1)>`），不转义就会执行脚本。Toast 那边则直接用 `textContent`，因为内容可能含服务器返回的错误信息，同样要防注入。

### 语法点
| 写法 | 什么意思 | 这里为什么用它 |
| --- | --- | --- |
| `this.$ = (id) => ...` | 箭头函数当实例方法，`this` 固定 | 到处取元素，写短一点 |
| `e.target.closest(sel)` | 从事件目标向上找最近匹配元素 | 事件委托，处理图标被点中的情况 |
| `el.dataset.state` | 读写 `data-state` 属性 | JS 只改数据属性，样式交给 CSS |
| `classList.toggle(name, force)` | 有则删无则加，第二个参数强制 | 工具按钮的选中态 |
| `input.value` 永远是字符串 | DOM 输入框的值类型 | 所以数字要 `Number(...)` |
| `??` 空值合并 | 只有 null/undefined 才取右边 | 线宽为 0 是有效值 |
| `\|\|` 逻辑或 | 任何假值（含 0、''）都取右边 | 名字为空时显示「访客」 |
| `innerHTML` vs `textContent` | 前者解析 HTML，后者纯文本 | 用户可控内容必须用后者或转义 |
| `while (host.childElementCount >= 3)` | 循环删到少于 3 个 | 限制 Toast 和日志条数 |
| `async` / `await` | 异步函数，等待 Promise 结果 | 剪贴板 API 是异步的 |
| `document.activeElement` | 当前获得焦点的元素 | 判断用户是否正在操作面板 |

### 写错了会怎样
- **工具栏用 `e.target.dataset.tool` 而不是 `closest`**。点按钮正中间（落在 `<path>` 上）没反应，只有点边缘空白才能切工具。
- **`updateSelection` 去掉 `activeElement` 判断**。拖取色器时每动一下就被写回旧值，疯狂闪烁，根本选不出想要的颜色；滑块拖到一半会被弹回去。
- **`log()` 里把 `escapeHtml(message)` 改成直接拼 `message`**。任何能把昵称改成 HTML 的人，都能在所有同房间成员的浏览器里执行脚本。
