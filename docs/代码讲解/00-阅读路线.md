这套文档一共四篇，讲完 `whiteboard/` 里全部业务代码（约 4200 行）。

```

01 数据层            shared/ids.js · shared/protocol.js · shared/merge.js
02 客户端-状态与网络   client/js/store.js · net.js · main.js
03 客户端-画布与交互   client/index.html · style.css · canvas.js · tools.js · presence.js · ui.js
04 服务端            server/config.js · store.js · ws.js · room.js · static.js · index.js
```

## 一、为什么不按目录顺序读

按目录读（先 `server/` 再 `client/`）会卡在第三页：`ws.js` 一上来就是二进制位运算，而你连"这个系统要解决什么问题"都还不知道。

**认知顺序应该是：先有问题，再有方案；先有名词，再有动词。**

```
① 先知道系统要防什么      →  四个翻车场景（见 docs/原理详解-小白版.md 第 2 节）
② 再认识最小的名词        →  id、图形、字段、戳            【01 数据层】
③ 然后看规则怎么用        →  校验、合并                    【01 数据层】
④ 接着看数据怎么流动      →  存 → 发 → 收                  【02 状态与网络】
⑤ 最后看怎么变成像素      →  画 → 点 → 拖                  【03 画布与交互】
⑥ 反过来看另一端          →  接 → 验 → 存盘 → 广播        【04 服务端】
```

第 ⑥ 步放最后，是因为服务端的每个设计（幂等、去重、先落盘）都是对客户端行为的**回应**。先懂客户端在干什么，服务端的设计才有理由。

## 二、六个阶段，每阶段解决一个疑问

| 阶段 | 你心里的问题 | 读完能回答 |
| --- | --- | --- |
| ① 现象 | 这东西跑起来是什么样 | 打开两个窗口，看到什么、F12 里有什么 |
| ② 名词 | 一条数据长什么样 | 一个图形为什么不是普通对象，而是一堆带戳的格子 |
| ③ 规则 | 两个版本撞上了听谁的 | 为什么比三个数就能保证收敛，不用服务器裁决 |
| ④ 流动 | 我拖一下，数据去哪了 | 乐观更新、待发队列、状态机、断线重连 |
| ⑤ 呈现 | 数据怎么变成屏幕上的方块 | 两套坐标系、DPR、命中测试、60ms 节流 |
| ⑥ 对端 | 服务器到底做了什么 | 序列化、幂等、归一化、先落盘再广播 |

## 四、三条主链路（先记住这个，再读细节）

### 链路 A：拖一个矩形（在线）

```
[浏览器 A]
tools.js  _onPointerDown      记录起点、判断点到谁
          _onPointerMove      更新 this.preview（只改内存，不落盘不发网）
          _throttleCommit     每 60ms 触发一次
          _commitPatches      调 store.applyLocal(..., { record: false })
             ↓
store.js  applyLocal          ① _nextOp 造 op（ver = 当前最大 + 1）
                              ② mergeOp 立刻改本地 → 界面即时响应
                              ③ _enqueue 进队列 → 通知 net
             ↓
net.js    sendOp              在线才发，离线就留在队列
          _send               JSON.stringify → ws.send
             ↓
[服务端]
index.js  handleMessage       令牌桶限流 → JSON.parse → 按 type 分发
          handleOp            room.applyOp
room.js   applyOp             ① normalizeOp 校验（与客户端同一份代码）
                              ② 校验 roomId / clientId 绑定
                              ③ seen 表幂等去重（opId + 指纹）
                              ④ hwm 高水位检查 clientSeq
                              ⑤ mergeOp 逐字段合并
                              ⑥ 先 store.append 落盘
                              ⑦ 分配 serverSeq → broadcast
             ↓
[浏览器 A 和 B]
net.js    _onOp               bootEpoch 检查 → seq 连续性检查
                              → store.applyRemote → lastApplied = seq
store.js  applyRemote         normalizeShape → mergeShape(authoritative)
             ↓
canvas.js render              requestAnimationFrame → _draw → 画出来
```

同时服务端还给 A 回一条 ack：

```
net.js    _onAck              只做一件事：dequeue（把 op 从待发队列摘掉）
```

**注意 ack 不推进 `lastApplied`**——这是全项目最容易写错的一行，见 02 篇。

### 链路 B：断网 → 继续画 → 恢复

```
① 调试面板勾「模拟断网」
   net.setSimulatedOffline(true) → ws.close(4001) → state = offline

② 用户继续拖
   store.applyLocal 照常改本地、照常 _enqueue
   → net.sendOp 发现 state !== online，什么都不做
   → pending 数组变长，localStorage 里的 queue 跟着更新
   → 界面完全正常，因为渲染只依赖 store，不依赖网络

③ 取消勾选
   net.connect → onopen → 发 hello（带 lastSeq）

④ 服务端回 welcome（全量快照 + serverSeq）

⑤ net._onWelcome
   lastApplied = serverSeq
   store.replaceAll(快照)          ← 整体替换，自愈
     └ replayPendingLocally()      ← 把队列里的 op 重新叠回去
   state = online

⑥ net._flushQueue
   按 clientSeq 排序，逐条重发

⑦ 服务端按 opId 去重
   重复的返回 duplicate，新的正常接受并广播

⑧ 两端 serverSeq 与 digest 一致 → 收敛
```

### 链路 C：按 Ctrl+Z

```
tools.js  doUndo
             ↓
store.js  undo              从 undoStack 弹出一条
          _applyEntry       对每个 item 取 backward 补丁
             └ _nextOp      ver = 当前最大 + 1  ← 关键：不是旧版本号
             └ mergeOp     本地立刻生效
             └ _enqueue    当作一条全新的 op 发出去
             ↓
        其他客户端收到后，看到的是"一次普通的反向修改"
```

**撤销不是时间倒流，是再做一个相反的操作。** 这是协作系统和单机系统最大的差别之一。

## 六、建议的读法（三遍）

**第一遍：只看标题和"它解决什么问题"。**

四篇加起来不到 40 个"它解决什么问题"小节。花 20 分钟读完，你就有整个项目的骨架了。**不要看代码。**

**第二遍：跟着链路 A 走一遍。**

打开 02 篇，从 `_onPointerDown` 开始，一路看到 `canvas.render`。每到一个函数就跳到对应文件确认一下——**不要相信文档，要相信代码**。这一遍大概 1 小时。

**第三遍：挑一个你最想改的地方，动手改。**

- 想加一种图形 → 从 `SHAPE_TYPES` 和 `_drawShape` 入手
- 想改合并规则 → 从 `mergeField` 入手
- 想改重连策略 → 从 `_scheduleReconnect` 入手

改坏了就 `git diff` 看回来。**改坏一次比读十遍记得牢。**

## 七、四个"读代码时容易卡住"的点

先记住，遇到时能少卡半小时。

**1. 为什么到处都在 `{ ...obj }`**

因为项目里几乎所有数据结构都是"不可变"风格：不修改入参，只返回新对象。这样合并函数才能安全地被调用任意次。看到 `{ ...x }` 就当它是"复制一份"。

**2. 为什么函数名带下划线前缀**

`_nextOp`、`_persistDoc`、`_onPointerDown` 是"约定上的私有"——JS 没有真正的 private（这个项目也没用 `#` 语法）。带下划线只是告诉读代码的人："这是内部实现，外部别调"。

**3. 为什么同一个逻辑在客户端和服务端各有一份**

不是重复代码，是**同一个文件被两端 import**（`shared/` 目录）。打开 `client/index.html` 看 `<script type="module">`，再打开 `server/index.js` 看 `import ... from '../shared/protocol.js'`，两边指的是同一个磁盘文件。

**4. 为什么 `state` 这个词到处都是**

它有四种含义，别混：

| 出现位置 | 指的是 |
| --- | --- |
| `net.state` | 连接状态（idle/connecting/syncing/online/offline） |
| `room.shapes` | 房间的权威数据 |
| `store.shapes` | 客户端的本地数据 |
| `style.css` 里的 `:root` 变量 | 视觉主题 |
