## 1. 先搞清楚：这个项目到底难在哪

很多人以为协作白板是个"画图程序"，所以第一反应是：画布、鼠标事件、Canvas API。

**画图确实不难。** 用 Canvas 画一个矩形，不超过 20 行代码：

```js
ctx.fillRect(x, y, w, h);
```

真正难的是后面这三件事，而且它们会互相纠缠：

| 难点 | 具体是什么 | 不知道会怎样 |
| --- | --- | --- |
| **多副本** | 同一个白板，A 电脑上一份、B 电脑上一份、服务器上一份 | 三份数据慢慢长得不一样，谁也说不清哪个是对的 |
| **网络会断** | 地铁进隧道、Wi-Fi 切换、笔记本合盖 | 断网期间用户还在画，这些改动怎么办 |
| **操作会并发** | A 和 B 几乎同时改同一个图形 | 后到的把先到的冲掉，用户看到自己的操作"消失" |

所以这个项目的本质不是画图，而是：

> **让同一份数据在好几个副本上、跨越不可靠的网络、经过任意顺序和重复的传递，最终长得一模一样。**

这句话里每个词都是坑，我们一个一个拆。

## 2. 最朴素的写法，会在第几秒崩掉

在讲正确做法之前，先看看"直觉写法"会怎么翻车。这样你才知道后面那些设计不是炫技，是被逼出来的。

### 故事一：同步整个图形，后到的覆盖先到的

最直觉的做法：每次图形变了，就把**整个图形对象**发给服务器，服务器存下来，再转发给别人。

```
时刻 1:  A 把矩形改成红色      → 发送 {id:1, x:100, y:100, fill:'red'}
时刻 2:  B 把同一个矩形挪到 300 → 发送 {id:1, x:300, y:100, fill:'blue'}

结果:    B 的消息后到，整个对象被覆盖
         → A 改的红色没了
         → 而 A 在自己的屏幕上还看得见红色，因为没人告诉他被覆盖了
```

**问题**：图形是一个整体，A 改的是颜色，B 改的是位置，两件事根本不冲突，却因为"打包成一个对象"而互相残杀。

### 故事二：重连后把离线操作重放一遍，图形翻倍

断网了，用户在本地画了 3 个矩形。网络恢复，客户端想"把这 3 个补发给服务器"。

但客户端不知道自己断网前发出去的那条到底有没有到。于是保守起见，全发一遍。

```
断网前: 发出「创建矩形 A」   ← 服务端其实收到了
断网中: 画了矩形 B、C
重连后: 把队列里的 A、B、C 全发一遍

结果:  服务端收到两个「创建矩形 A」
        → 画布上出现两个一模一样的矩形，叠在一起
        → 用户拖动其中一个，另一个留在原地
```

**问题**：同一条消息被处理了两次，产生了两个副作用。

### 故事三：删除的图形又活过来了

A 删掉一个矩形。B 当时断网，手里还留着这个矩形的数据。

B 重连后，把自己手上的数据"补"给服务器——包括那个已经被删掉的矩形。

```
A: 删除矩形 → 服务端删除
B: 断网中，手里还有矩形
B: 重连，补发自己知道的矩形

结果:   矩形回来了。A 一脸问号。
```

**问题**：删除是"把数据从列表里拿掉"，但拿掉的东西，别人手里还有。

### 故事四：点撤销，什么都没发生

A 移动了一个矩形，然后按 Ctrl+Z。

本地的做法很自然：把刚才那条"移动到 (300,100)"的操作再执行一遍？不对，应该是"移回 (100,100)"。

但如果实现成"重新发送那条旧的移动操作"，服务端会检查版本号：这条操作是旧的，我这儿已经有更新的版本了，丢掉。

```
A: 撤销 → 发送旧操作 (ver=3)
服务端: 当前已是 ver=5，ver=3 太旧 → 拒绝
结果:   用户点了撤销，画布一动不动。看起来像卡了。
```

---

四个故事对应四种病，这个项目的药方是这样的：

| 病 | 药 | 在哪 |
| --- | --- | --- |
| 整体覆盖，丢别人的修改 | 把图形拆成**字段**，每个字段单独比版本 | `shared/merge.js` |
| 重复投递，图形翻倍 | 每条操作带**唯一 ID**，服务端见过就跳过 | `server/room.js` |
| 删除的东西被复活 | 删除只是**打个墓碑**，不真的删数据 | `shared/merge.js` |
| 撤销没反应 | 撤销**生成一条新操作**，版本号往上加 | `client/js/store.js` |

下面逐个讲。

## 3. 核心思想：别同步"状态"，同步"改动"

这是整个项目的地基，也是唯一一个你必须先接受、后面才看得懂的观念。

### 两种同步思路

假设你和朋友一起维护一个待办清单。

**思路 A：同步结果。** 每改一次，就把整张清单拍照发过去。

- 优点：简单，对方拿到就能直接用。
- 缺点：照片很大；两张照片同时到，你得决定用哪张，另一张里你朋友的改动就没了。

**思路 B：同步动作。** 只说"我加了'买牛奶'""我把第 2 条删了"。

- 优点：消息小；两条动作不冲突时可以都执行。
- 缺点：对方要自己按顺序执行一遍，才能算出清单长什么样。

**这个项目选 B。** 所有的改动都叫 **op**（operation，操作）。项目里一条 op 长这样（`shared/protocol.js`）：

```js
{
  opId:        "3f2a...",   // 这条操作的唯一身份证（uuid）
  roomId:      "demo",      // 属于哪个房间
  clientId:    "c-ab12cd34",// 谁发的
  sessionEpoch:"m8x2-9f",   // 这个标签页的"本次会话"标识
  clientSeq:   42,          // 这个客户端的第 42 条操作
  kind:        "patch",     // create / patch / delete
  target:      "9b1e...",   // 改的是哪个图形
  ver:         5,           // 我基于第 5 版改的
  patch:       { fill: "#ff0000" },  // 具体改了什么
  ts:          1729900000000
}
```

注意 `patch` 里只有 `fill` 一个字段。**这就是"字段级"的第一层含义**：A 改颜色只发颜色，B 挪位置只发位置，两条消息天生不打架。

### 同步动作的代价

选 B 就要付一个代价：**你得有一个规则，能把一堆乱七八糟到达的操作，算出唯一的结果。**

这个规则就是"合并函数"。它的正确性，决定了整个项目能不能用。

## 4. 数据结构：图形不是对象，是一排带戳的格子

### 4.1 普通写法 vs 本项目写法

普通人写白板，图形大概长这样：

```js
const shape = {
  id: 'abc',
  type: 'rect',
  x: 100, y: 100, w: 160, h: 110,
  fill: '#ffffff',
};
```

本项目里，同一个图形长这样（`shared/merge.js` 的 `cloneShape` / `emptyShape`）：

```js
const shape = {
  id: 'abc',
  type: 'rect',
  fields: {
    x:    { val: 100,       v: 3, c: 'c-aaa', o: 'op-1' },
    y:    { val: 100,       v: 3, c: 'c-aaa', o: 'op-1' },
    w:    { val: 160,       v: 3, c: 'c-aaa', o: 'op-1' },
    h:    { val: 110,       v: 3, c: 'c-aaa', o: 'op-1' },
    fill: { val: '#ff0000', v: 7, c: 'c-bbb', o: 'op-9' },  // ← A 改的
    x:    { val: 300,       v: 8, c: 'c-ccc', o: 'op-12' }, // ← B 挪的
  },
};
```

每个字段不再是一个值，而是**一个值 + 一个戳**。

**为什么要这么麻烦？** 因为只有每个字段单独带版本，才能实现"各改各的，互不影响"：

```
A 在第 7 版把 fill 改成红色
B 在第 8 版把 x 挪到 300

合并时逐字段比：
  fill: A 的戳 v=7 > 原来的 v=3  → 用 A 的红色  ✅
  x:    B 的戳 v=8 > 原来的 v=3  → 用 B 的位置  ✅

两个操作都活着。
```

如果按"整个图形一个版本号"来比，B 的 v=8 会赢，于是整条图形都用 B 的版本——A 改的红色就没了。**这是最容易在现场被发现的"像 bug"的场景，所以这里必须做字段级。**

### 4.2 戳里为什么要三个数字

戳是 `(v, c, o)` 三个数：版本号、客户端 ID、opId。

**只比版本号不行吗？** 不行。看这个场景：

```
A 和 B 都在 v=5 的基础上改同一个字段：
  A 发出 {fill: 红, v: 6}
  B 发出 {fill: 蓝, v: 6}

两个戳的 v 都是 6，谁赢？
→ 如果实现成"先到的赢"，那么 A 的电脑和 B 的电脑可能先到的不一样，
  最终两边算出不同结果 —— 白板永久不一致。
```

这叫**并列（tie）**。并列是一致性的死敌，因为并列意味着"结果取决于到达顺序"，而两台机器的到达顺序天然不同。

解决办法：**让任意两个戳都能分出大小，永远没有并列。** 这就是"全序"。

```
先比 v，v 一样比 c（客户端 ID 字符串比较），c 也一样比 o（opId）
因为 opId 是 uuid，两条不同的操作几乎不可能有相同的 opId
→ 任意两个戳，一定能分出谁大
→ 所有机器算出来的赢家必然是同一个
```

对应代码（`shared/merge.js`）：

```js
export function cmpStamp(a, b) {
  if (a.v !== b.v) return a.v < b.v ? -1 : 1;
  if (a.c !== b.c) return a.c < b.c ? -1 : 1;
  if (a.o !== b.o) return a.o < b.o ? -1 : 1;
  return 0;
}
```

### 4.3 为什么"全序"就等于"一定收敛"

这是整个项目最抽象、也最值得讲清的一段。别怕，只有三步。

合并函数（`mergeField`）做的事非常简单：**比两个戳，取大的那个。**

```
merge(我, 你) = 谁戳大用谁
```

"取最大"这个操作，天生满足三条性质：

| 性质 | 人话 | 为什么重要 |
| --- | --- | --- |
| **交换律** | `max(a,b) = max(b,a)` | 消息谁先到都无所谓 |
| **结合律** | `max(max(a,b),c) = max(a,max(b,c))` | 分几批合并都无所谓 |
| **幂等性** | `max(a,a) = a` | 同一条消息收一百遍，结果不变 |

三条合起来意味着：

> **不管消息以什么顺序到达、重复多少次、分成几批，最终每个副本算出来的结果都相同。**

这就是"收敛"。你不需要任何协调协议，不需要服务器去"裁决"，不需要加锁——**收敛性是从合并函数的数学性质里白送的。**

这也是为什么项目里服务端不做一致性裁决：一致性在客户端就已经保证了。

### 4.4 删除为什么是"墓碑"

回到故事三。如果删除是真的把数据从 Map 里删掉：

```
服务端: shapes.delete('abc')
B(离线): 手里还有 'abc' 的完整数据
B 重连: 发「创建 abc」 → 服务端: 没有 abc，那就创建吧 → 复活
```

所以删除不能真删，要留个记号（`client/js/store.js` 的 `deleteShape`）：

```js
const op = this._nextOp({
  kind: OP_KIND.DELETE,
  target: id,
  patch: { deleted: true },   // ← 不是删除数据，是把 deleted 字段设成 true
  ver: this._versionOf(id),
});
```

`deleted` 也是 `fields` 里的一个字段，也带戳，也参与合并。于是：

```
A 删除 (deleted=true, v=9)
B 离线时编辑 (x=500, v=8)

合并: deleted 用 A 的 true（v=9 更大），x 用 B 的 500
结果: 图形被删除，且位置更新了 —— 但看不见，因为 deleted=true
```

墓碑永远留着，渲染时用 `isVisible()` 过滤掉。代价是存储会慢慢变大，所以项目里有日志压缩（`server/store.js` 的 `compact`）。

### 4.5 渲染层看的是"扁平视图"

带戳的结构适合合并，但不适合画图。画矩形不需要知道它的版本号。

所以有一层转换（`shared/merge.js` 的 `flatten`）：

```js
// 存储/网络用这个
{ id, type, fields: { x: {val:100, v:3, c:'..', o:'..'}, ... } }

// 渲染/命中测试用这个
{ id, type, x: 100, y: 100, w: 160, h: 110, fill: '#ffffff', ... }
```

**为什么要分两层？** 因为网络结构和渲染逻辑会各自演化。如果渲染代码直接读 `fields.x.val`，以后一改数据结构，画布代码全得跟着改。中间隔一层 `flatten`，两边就解耦了。

## 5. 一次编辑的完整旅程

这一节是全篇最重要的。把"你拖动一个矩形"这件事，从鼠标按下到对方屏幕上出现，完整走一遍。

```
 A 浏览器                    服务端(房间)                  B 浏览器
    │                            │                           │
    │ ① 鼠标拖动                  │                           │
    │ ② 本地先改（立刻看到）       │                           │
    │ ③ op 进待发队列              │                           │
    │──── ④ 发 op ──────────────►│                           │
    │                            │ ⑤ 校验 / 去重              │
    │                            │ ⑥ 逐字段合并               │
    │                            │ ⑦ 先写 JSONL 落盘          │
    │                            │ ⑧ 分配 serverSeq           │
    │◄─── ⑨ 广播 op ─────────────┤──── ⑨ 广播 op ───────────►│
    │ ⑩ 合并（结果与 B 相同）      │                           │ ⑩ 合并
    │◄─── ⑪ ack ─────────────────┤                           │
    │ ⑫ 从队列里摘掉              │                           │
```

逐步看。

### ① 鼠标拖动：只更新"预览"

`client/js/tools.js` 里，拖动时并不立刻发消息：

```js
const COMMIT_INTERVAL = 60;   // 毫秒
```

鼠标每动一次（每秒可能上百次），只更新一个 `preview` 对象，画布直接画它。**手感是零延迟的**，因为它压根没等网络。

每 60ms 才真正提交一条 op，松手时补最后一次。为什么？因为一次拖动如果每个 `mousemove` 都发一条，会产生几百条 op——网络流量、撤销栈、服务端日志全部爆炸。

### ② 本地先改：乐观应用

`client/js/store.js` 的 `applyLocal`：

```js
const op = this._nextOp({ kind: 'patch', target: id, patch, ver: this._versionOf(id) });
this.shapes.set(id, mergeOp(shape, op));   // ← 立刻生效，不等服务端
```

这叫**乐观更新（optimistic update）**：先假设服务端会接受，直接改本地。用户看到的永远是"我操作完立刻就变了"。

代价是：万一服务端拒绝，本地就得回滚。这个项目里回滚的方式是"用服务端的权威态覆盖"（`adoptAuthoritative`），并且弹个提示。

### ③ 入队 + ④ 发送

```js
_enqueue(op) {
  this.pending.push(op);        // 进队列
  this._persistQueue();         // 存进 localStorage，刷新不丢
  this.onOp(op);                // 通知 net 去发
}
```

`net.sendOp` 里有个判断：**在线才发，离线就留在队列里。** 注意队列是先加的，所以离线期间队列会一直变长，这就是"断网还能画"的实现方式——不是特殊逻辑，是默认行为。

### ⑤ 服务端校验：用的是同一份代码

`server/room.js` 的 `applyOp` 第一件事：

```js
const parsed = normalizeOp(rawOp);
```

`normalizeOp` 来自 `shared/protocol.js`——**浏览器和 Node 引入的是同一个文件**。

为什么强调这一点？因为服务端会对越界的值做归一化（比如 `x` 超出 ±100000 就截断到边界，小数四舍五入成整数）。如果客户端和服务端用的是两套不同的规则，服务端存的是"截断后的 100000"，客户端本地显示的是"原来的 250000"，两边就永久分叉了。

> **一条经验：凡是两端都要执行的规则，就只写一份。**

### ⑥ 幂等去重：opId 是身份证

```js
const seenFp = this.seen.get(op.opId);
if (seenFp !== undefined) {
  // 见过了，直接返回上次的结果，不再应用一次
  return { ok: true, accepted: true, duplicate: true, ... };
}
```

这就是故事二的解药。客户端重连时哪怕把整条队列重发十遍，服务端也只会真正执行一次。

更细的一点：项目里存的不是 `opId → true`，而是 `opId → 内容指纹`：

```js
if (seenFp !== fingerprint) {
  return { ok: false, code: 'OPID_CONFLICT', ... };
}
```

**为什么？** 同一个 opId 却带着不同内容，说明要么客户端有 bug，要么有人在伪造消息。这种情况不能默默接受，必须报错并让客户端重新对齐。

### ⑦ 先落盘，再广播

```js
this.store.append(this.id, { seq, shape: next });   // 同步写文件
this.serverSeq = seq;
this.shapes.set(op.target, next);
// 然后才 broadcast
```

顺序不能反。如果先广播再落盘，服务端可能在广播后、写盘前崩溃：客户端认为自己收到过 `seq=100`，重启后服务端重放日志却没有 100——两端对"100 号操作对应什么状态"产生分歧。

`append` 用的是 `appendFileSync`，同步阻塞。这在服务端通常是禁忌，但这里是有意的：**宁可慢一点，也不能在崩溃时丢掉已确认的操作。**

### ⑧ 分配 serverSeq：给所有操作排一个总顺序

每条被接受的 op 都会拿到一个单调递增的整数。它有两个用途：

1. 客户端靠它检测"我有没有漏消息"（详见第 6 节）；
2. 服务端重启后，靠它判断日志有没有落后。

注意它和 `ver` 不是一回事：

| | 谁分配 | 范围 | 用途 |
| --- | --- | --- | --- |
| `ver` | 客户端 | 单个图形内 | 决定字段合并谁赢 |
| `serverSeq` | 服务端 | 整个房间 | 决定消息顺序、检测缺口 |

### ⑨ 广播给所有人，包括发起者

```js
this.broadcast({ type: MSG.OP, seq, bootEpoch, shape: next, opId: op.opId });
```

`broadcast` 没有排除发起者。很多人会觉得多余——A 自己发的，为什么还要收回来？

因为**服务端会对数据做归一化**。A 发的是 `x: 250000.7`，服务端存的是 `x: 100000`。如果 A 收不到广播，它本地永远是 250000.7，而别人看到的是 100000。

让发起者也走一遍"接收 → 合并"的流程，所有人（包括自己）看到的就是同一份数据。

### ⑩ 客户端合并：mergeShape，不是 mergeOp

`client/js/store.js` 的 `applyRemote`：

```js
this.shapes.set(
  incoming.id,
  current ? mergeShape(current, incoming, { authoritative: true }) : incoming,
);
```

这里有个容易写错的地方，代码里还专门留了注释：

```js
// 注意：这里必须用 mergeShape（图形 vs 图形），不能用 mergeOp（图形 vs op）
```

因为广播里带的是**完整的带戳图形**，不是一条 op。用 `mergeOp` 会把整个图形当成一次新的 patch 去盖戳，戳就乱了。

`authoritative: true` 的作用是：戳相等时采用服务端的值。这样服务端的归一化结果才能"压过"本地的原始值。

### ⑪⑫ ack 只负责出队，绝不推进序号

```js
_onAck(msg) {
  this.store.dequeue(msg.opId);   // 只做这一件事
  ...
}
```

而推进 `lastApplied` 的是 `_onOp`（收到广播时）。这个分工看起来随意，其实是踩过坑的：

```
假设 ack 也推进 lastApplied：
  发出 seq=9 和 seq=10 两条
  ack(10) 先到 → lastApplied = 10
  然后广播 seq=9 到 → 9 <= 10，被当成"重放的旧帧"丢弃
  
  结果：seq=9 那条永远没被应用，白板少了一个图形，而且再也补不回来。
```

`net.js` 顶部把这条规则写成了注释，因为破坏它只需要删一行代码。

## 6. 断网之后发生了什么

### 6.1 断网时，界面为什么完全没感觉

因为**本地编辑从来不等网络**。回顾第 5 节的 ②③④：改本地 → 进队列 → 尝试发送（失败就算了）。

所以断网时用户看到的只是右上角状态条变红，画布一切正常。这不是"做了离线模式"，而是"本来就没依赖网络"。

### 6.2 localStorage 里存了什么

打开 F12 → Application → Local Storage，你会看到四个 key：

| key | 存什么 | 为什么放这儿 |
| --- | --- | --- |
| `wb:doc:<room>` | 整个文档的图形（带戳） | 刷新页面不白屏 |
| `wb:queue:<room>` | 还没被确认的 op 队列 | 刷新页面不丢未同步的编辑 |
| `wb:seq:<room>` | `clientSeq` 计数器 | 刷新后序号接着涨，不会重号 |
| `wb:epoch:<room>` | 会话标识 | 区分"同一个人的不同次打开" |

还有一个 `sessionStorage` 里的 `wb:clientId`——**故意放 sessionStorage 而不是 localStorage**，因为要保证同一个浏览器的两个标签页拿到不同的 clientId。

如果两个标签页共用一个 clientId，它们发出的戳会一模一样，裁决结果就取决于谁先到——又回到"并列"那个坑里了。

### 6.3 重连的四步

```
① 连上 → 发 hello（带上我最后的 lastSeq）
② 服务端回 welcome（整个房间的快照 + serverSeq）
③ 客户端：清空本地文档 → 装入快照 → 把待发队列重新叠上去
④ 客户端：把队列里的 op 按 clientSeq 顺序重发
```

对应 `net.js` 的 `_onWelcome`：

```js
this.lastApplied = msg.serverSeq || 0;
this.store.replaceAll(msg.shapes || []);   // ③ 快照替换 + 重放队列
this._setState('online');
this._flushQueue();                        // ④ 重发
```

### 6.4 为什么是"快照全量替换"，而不是"增量补齐"

增量补齐（"告诉我我漏了哪几条"）看起来更省流量，但实现复杂度高得多：要维护每个客户端的游标、处理游标失效、处理服务端日志被压缩过的情况。

全量替换的好处是**自愈**：不管本地状态错成什么样，一次快照就回到正确状态。代价是图形多的时候快照大——但白板场景下几百个图形也就几十 KB，完全可以接受。

> 工程上的常见取舍：**优先选"简单且一定能修好"的方案，而不是"省一点流量但可能修不好"的方案。**

### 6.5 重放会不会产生重复图形？

不会，有两道保险：

1. 客户端合并是幂等的（`mergeOp` 用同一份戳，结果不变）；
2. 服务端按 `opId` 去重（第 5 节 ⑥）。

### 6.6 断线重连的退避为什么要加"抖动"

```js
const delay = Math.min(MAX_DELAY, BASE_DELAY * 2 ** this.retries) + Math.random() * 300;
```

- `BASE_DELAY * 2 ** retries`：0.5s → 1s → 2s → 4s …最多 15s。**避免服务器挂掉时所有客户端疯狂重连把它压死。**
- `Math.random() * 300`：加一点随机。**避免所有客户端在同一毫秒一起重连**（它们往往是在同一时刻掉线的，退避时间也会一样）。

这个随机量叫"抖动（jitter）"，是分布式系统里的标准操作。

### 6.7 为什么要检测 seq 缺口

假设客户端 `lastApplied = 10`，突然收到 `seq = 12`。说明 11 丢了。

```js
if (this.lastApplied > 0 && msg.seq !== this.lastApplied + 1) {
  this._forceResync('seq-gap');   // 直接全量重拉，不试图"补"
}
```

**为什么不试着补？** 因为一旦漏了一条，你就不知道漏的那条改了什么，后续所有合并都可能基于错误的前提。这时候唯一安全的做法是承认自己坏了，重新拉一份。

这个思路值得记住：**状态一旦可疑，就重建，不要修补。**

## 7. 三个"看起来像 bug，其实是设计"的地方

### 7.1 两人同时拖同一个矩形 → 后写赢，不是叠加

A 把矩形往右拖 100px，B 同时往左拖 100px。最终位置是其中一个的结果，不是"抵消后不动"。

这是**有意的取舍**。要让两个拖动叠加，需要记录"相对位移"而不是"绝对坐标"，还要处理"基于哪个版本位移"的问题——那就是 CRDT 的领域了，复杂度高一个量级。

项目在 `README.md` 的"已知限制"里明确写了这一点。**面试时主动说出这个限制，比假装它不存在要加分得多**——它证明你知道边界在哪。

### 7.2 两人改不同字段 → 两个都保留

这就是 4.1 讲的字段级合并。这也是这个项目最值得演示的一手：

```
窗口 A：选中矩形，改填充色
窗口 B：同时拖动同一个矩形

结果：颜色和位置都是最新的，谁也没覆盖谁
```

如果换成"整个图形一个版本号"，这个演示就会变成"其中一个操作凭空消失"。

### 7.3 离线改的版本落后于在线的人 → 服务端说"不接受"，但会给你正确状态

场景：A 断网时把矩形移到 (500,500)。同时 B 在线把它改成了 (200,200)，版本更高。A 重连，把自己的 op 发上去。

服务端的处理（`server/room.js`）：

```js
const next = mergeOp(current, op);
const changed = !shapesEqual(current, next);

if (!changed) {
  // 没产生任何变更 —— 说明这条 op 版本落后
  return { ok: true, accepted: false, duplicate: false, shape: current, seq: null };
}
```

注意返回的是 `accepted: false` **但 `shape` 带着当前权威态**。客户端收到后：

```js
if (!msg.accepted) {
  if (msg.shape) this.store.adoptAuthoritative(msg.shape);   // 强制覆盖本地
  this.handlers.onConflict?.(msg);                            // 弹提示
}
```

用户看到的是一个 toast："离线修改已被他人覆盖，已同步为最新状态"。

**为什么要弹提示？** 因为静默覆盖是最伤信任的交互。用户明明看到自己拖到了 (500,500)，一刷新变了位置却没人解释，会以为程序坏了。一句话解释清楚，体验完全不同。

## 8. 撤销为什么这么麻烦

### 8.1 单机版撤销很简单

维护一个栈，每次操作记下"怎么反向操作"：

```
操作：把 x 从 100 改成 300
反向：把 x 从 300 改回 100
撤销：执行反向操作
```

### 8.2 协作版踩的坑

如果撤销的实现是"把旧的那条 op 再发一遍"：

```
A: 移动 (ver=3) → 服务端接受，图形现在是 ver=3
A: 撤销 → 重发那条 ver=3 的 op
服务端: 逐字段比戳，ver=3 不大于当前 ver=3 → 丢弃
结果: 什么都没发生
```

**问题**：旧 op 的版本号已经落后了，LWW 会直接把它当陈旧数据丢掉。

### 8.3 解法：撤销 = 生成一条新 op

`client/js/store.js` 的 `_applyEntry`：

```js
const op = this._nextOp({
  kind,
  target: item.id,
  patch: { ...spec.patch },      // 反向补丁
  ver: this._versionOf(item.id), // ← 当前最大版本 + 1，不是旧版本
});
```

于是撤销变成了一次**全新的、版本更高的修改**。它和普通编辑没有区别，能被同步、能被合并、能被别人看到。

这个思路很重要：**在协作系统里，"撤销"不是"时间倒流"，而是"再做一个相反的操作"。**

### 8.4 拖动的撤销为什么要合并

一次拖动会产生好几条 op（每 60ms 一条）。如果每条都进撤销栈，用户按一次 Ctrl+Z 只退回一点点，得按十几次才能回到原位。

所以 `tools.js` 在拖动过程中用 `record: false` 提交（不记录撤销），松手时用 `recordUndo` 合并成一条记录。

**这类细节不写测试根本发现不了，但用户一用就觉得"手感不对"。** 项目的 `tests/` 里有专门覆盖它的用例。

## 9. 服务端到底在干嘛

很多人以为服务端是"权威"，负责决定谁对谁错。**这个项目里不是。**

### 9.1 服务端只做三件事

| 角色 | 做什么 | 代码 |
| --- | --- | --- |
| **序列化点** | 所有 op 串行处理，给每条盖一个单调 `serverSeq` | `room.js` `applyOp` |
| **幂等去重** | `opId` 见过就跳过，防止重复投递 | `room.js` `this.seen` |
| **归一化** | 越界值 clamp、小数取整、非法数据拒绝 | `protocol.js` `normalizeOp` |

**它不裁决冲突。** 冲突的解决在客户端的合并函数里——因为合并函数满足交换律/结合律/幂等，所以只要所有客户端收到**同一组** op，就必然算出同一个结果。服务端的作用只是保证"大家收到的是同一组、同一顺序"。

### 9.2 那服务端能不能去掉？

不能，因为：

1. **需要一个大家都信得过的顺序**。没有服务端，客户端之间要自己选主，那是另一套复杂度。
2. **需要持久化**。谁关电脑谁的数据就没了，白板就失去了意义。
3. **需要挡住脏数据**。浏览器里 F12 一开，谁都能往 WebSocket 里灌任意 JSON。没有服务端校验，一个恶意客户端就能把所有人的画布搞坏。

### 9.3 单进程的局限

房间状态全在内存的 `Map` 里。这意味着：

- 只能单实例部署（多实例的话，A 连到实例 1、B 连到实例 2，互相收不到广播）；
- 进程重启后从 JSONL 重放（能恢复，但重启期间连不上）。

要支持多实例，得把广播换成 Redis Pub/Sub 或消息队列，把持久化换成数据库。项目没做，但 `README.md` 里写清了。

## 10. 为什么不用现成的轮子

这一节回答"你为什么不用 X"——面试必问。

### 10.1 为什么不用 Yjs / Automerge

它们是最成熟的 CRDT 库，用上去代码量能少一半。不用的理由有三层：

1. **题目要考的是理解，不是集成**。用 Yjs 之后，你讲不出"为什么这样能收敛"，只能讲"我调了个 API"。
2. **它们解决的是更难的问题**。Yjs 支持字符级协同编辑、相对位置（图形跟着容器一起动）。白板的冲突率远低于文本编辑，字段级 LWW 就够了。
3. **代价是可控的**。项目明确写了"字段级 LWW 不是意图保留"，把边界摆出来，比假装全能更可信。

> 答辩时的标准答法：**"我知道 Yjs 更强大，但这个场景的冲突率低，LWW 的复杂度/收益比更好；如果要做文本字符级协同，我会换 Yjs。"**

### 10.2 为什么手写 WebSocket

`server/ws.js` 445 行，实现了 RFC 6455 的握手、分帧、掩码、分片、关闭码。

- 题目要求"说明通信协议、消息格式和异常处理方式"——手写过才讲得出来；
- 零依赖 → 评卷方 `git clone` 之后 `node server/index.js` 直接能跑，不用 `npm install`（内网环境经常装不上包）。

### 10.3 为什么不用 Express / Koa

服务端总共就三类请求：静态文件、`/ws` 升级、两个调试接口。`node:http` 原生 API 一百行就够，引入框架反而多一层抽象要看。

### 10.4 为什么不用数据库

JSONL（一行一个 JSON）的好处：

- 追加写，天然顺序，不需要事务；
- 出问题能直接用记事本打开看；
- 崩溃最多丢最后半行，重放时跳过即可（`store.js` 的 `truncated` 处理）。

几百个图形、单房间的场景，JSONL 完全够用。用数据库是杀鸡用牛刀，还多一个部署依赖。

### 10.5 为什么不用 React / Vue

整个应用的"状态"就是一个 `Map<shapeId, shape>`，加一个待发队列。用框架反而要处理"框架状态"和"文档状态"两份状态怎么同步的问题。

用原生 DOM + Canvas，`store.onChange` 一触发就重画，链路清晰，没有隐藏的更新时机。

| 改重连退避 | `client/js/net.js` | `_scheduleReconnect` |

1. `shared/merge.js` 的 `cmpStamp` —— 改成非全序，收敛性立刻没了；
2. `client/js/net.js` 的 `lastApplied` 推进时机 —— 让 ack 也推进，会丢帧；
3. `shared/protocol.js` 的 `FIELD_SPEC` —— 客户端和服务端共用，改一处等于改两边（这是好事）。

## 12. 五个可以自己动手做的实验

看懂 ≠ 会用。这五个实验都能在 10 分钟内做完，做完你对这套机制的理解会完全不一样。

### 实验一：把合并改成"本地优先"，观察不一致

把 `mergeField` 里的 `if (cmp > 0) return { ...remote };` 改成 `return { ...local };`（永远用本地的）。

打开两个窗口，A 改颜色、B 挪位置。**两边会永久不一致**，而且刷新也修不好——因为刷新只拉服务端快照，本地又会用自己的值覆盖回去。

> 这个实验让你亲手体会"为什么合并函数必须对称"。

### 实验二：把墓碑改成物理删除，复现"复活"

把 `deleteShape` 改成真的 `this.shapes.delete(id)`。

A 删掉一个图形，B 断网（用调试面板勾"模拟断网"），B 重连。

**图形会活过来。** 这就是第 2 节故事三的现场版。

### 实验三：让 ack 也推进 lastApplied，复现丢帧

在 `_onAck` 里加一行 `this.lastApplied = msg.seq;`。

然后快速连续画 20 个图形（用脚本或快速点击）。**偶尔会少一两个**，而且日志里能看到"serverSeq 出现缺口"。

> 这个 bug 极难复现、极难定位，所以项目把它写成了注释警示。

### 实验四：把提交间隔改成 0，看 op 数量爆炸

把 `tools.js` 的 `COMMIT_INTERVAL` 改成 `0`。

拖动一次矩形，然后看调试面板里的"发送"计数——**从几条变成几百条**。

> 这就是为什么要有节流。分布式系统里，"多说话"的代价比你想的高。

### 实验五：断网画 10 个图形，然后刷新页面

勾"模拟断网"，画 10 个图形，然后 **F5 刷新**（别取消勾选）。

刷新后 10 个图形还在，队列深度还是 10。取消勾选，全部同步过去。

> 这个实验证明：离线能力不依赖内存，是持久化的。

## 13. 常见疑问

**Q：为什么用版本号，不用时间戳比大小？**
A：因为电脑的时钟不准，而且不同机器的时钟会漂移。A 的电脑慢 5 秒，它发出的"更晚"的操作会被判定为"更早"。版本号是逻辑时钟，不受物理时间影响。`ts` 字段只用于展示和排序，不参与裁决。

**Q：版本号会溢出吗？**
A：`ver` 上限是 1e9，`serverSeq` 是 JS 安全整数范围。正常使用永远到不了。真要到了，得换 64 位或重新设计——但那是几十年后的事。

**Q：图形很多会卡吗？**
A：渲染是全量重绘。几千个图形在 Canvas 上仍然流畅（60fps 下每帧 16ms，画几千个矩形大概 2-3ms）。真正的瓶颈是网络快照大小，所以有 `MAX_SHAPES_PER_ROOM = 5000` 的上限。

**Q：两个人同时创建图形，id 会撞吗？**
A：用的是 uuid v4，碰撞概率是 1/2^122，比连续中十次彩票还低。不需要额外处理。

**Q：op 里为什么要带 roomId 和 clientId？服务端不是知道吗？**
A：为了防伪造。如果只信任连接身份，一个客户端可以构造"我是别人"的 op。服务端会校验 `op.clientId === conn.clientId`，不一致直接拒绝（`room.js` 的 `CLIENT_MISMATCH`）。

**Q：为什么不给每个字段单独发 op，而是打包在一个 patch 里？**
A：因为一次拖动改的是 x 和 y 两个字段，它们逻辑上是一次操作。打包之后共享同一个戳，撤销时也能一起回退。如果拆开发，可能出现"x 改了、y 没改"的中间态。

**Q：光标位置为什么不走 op？**
A：光标是瞬时信息，不需要持久化，也不需要一致性（丢一帧无所谓）。所以它走独立的 `presence` 通道，不进文档状态——`presence.js` 开头专门写了这个理由。**把"需要一致性的"和"不需要一致性的"数据分开，能省掉大量复杂度。**

**Q：服务端重启会怎样？**
A：每次启动生成新的 `bootEpoch`。客户端发现 `bootEpoch` 变了，就知道服务端重启过，会全量重拉（`net.js` 的 `_onWelcome` 里有 `epochChanged` 判断）。房间数据从 JSONL 重放恢复。

## 14. 术语表

| 术语 | 人话解释 |
| --- | --- |
| **op（操作）** | 一次改动的描述，比如"把 id=abc 的 fill 改成红色" |
| **LWW** | Last-Write-Wins，最后写入者胜。本项目是"版本号最大的赢" |
| **LWW-Register** | 一个带时间戳的值，合并时取戳最大的 |
| **字段级** | 每个字段单独比版本，而不是整个对象一起比 |
| **全序戳** | 任意两个戳都能分出大小，不会并列。本项目用 `(v, c, o)` |
| **收敛（convergence）** | 所有副本最终算出完全相同的结果 |
| **交换律/结合律/幂等** | 顺序无关、分批无关、重复无关。三条合起来保证收敛 |
| **墓碑（tombstone）** | 删除时只标记 `deleted=true`，不真删数据，防止被离线端复活 |
| **乐观更新** | 先改本地再发网络，不等服务端确认 |
| **幂等（idempotent）** | 同一条消息执行一次和执行一百次，结果一样 |
| **快照（snapshot）** | 某一时刻整个房间的完整状态 |
| **seq 缺口** | 收到的序号不连续，说明中间漏了消息 |
| **退避（backoff）** | 重连失败后等越来越久再试，避免压垮服务器 |
| **抖动（jitter）** | 退避时间上加随机量，避免所有客户端同时重连 |
| **bootEpoch** | 服务端每次启动换一个标识，客户端据此判断"它重启过" |
| **presence** | 多人光标这类瞬时信息，不进入文档状态 |
| **权威态（authoritative）** | 服务端存的那份，带归一化结果 |

## 15. 一分钟讲给别人听

如果只能讲一分钟，讲这个：

> 这是一个多人实时协作白板。难点不在画图，在于让多份数据在断网、并发、重复投递的情况下最终长得一样。
>
> 核心做法是不同步状态，而是同步操作（op）。每个图形的每个字段都是一个独立的 LWW 寄存器，带一个三元组戳 `(版本号, 客户端ID, opId)`。这个三元组是全序的，所以任意两条操作都能分出胜负，永远不会并列。合并就是逐字段取最大——而"取最大"天然满足交换律、结合律、幂等性，所以不管消息以什么顺序到达、重复多少次，所有副本最终必然收敛到同一状态。
>
> 服务端不做裁决，只做三件事：给操作排单调序号、按 opId 幂等去重、把越界值归一化。它先落盘再广播，保证崩溃不丢数据。
>
> 离线是靠"本地乐观应用 + localStorage 队列"实现的，界面从不等待网络。重连时先拉全量快照替换本地，再把未确认的队列叠回去重发——幂等保证重发不会产生重复图形。
>
> 三个关键取舍：删除用墓碑不物理删；撤销不是重放旧操作而是生成版本更高的新操作；两人同时拖同一图形是后写赢而不是叠加——最后这条我知道它的局限，要做意图保留就得上 CRDT。
