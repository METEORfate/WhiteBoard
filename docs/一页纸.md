# 一页纸

一个零依赖的多人协作白板：浏览器里画图形，多端实时同步，断网能继续画，重连后自动补齐。核心难点不是画图，而是**两个人同时改同一张图时，两端最终看到同一个结果**。

## 问题 → 做法 → 代价

| 问题 | 做法 | 代价 |
| --- | --- | --- |
| 两人同时拖同一个图形 | 字段级 LWW：每个字段带一个全序戳 `(ver, clientId, opId)` | 同一字段的并发写只有一方生效，不是位移叠加 |
| 一人改颜色、一人挪位置 | 字段戳彼此独立，字段集合不相交，两个写都保留 | 每个字段都存戳，图形体积变大 |
| 断网后还得继续画 | 本地乐观应用 + `localStorage` 待发队列，刷新不丢 | 重连要重放；离线写入版本落后时会被服务端驳回，需 rebase 后重发 |
| 重连后不知道差了多少 | 快照全量替换 → 叠回未确认队列 → 按 `clientSeq` 重放 | 每次重连传全量，带宽随图形数增长 |
| 重发导致重复图形 | 服务端按 `opId` + 内容指纹去重，重复只回旧结果 | 要维护 `seen` 表（5 万条上限，FIFO 淘汰） |
| 协作里的撤销点了没反应 | 撤销不重放旧 op，用「当前最大版本 + 1」生成新 op | 撤销本身占一个版本，可能盖掉别人刚改的字段 |
| 两端归一化规则不一致 | `shared/` 是同一份物理文件，浏览器与 Node 共用 | 改协议要同时回归两端，不能只改一侧 |
| 崩溃后序号与内容错位 | 服务端先落盘（`appendFileSync`）再广播，JSONL 追加写 | 每条 op 同步阻塞一次磁盘写，吞吐受限于磁盘 |

## 四条不能破坏的规则

破坏任意一条，「最终一致」就退化成「最终分叉」。

| 规则 | 破坏了会怎样 |
| --- | --- |
| 广播与 ack 都带**归一化后的全量 shape**，不带 patch | 客户端各自 merge，本地旧值会算出不同结果，且戳相同谁也盖不过谁，差异永久保留 |
| `lastAppliedSeq` 只由**快照和广播**推进，绝不由 ack 推进 | ack(10) 先把水位推到 10，随后到达的广播 seq=9 被当成重放丢弃，那条修改永久丢失 |
| 比较键必须含 `opId`，且 `ver` **入队即冻结** | 重发时重算 ver，同一次逻辑操作有了两个戳，被当成两次独立写，结果与撤销栈都错 |
| 服务端**先落盘再广播**，快照建完才把连接加入广播集合 | 客户端已应用并推进了 seq，服务端崩溃重放后同一个 seq 对应另一个状态，序号相同内容不同 |

## 实测

| 项目 | 结果 |
| --- | --- |
| 单元 / 集成用例 | **96 / 96 通过**，13 个测试文件（耗时见 `docs/测试报告.md`） |
| 浏览器端到端 | **21 / 21 通过**（真实 Chrome + 裸 CDP，双标签页） |
| 200 条离线重放 | 朴素整队 flush 实测只有 **129 / 200** 条到达，其余被限流丢弃；改为客户端令牌桶 30 条/秒、32 条在途，服务端超限必回 `RATE_LIMITED` 后重发 |
| 覆盖点 | 合并代数性质（交换/结合/幂等）、乱序重复收敛、握手官方向量、房间隔离、重启恢复、断网重连 |

200 条这一行只有**修复前**的对照数字，仓库里没有修复后的精确条数，只有「几百条不会被吞掉」的定性结论。

## 已知边界

- **单进程内存态**：房间状态在 `Map` 里，只能单实例部署；多实例要换 Redis Pub/Sub 或粘性会话。
- **无鉴权**：房间号即凭证，拿到链接就能进、能改、能删。
- **字段级 LWW 不是意图保留**：同时拖动是「后改的赢」，不是位移叠加。
- **文本是整串替换**：两人同改一段文字，后写的整段覆盖先写的，字符级协同需要 OT 或序列 CRDT。
