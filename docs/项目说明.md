## 1. 项目概述

### 1.1 它是什么

一个支持多人实时协作的白板。多个浏览器打开同一个房间，任何一端的创建、移动、缩放、改样式、删除、撤销都会实时出现在其他端；断网期间可以继续编辑，网络恢复后自动补齐，并且不会重复、不会覆盖、不会复活已删除的图形。

### 1.2 需求对照

| 编号 | 要求 | 实现位置 | 说明 |
| --- | --- | --- | --- |
| ① | 至少两种图形 | `client/js/tools.js`、`canvas.js` | 矩形、椭圆、文本、画笔四种 |
| ② | 创建 / 移动 / 编辑 / 删除 / 缩放 / 撤销 | `tools.js`、`store.js` | 8 方向缩放把手、双击改文本、撤销栈（拖动合并为一步） |
| ③ | WebSocket 多端实时同步 | `server/ws.js`、`room.js`、`client/js/net.js` | 手写 RFC 6455，全双工广播 |
| ④ | 房间 / 文档标识隔离 | `server/index.js`、`room.js` | `?room=` → `hello.roomId` → 独立 `Room` 实例，跨房间广播不串台 |
| ⑤ | 本地保存未同步操作 | `client/js/store.js` | localStorage 三键：文档副本 / 待发队列 / clientSeq 水位 |
| ⑥ | 恢复网络后同步离线操作 | `net.js`、`store.js` | 快照替换 → 叠回队列 → 按序重放 → 幂等去重 |
| ⑦ | 并发、重复、非法数据 | `shared/merge.js`、`protocol.js`、`room.js` | 字段级 LWW / opId 幂等 / 白名单校验 |

| 非功能要求 | 落实方式 |
| --- | --- |
| 多客户端操作不损坏数据结构 | 合并函数满足交换律、结合律、幂等性（第 6 章）；服务端串行化 + 先落盘再广播 |
| 说明一致性模型、冲突处理、断线重连 | 本文第 6、7、8 章 |
| 至少一个并发编辑或断网恢复测试 | `tests/offline.test.js`（5 例）+ 端到端第 8–14 项（真实断网恢复） |
| 说明通信协议、消息格式、异常处理 | 本文第 5、9 章 |

### 1.3 技术选型的理由

**零依赖原生 JS**。不是为了炫技，是因为这道题的核心难点在协议和一致性，而任何一个框架都会把这些细节藏在 `onmessage` 回调后面。自己实现 RFC 6455 之后，「浏览器发来的一帧到底长什么样」这件事才变成可调试、可测试的东西——事实上正是这个选择让我们在测试阶段抓到了两个**单测全绿但真实浏览器必炸**的缺陷（见 [10.4](#104-两个致命缺陷的复盘)）。

代价也很清楚：没有框架的响应式，`ui.refresh()` 要手动调用；没有构建工具，模块路径必须写对相对层级。这些成本在这个规模下（约 5000 行）是可接受的。

## 3. 架构总览

### 3.1 分层

```
┌──────────────────────────── 浏览器 ────────────────────────────┐
│  tools.js      工具状态机：指针事件 → 意图（创建/移动/缩放/选中）│
│  canvas.js     渲染：DPR、视口变换、命中测试、选中框、把手       │
│  store.js      文档状态：乐观应用、待发队列、撤销栈、持久化       │
│  net.js        连接状态机：握手、心跳、退避重连、缺口检测         │
│  presence.js   远端光标        ui.js  状态条/面板/日志/toast     │
└───────────────────────────────┬────────────────────────────────┘
                                │  JSON over WebSocket
┌───────────────────────────────┴────────────────────────────────┐
│  shared/protocol.js   消息类型 + 字段规格 + 归一化/校验（共用）  │
│  shared/merge.js      全序戳比较 + 逐字段合并（共用）            │
│  shared/ids.js        uuid / 短 id / 会话 epoch（共用）          │
└───────────────────────────────┬────────────────────────────────┘
┌───────────────────────────────┴────────────────────────────────┐
│  server/index.js   HTTP 入口、/ws 升级、限流、消息分发、清扫     │
│  server/room.js    房间：权威状态、幂等去重、序列化点、广播       │
│  server/store.js   JSONL 追加写 + 重放 + 尾行修复 + 原子压缩     │
│  server/ws.js      RFC 6455 握手/分帧/掩码/分片/关闭码           │
│  server/static.js  静态资源、路径穿越防护、ETag                  │
└─────────────────────────────────────────────────────────────────┘
```

`shared/` 是关键设计：**浏览器和 Node 引入的是同一份物理文件**。如果客户端用一套 clamp 规则、服务端用另一套，那么服务端归一化后的值（比如把 `x: 100.4` 变成 `100`）会和客户端本地值（`100.4`）永久分叉——客户端认为自己是 100.4，服务端广播回来是 100，两边戳相同谁也不肯让步。共用代码从根上消除这类分歧。

### 3.3 一次编辑的完整路径

```
用户拖拽矩形右下角
  → tools.js  计算新 w/h，60ms 节流提交
  → store.applyLocal()  ① 本地立即 mergeOp 生效（界面零延迟）
                        ② 生成 op（ver = 当前最大版本 + 1，冻结）
                        ③ 入待发队列 + 写 localStorage
                        ④ 登记撤销记录
  → net.sendOp()  在线则 send({type:'op', op})
  → server: room.applyOp()
        ① normalizeOp（与客户端同一份代码）
        ② 校验 roomId / clientId 绑定
        ③ opId 幂等查表
        ④ clientSeq 高水位
        ⑤ 未知图形 / 类型冲突 / 房间上限
        ⑥ mergeOp 逐字段合并
        ⑦ store.append 落盘 → serverSeq += 1 → 广播给所有人（含发起者）
  → 所有客户端 net._onOp()
        ① bootEpoch 校验  ② seq 连续性校验  ③ store.applyRemote(mergeShape)
        ④ 从队列摘掉自己的 op  ⑤ lastApplied = seq
  → 发起者收到 ack：仅用于从队列摘除，不推进 seq
```

注意第 ⑦ 步「广播给所有人**含发起者**」和第 ④ 步「ack 不推进 seq」是配套的：发起者靠广播推进序号，ack 只负责清队列。这两条如果搞反，就会出现「发起者本地序号比服务端超前」的隐蔽分叉。

## 4. 数据模型

### 4.1 图形 = 一组带戳字段

图形不存「值」，存的是「值 + 谁在什么时候写的」。

```json
{
  "id": "1e264fab-08dd-4aff-8c23-d9c8ae164099",
  "type": "rect",
  "fields": {
    "x":  { "val": 299, "v": 3, "c": "c-a1b2c3d4e5", "o": "8f14e45f-..." },
    "y":  { "val": 191, "v": 1, "c": "c-a1b2c3d4e5", "o": "3c59dc04-..." },
    "w":  { "val": 180, "v": 3, "c": "c-a1b2c3d4e5", "o": "8f14e45f-..." },
    "h":  { "val": 120, "v": 1, "c": "c-a1b2c3d4e5", "o": "3c59dc04-..." },
    "fill": { "val": "#dbeafe", "v": 2, "c": "c-9f8e7d6c5b", "o": "b6d767d2-..." },
    "deleted": { "val": false, "v": 1, "c": "c-a1b2c3d4e5", "o": "3c59dc04-..." }
  }
}
```

`fields` 的每个条目是一个 **LWW-Register**（Last-Writer-Wins Register）：`val` 是值，`(v, c, o)` 是写入它的那一次操作的**全序戳**。

渲染时才拍平成一个普通对象（`merge.js: flatten`），缺失字段用 `FIELD_SPEC` 的默认值补齐——这样即使某个字段从未被写过，各端画出来的图形也完全一样。

### 4.2 全序戳

```
stamp = (v: number, c: clientId, o: opId)
```

比较规则（`merge.js: cmpStamp`）：先比 `v`，相等比 `c`（字典序），再相等比 `o`。

- `v` 是**逻辑版本号**，不是时间戳。用本地时钟会导致「时钟快的机器永远赢」，而且在没有 NTP 同步的环境里偏差可以到秒级。逻辑版本由客户端在生成 op 时取「该图形当前最大字段版本 + 1」，服务端不改它。
- `c` 是 `clientId`，用于打破「两个客户端恰好用了同一个 `v`」的平局。这是最常见的并发场景：两人同时从版本 1 开始改。
- `o` 是 `opId`（uuid），用于打破「同一个客户端同一版本发了两条不同 op」的极端情况（理论上不该发生，但网络重试和页面回退可能造出来）。

三者组合保证**任意两条 op 的戳不会相等**，因此比较结果是全序（total order），合并有确定答案。这一点是收敛性的前提：如果存在并列且处理方式依赖到达顺序，那么「A 先到」和「B 先到」就会得到不同结果，最终分叉。

### 4.3 墓碑

删除不物理移除，而是把 `deleted` 字段写成一个更高版本的 `true`：

```js
// store.js: deleteShape
const op = this._nextOp({
  kind: OP_KIND.DELETE,
  target: id,
  patch: { deleted: true },
  ver: this._versionOf(id),   // 当前最大版本 + 1
});
```

**为什么必须这样**：假设 A 在线删除了图形 G，B 离线时手里还有 G，并且在 G 上挪了一下位置。B 重连后会把这条 `patch` 发上来。如果服务端已经物理删除了 G，就会返回 `UNKNOWN_SHAPE`，B 触发全量重拉——这时 B 的图形消失，看起来是「删除生效了」，似乎没问题。

但真正的灾难在另一边：如果 B 离线时是**重新创建**了一个 id 相同的图形（比如从本地缓存恢复后又改了一次，产生了 `create`），服务端物理删除后收到这条 `create`，会把它当成新图形接受，于是已删除的图形**复活**在所有客户端上。

墓碑参与合并就解决了：`deleted=true` 带着更高的版本号，B 的旧 `patch` 版本更低，逐字段合并时被丢弃；B 的 `create` 也会因为 `deleted` 字段版本不够而合并出 `deleted=true` 的结果——图形保持删除状态。

墓碑也支持「复活」：如果后续有更高版本的 `deleted=false`（撤销删除就是这条），图形会正常回来。语义是自洽的。

### 4.4 为什么不是「整图形一个版本号」

如果整个图形共用一个 `ver`，那么「A 改颜色」和「B 挪位置」就是两个竞争同一个版本号的写操作——版本大的那个赢，另一个的修改被**整体丢弃**。

这是最常见的协作 demo 缺陷。用户看到的现象是：「我明明把颜色改成黄色了，怎么又变回去了？」而实际上两个人都没做错，是合并粒度太粗。

字段级 LWW 把粒度降到字段，两个不相交的字段集合互不影响，两个修改都保留。代价是存储变大（每个字段要带三元素戳）、合并逻辑稍复杂，但换来的是最直观的正确性。项目里 `tests/merge.test.js` 第 3 例和端到端第 13 项就是专门钉这个行为的：

```
并发修改不同字段：两个操作都被保留（字段级 LWW）— x=120 fill=#fde68a
```

## 5. 通信协议

### 5.1 传输

- 单条 WebSocket 连接，路径 `/ws`，JSON 文本帧。
- 帧上限 64 KB（`LIMITS.MAX_FRAME_BYTES`），超限以 `1009 Message Too Big` 关闭。
- 客户端必须掩码（RFC 6455 强制），服务端不回掩码；未掩码帧以 `1002 Protocol Error` 关闭。
- 支持分片（continuation frame）重组，但限制单消息总大小。
- 文本帧 UTF-8 严格校验：用 `TextDecoder('utf-8', {fatal: true})`，非法字节序列以 `1007 Invalid Payload` 关闭。

### 5.2 消息一览

| 方向 | type | 作用 | 关键字段 |
| --- | --- | --- | --- |
| C→S | `hello` | 加入房间、声明身份 | `roomId` `clientId` `sessionEpoch` `name` `lastSeq` |
| S→C | `welcome` | 全量快照 | `roomId` `bootEpoch` `serverSeq` `shapes[]` `members[]` |
| C→S | `op` | 提交一次编辑 | `op: { opId, clientId, clientSeq, kind, target, ver, patch, shapeType? }` |
| S→C | `op` | 广播已接受的编辑 | `seq` `bootEpoch` `shape`（归一化后全量） `opId` |
| S→C | `ack` | 确认某条 op 的处理结果 | `opId` `accepted` `duplicate` `seq` `shape` |
| C→S | `presence` | 上报光标 | `cursor: {x,y}` 或 `null` |
| S→C | `presence` | 广播成员变化/光标 | `event: join\|leave\|move` `clientId` `name` `color` `cursor` |
| S→C | `resync` | 要求客户端全量重拉 | `reason` |
| S→C | `error` | 拒绝原因 | `code` `message` |
| C→S | `ping` | 应用层心跳 | `t` |
| S→C | `pong` | 心跳应答 | `t` `serverSeq` |

**为什么心跳走应用层而不是 WebSocket 控制帧**：浏览器的 `WebSocket` API 不允许应用代码发送 ping/pong 控制帧（只有 `send()` 发数据帧）。要检测「连接还在但服务端已死」这种半开状态，只能自己做应用层心跳。

### 5.3 op 的字段规格

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `opId` | uuid | 必填 | 全局唯一，幂等去重的键 |
| `roomId` | string | `[A-Za-z0-9_-]{1,64}` | 必须与连接所在房间一致 |
| `clientId` | string | `[a-z0-9-]{6,40}` | 必须与连接身份一致（防冒名） |
| `sessionEpoch` | string | `[a-z0-9-]{4,40}` | 会话代际，配合 clientSeq 防误判重放 |
| `clientSeq` | int | `1..1e12` | 单调递增，服务端维护高水位 |
| `kind` | enum | `create` \| `patch` \| `delete` | |
| `target` | uuid | 必填 | 目标图形 id |
| `shapeType` | enum | `rect` \| `ellipse` \| `text` | 仅 `create` 必填 |
| `ver` | int | `1..1e9` | 字段级戳的版本分量 |
| `patch` | object | 非空，≤12 个字段 | 只允许白名单字段 |
| `ts` | number | 可选 | 仅用于调试展示，**不参与裁决** |

`patch` 白名单（`FIELD_SPEC`）：

| 字段 | 类型 | 约束 | 默认值 |
| --- | --- | --- | --- |
| `x` `y` | number | ±100000，取整，越界 clamp | 0 |
| `w` `h` | number | 2..20000，取整 | 160 / 120 |
| `fill` `stroke` | color | `#rrggbb` / `#rrggbbaa` / `transparent` | `#ffffff` / `#1f2933` |
| `strokeWidth` | number | 0..64，取整 | 2 |
| `text` | string | ≤2000 **码点** | `''` |
| `fontSize` | number | 6..400，取整 | 20 |
| `z` | number | 0..1e15，取整 | 0（新建时用时间戳，保证各端层级一致） |
| `deleted` | boolean | | `false` |

白名单之外一律 `UNKNOWN_FIELD` 拒绝。这条规则不只是为了安全：如果允许未知字段进入文档，那么不同版本的客户端会把对方的字段当成不认识的垃圾丢掉，导致「合并后字段消失」的诡异 bug。

### 5.4 正常时序

```
客户端 A                  服务端                    客户端 B
   │                        │                          │
   ├── hello ──────────────►│                          │
   │◄───────────── welcome ─┤ (快照 shapes[] + serverSeq)
   │                        │◄──────────── hello ──────┤
   │                        ├─────────── welcome ─────►│
   │                        │◄────── presence(join) ───┤
   │◄───── presence(join) ──┤                          │
   │                        │                          │
   ├── op(create) ─────────►│                          │
   │                        ├─ 校验 → 幂等 → 合并      │
   │                        ├─ 落盘 → seq=1            │
   │◄── op(seq=1, shape) ───┼─── op(seq=1, shape) ────►│
   │◄──────── ack ──────────┤                          │
   │                        │                          │
   │                        │◄───────── op(patch) ─────┤
   │◄── op(seq=2, shape) ───┼─── op(seq=2, shape) ────►│
   │                        ├──────────── ack ────────►│
```

要点：

- 发起者**同时**收到广播和 ack。广播用于推进 `lastApplied` 并更新文档，ack 仅用于从待发队列摘除。
- 快照与广播之间有竞态：`join()` 先把连接标记为 `joined=false` 并开始发快照，期间到达的广播进入 `conn.pending` 缓冲，快照发完再补发。否则「先收到新 op、再被旧快照覆盖」会丢掉一次修改。

| code | 触发条件 | 客户端反应 |
| --- | --- | --- |
| `BAD_JSON` | 消息不是合法 JSON | 记日志，累计违规计数 |
| `BAD_MESSAGE` | 缺 `type` | 记日志 |

## 6. 一致性模型

### 6.1 我们要的一致性是什么

**最终一致（Eventual Consistency）**：在所有客户端都停止编辑且消息全部送达之后，所有副本的内容完全相同。

不追求强一致（不需要任何时刻都相同）——那需要分布式锁或中心化串行提交，会让「本地编辑立即显示」这个体验消失，网络一慢就卡。

### 6.2 合并函数

```js
// shared/merge.js
export function cmpStamp(a, b) {
  if (a.v !== b.v) return a.v < b.v ? -1 : 1;
  if (a.c !== b.c) return a.c < b.c ? -1 : 1;
  if (a.o !== b.o) return a.o < b.o ? -1 : 1;
  return 0;
}

export function mergeField(local, remote, opts = {}) {
  if (!local) return remote ? { ...remote } : local;
  if (!remote) return { ...local };
  const cmp = cmpStamp(remote, local);
  if (cmp > 0) return { ...remote };
  if (cmp === 0 && opts.authoritative) return { ...remote };
  return { ...local };
}

export function mergeShape(a, b, opts = {}) {
  const out = { id: a.id, type: a.type, fields: {} };
  const names = new Set([...Object.keys(a.fields), ...Object.keys(b.fields)]);
  for (const name of names) {
    out.fields[name] = mergeField(a.fields[name], b.fields[name], opts);
  }
  return out;
}
```

`mergeField` 就是一个**取最大值**操作，只不过比较的是 `(v, c, o)` 三元组。

### 6.3 收敛性论证

合并函数 `⊔` 需要满足三条代数性质，才能保证「与消息到达顺序无关」：

**① 交换律** `a ⊔ b = b ⊔ a`

`mergeField` 的实现是「比较后取较大者」，比较结果与参数顺序无关（`cmpStamp` 是反对称的：`cmp(a,b) = -cmp(b,a)`）。因此交换两个参数不改变返回的是哪一个。

**② 结合律** `(a ⊔ b) ⊔ c = a ⊔ (b ⊔ c)`

逐字段看：每次 `⊔` 都是取三个戳中的最大者。取最大这个操作在任意结合顺序下都得到同一个元素，因为全序关系下最大值唯一。这就是为什么 `cmpStamp` 必须是**全序**而不是偏序——偏序下可能有多个极大元，结合顺序不同就会留下不同的那个。

**③ 幂等性** `a ⊔ a = a`

`cmpStamp(a,a) = 0`，`mergeField` 在 `cmp <= 0` 时返回 `local`，即 `a`。所以同一条 op 应用一万次和一次结果相同。

**推论**：设客户端收到同一批 op 的任意排列 `π`，最终状态为 `op₁ ⊔ op₂ ⊔ … ⊔ opₙ`。由交换律和结合律，这个值不依赖 `π`；由幂等性，重复投递不改变它。因此**所有客户端最终收敛到同一个状态**，无需任何协调。

这就是为什么服务端不需要「算对」——它只需要保证「所有客户端看到同一批 op」，顺序甚至不重要（虽然我们仍然保证顺序，见下）。

`tests/merge.test.js` 第 4 例直接对三条性质做了随机验证，不是靠人工推演。

### 6.4 那服务端还需要吗

需要。服务端的三个角色都不是为了「裁决冲突」，而是为了让系统可用、可解释：

**① 序列化点**。给每个被接受的 op 盖一个单调递增的 `serverSeq`。客户端据此判断「我有没有漏消息」——如果收到的 `seq` 不等于 `lastApplied + 1`，说明中间丢了帧，必须全量重拉。没有这个序号，丢帧是完全静默的：客户端永远不知道自己缺了东西。

**② 幂等去重**。客户端重连后可能重发队列里的 op（它不知道上次发出去有没有到）。服务端记住 `opId → 内容指纹`，重复的直接回旧结果，不重复应用。指纹不一致（同 opId 不同内容）说明客户端有 bug 或有人在伪造，返回 `OPID_CONFLICT` 并要求重拉。

**③ 归一化权威**。把 `x: 100.4` 归一成 `100`、把 `#ABCDEF` 归一成 `#abcdef`、把越界坐标 clamp 到边界。关键是：广播出去的是**归一化后的全量图形**，而不是原始 op。这样每个客户端拿到的都是同一个已归一的值，不需要自己再算一遍（虽然它也会算，因为共用 `protocol.js`）。

另外两个工程上的必要性：**持久化**（服务端重启后房间还在）和**广播**（N 个客户端两两直连需要 N² 条连接）。

### 6.5 四条铁律

架构审查阶段识别出四类「看起来能跑，但会在特定时序下永久分叉」的坑。它们都写在代码注释里，因为破坏任何一条只需要改一行：

**铁律一：广播和 ack 都必须带归一化后的全量图形，不能带 patch。**

如果广播只带 `{patch}`，客户端需要自己 merge 一次。而客户端的 merge 结果依赖它本地的当前值——如果它本地因为某种原因（比如刚重连、快照还没到）是旧值，merge 出来的结果就和服务端不同，且这个差异会永久保留（因为戳相同，之后谁也不肯覆盖）。

**铁律二：`lastAppliedSeq` 只由快照和广播推进，绝不由 ack 推进。**

```js
// net.js 顶部注释
// 1. lastAppliedSeq 只由「快照」和「广播 op」推进，绝不由 ack 推进。
//    否则 ack(seq=10) 会把还在途的 seq=9 当成重放丢掉。
```

反例：客户端连发 op₁、op₂，服务端依次处理产生 seq=1、seq=2。如果 ack 先于广播到达（网络乱序或服务端实现顺序不同），`lastApplied` 被 ack 推到 2，然后广播 seq=1 到达，被 `if (msg.seq <= this.lastApplied) return` 当成重放丢弃——op₁ 的修改永久丢失，两端分叉。

**铁律三：比较键必须含 `opId`，且 `ver` 在入队那一刻就冻结。**

```js
// store.js 顶部注释
// 所有 op 的 ver 在「入队那一刻」就冻结，重试不会重算。
// 一旦重算，两端对同一个逻辑操作会得到不同的戳，最终状态就会分叉。
```

如果重发时重算 `ver`，同一条逻辑操作就有了两个不同的戳，合并时会被当成两次独立的写——不仅结果可能不同，撤销栈也会错乱。

**铁律四：先落盘再广播；快照构建完成后才把连接注册进广播集合。**

顺序反过来就是：广播已发出、客户端已应用、服务端崩溃、重放时没有这条 op——客户端认为 `seq=5` 对应状态 X，服务端重放后 `seq=5` 对应状态 Y。序号相同但内容不同，是最难排查的一类 bug。

## 7. 冲突处理

### 7.1 冲突分类

| 场景 | 例子 | 处理 | 结果 |
| --- | --- | --- | --- |
| 并发改**不同字段** | A 改颜色，B 挪位置 | 字段级 LWW，字段集合不相交 | **两者都保留** |
| 并发改**同一字段** | A、B 同时拖同一个图形 | 字段级 LWW，戳大者胜 | 一方的位置生效，另一方被覆盖（可撤销回来） |
| 并发**删除 vs 编辑** | A 删除，B 同时在改 | 墓碑参与比较，版本高者胜 | 通常删除生效；若 B 的版本更高则图形保留并带 B 的修改 |
| 离线 op **版本落后** | B 离线改，A 在线改了很多次 | 服务端 merge 后 `changed=false`，回 `accepted:false` + 权威态 | 客户端先采用权威态，再用 `max(本地, 权威)+1` 重放一次（rebase） |
| **重复投递** | 重连重发、网络重传 | `opId` + 指纹幂等 | 回旧 ack，不重复应用 |
| 同 `opId` **不同内容** | 客户端 bug / 伪造 | 指纹比对失败 | `OPID_CONFLICT` + 强制重拉 |
| **撤销与他人修改** | A 撤销，B 已改过同一字段 | 撤销生成「当前版本+1」的新 op | 撤销总是生效（版本最高） |

### 7.2 并发改不同字段：两个都保留

这是字段级 LWW 最核心的价值，也是现场演示最有说服力的一幕。

A 把矩形从 `x=299` 拖到 `x=120`（产生 `patch: {x: 120}`，`ver = maxVersion+1 = 4`），几乎同时 B 把填充色改成 `#fde68a`（`patch: {fill: '#fde68a'}`，`ver = 4`）。

两个 op 的 `ver` 都是 4，`clientId` 不同。合并时：

- `x` 字段：只有 A 写了，取 A 的值 → `120`
- `fill` 字段：只有 B 写了，取 B 的值 → `#fde68a`
- 其他字段：都没写，保持原值

结果：`x=120` **且** `fill=#fde68a`。两个修改都保留。

如果是整图形 LWW，B 的 `clientId` 字典序更大（或更小），胜者会带着自己那一版的**完整**图形覆盖，另一个人的修改消失。

### 7.3 并发改同一字段：戳大者胜

A、B 同时拖同一个图形到不同位置，都是 `ver = 4`。比较 `clientId` 字典序，大的赢。

这个结果是「任意但确定」的：所有客户端都会算出同一个答案（收敛性保证），但用户可能觉得「我拖的位置被抢了」。工程上的补偿手段：

- 撤销栈仍然有效——被覆盖的一方按 Ctrl+Z 会生成 `ver = 5` 的新 op，一定生效
- 拖动过程中不逐帧发 op，只在 60ms 节流点提交，减少无意义的中间版本竞争
- 一次拖动只登记**一条**撤销记录（`recordUndo` 批量），撤销体验符合直觉

要做到真正的「意图保留」（把两人的位移叠加）需要 CRDT 的位置类型，见 [第 11 章](#11-已知不足)。

### 7.4 删除 vs 编辑

删除是 `patch: {deleted: true}` 加一个更高的 `ver`，所以它和普通字段修改走完全相同的比较逻辑，不需要特判。

- 如果删除的 `ver` 更高 → 图形在所有端消失
- 如果离线端的 `patch` 版本更高（离线端一直在改，版本涨得比在线端快）→ 图形保留，并带上离线端的修改

第二种情况看起来反直觉（删除了又出现），但它符合 LWW 的语义：后写的赢。而「删除」这个动作本身的版本比「修改」旧，说明修改发生在删除之后——从因果上是对的。

关键是不会出现「一半客户端显示、一半不显示」的分叉，因为 `deleted` 是一个普通字段，参与同一套合并。

### 7.5 离线 op 版本落后

B 离线时把图形改成 `x=50, ver=5`。期间 A 在线改了 3 次，服务端版本涨到 `ver=8`。

B 重连后发来 `ver=5` 的 op。服务端 `mergeOp` 逐字段比较，所有字段的戳都更小，合并结果 `shapesEqual(current, next) === true`，于是：

```js
// room.js
if (!changed) {
  // 没产生状态变更（例如离线 op 版本落后于在线编辑）：回权威态让客户端自我修正
  return { ok: true, accepted: false, duplicate: false, shape: current, seq: null };
}
```

注意返回的是 `ok: true, accepted: false`，不是错误。因为这条 op 本身合法，只是没有效果——把它当错误会让客户端反复重试。

客户端收到 `accepted: false` 时不是简单丢弃，而是「先对齐、再重盖」：

```js
// net.js: _onAck
this.store.adoptAuthoritative(msg.shape);            // 先采用权威态
const retried = this.store.rebase(op, msg.shape);    // 再把这条修改盖上去
```

```js
// store.js: rebase —— 内容不变、换新 opId、ver 取两边最大 +1
ver: Math.max(maxVersion(current), maxVersion(serverShape)) + 1
```

**为什么不能直接丢弃**：`ver` 是「入队那一刻本地版本 + 1」冻结下来的。离线端本地副本落后几版，
算出的 `ver` 必然输给在线端——但这条修改在因果上是**更晚发生**的（用户是在离线期间改的），
直接丢弃等于「用户离线改的东西凭空消失」，这是真实的丢数据体验。

rebase 之后语义从「版本号大者胜」变成「重连后的写入算一次新写入」：

- 代价：它可能覆盖对方在线期间的修改（仍然是后写者胜，且可以 Ctrl+Z 撤回）
- 只重试一次（`op.rebased` 标记），避免两端来回覆盖变成活锁
- 收敛性不变：重基后的 op 只是一条全新的普通 op，走同一套广播与合并
- 删除不参与重试：删除与编辑的冲突交给版本裁决，避免出现「删了又活」

`adoptAuthoritative` 仍然是**直接覆盖**（不走 merge），因为此时服务端状态就是权威——
客户端的本地值虽然戳更小，但客户端可能因为某种原因还留着它，直接覆盖才能保证对齐。

### 7.6 重复操作

三种重复来源：

1. **重连重发**：客户端不知道自己上次发的到没到，重连后按队列重发
2. **网络重传**：TCP 层已保证不重复，但应用层重试可能重复
3. **用户手抖**：双击提交按钮之类

服务端的处理（`room.js: applyOp` 第 3 步）：

```js
const fingerprint = opFingerprint(op);
const seenFp = this.seen.get(op.opId);
if (seenFp !== undefined) {
  this.stats.duplicates += 1;
  if (seenFp !== fingerprint) {
    // 同 opId 不同内容：说明客户端有 bug 或有人在伪造
    return { ok: false, code: 'OPID_CONFLICT', message: '同一 opId 携带了不同内容', resync: true };
  }
  return { ok: true, accepted: true, duplicate: true, shape: this.shapes.get(op.target) || null, seq: null };
}
```

同 opId 同内容 → 回当前权威态（注意 `seq: null`，不推进任何序号），客户端收到后从队列摘除即可。同 opId 不同内容 → 这是不可能合法发生的情况，拒绝并要求重拉。

`seen` 表有上限（50000），超了按插入顺序淘汰最旧的。这带来一个理论上的漏洞：如果一条 op 在 5 万条之后才被重发，它会被当成新 op 重新应用。但由于合并是幂等的，重新应用同一条 op 的结果和只应用一次相同——**所以这个淘汰是安全的**。这是幂等性带来的额外好处：去重表只是性能优化，不是正确性依赖。

### 7.7 撤销在协作场景里的坑

朴素实现：撤销 = 重放反向 op。在单机上行得通，在协作里必然失效。

假设 A 把 `x` 从 100 改成 200（`ver=3`）。B 随后把 `x` 改成 300（`ver=4`）。A 点撤销，如果重放 `{x: 100, ver: 3}`，服务端逐字段比较发现 `ver=3 < 4`，直接丢弃——**用户点了撤销，什么都没发生**。

正确做法（`store.js: _applyEntry`）：

```js
/**
 * 撤销/重做不重放旧 op，而是用「当前版本 +1」重新生成一条新 op。
 * 否则旧 op 的版本号已经落后，服务端会直接拒掉，用户点了撤销却毫无反应。
 */
const op = this._nextOp({
  kind, target: item.id, patch: { ...spec.patch },
  ver: this._versionOf(item.id),   // 当前最大版本 + 1
});
```

撤销生成 `{x: 100, ver: 5}`，版本最高，一定生效。

代价是撤销**会覆盖别人的后续修改**（A 撤销会连 B 的 300 一起抹掉）。这是 LWW 语义的必然结果，也是 Figma 类产品的实际行为——比「撤销无效」好得多，而且用户能理解「我撤销了一步」。

拖动等连续操作在 `tools.js` 里合并成一条撤销记录，避免撤销一次只回退一个 60ms 节流点。

## 8. 离线与重连

### 8.1 本地持久化布局

| key | 内容 | 作用 |
| --- | --- | --- |
| `wb:doc:<room>` | 带戳图形数组 | 刷新页面立即恢复画面，不用等网络 |
| `wb:queue:<room>` | 待发 op 数组 | 离线编辑不丢，重连后重放 |
| `wb:seq:<room>` | 本端 clientSeq 水位 | 刷新后序号接着涨，不倒退 |

`clientId` 存 `sessionStorage`（每标签页独立），`sessionEpoch` 存 `localStorage`。

**为什么 `clientId` 用 sessionStorage**：如果两个标签页共用同一个 `clientId`，那么同一个人在两个窗口里拖动同一个图形，会产生**戳完全相同**的两条 op（`v` 相同、`c` 相同，`o` 不同——靠 `opId` 打破平局）。虽然全序仍然成立，但裁决结果取决于 `opId` 的字典序，用户会觉得「莫名其妙跳回另一个位置」。每标签页独立 id 让这种情况变成正常的「两个人竞争」，语义清晰。

**为什么 `sessionEpoch` 和 `clientSeq` 用 localStorage**：刷新页面后 `clientSeq` 必须接着涨，否则重放队列里的 op 序号会比服务端高水位小，触发 `SEQ_RESET` 误判。

`_restore()` 里的这行是关键：

```js
const maxQueued = this.pending.reduce((m, op) => Math.max(m, op.clientSeq || 0), 0);
this.clientSeq = Math.max(this.clientSeq, savedSeq, maxQueued);
```

取三者最大值，防止「水位键丢了但队列还在」导致新 op 复用旧序号。

### 8.2 待发队列

- 所有本地编辑**先入队再发送**（`store._enqueue` → `onOp` → `net.sendOp`）
- 在线时 `sendOp` 立即发送；离线时只留在队列里
- 收到广播（自己那条被服务端接受）或 ack → `dequeue(opId)` 摘除
- 队列按 `clientSeq` 升序重放（`takePending` 排序）

**先入队再发送**而不是「发送成功才入队」：如果先发后记，发送瞬间崩溃就会丢这条 op；先记后发，最坏情况是重发一次，而重发是幂等的。

### 8.3 连接状态机

```
         ┌──────── 网络错误 / 服务端关闭 / 心跳超时 ────────┐
         ▼                                                │
      offline ──connect()──► connecting ──onopen──► syncing ──welcome──► online
         ▲                       │                                        │
         │                       │ 失败                                   │
         └───────────────────────┴────────────────────────────────────────┘
                                  （指数退避后重试）
```

| 状态 | 含义 | 行为 |
| --- | --- | --- |
| `idle` | 初始 | — |
| `connecting` | TCP/TLS 握手中 | 本地编辑入队，不发 |
| `syncing` | 已连上，等 `welcome` | 本地编辑入队，不发；收到快照后一次性重放 |
| `online` | 正常 | 编辑立即发送 |
| `offline` | 断开 | 编辑入队；按退避重连 |

`syncing` 是必要的中间态：`onopen` 之后到 `welcome` 之前，服务端还没告诉客户端当前 `serverSeq`。此时如果发 op，op 可能被应用在一个客户端还不知道的状态上，而且 `lastApplied` 是 0，后续广播会被误判为「缺口」。

### 8.4 重连后的对齐流程

```
1. ws.onopen  → state=syncing，发 hello（带 lastSeq，服务端目前不使用，
                                          客户端总是全量拉）
2. welcome    → lastApplied = serverSeq
              → store.replaceAll(shapes)   全量替换本地文档
              → store.replayPendingLocally()  把队列里的 op 重新叠回去
              → state=online
              → net._flushQueue()  按 clientSeq 升序重发队列（客户端令牌桶 30 条/秒 + 32 条在途）
3. 每条 op 的响应：
   - 广播（含发起者）→ 文档更新 + dequeue + lastApplied = seq
   - ack accepted=true  → dequeue
   - ack accepted=false → adoptAuthoritative（版本落后）+ rebase 重放一次
   - error 带 opId     → 从队列摘掉（结构性错误，重试也不会成功）
   - error RATE_LIMITED → 清空在途标记，退避后继续重放（op 重发是幂等的）
```

**为什么要 `replayPendingLocally`**：`replaceAll` 用服务端快照整体替换，会把本地未同步的修改冲掉。叠回队列后，界面在重放的 RTT 期间也显示自己的修改，不会闪一下再回来。

这个叠回是幂等的：如果服务端快照里已经包含某条 op 的效果（说明上次其实发出去了），再 merge 一次结果相同。

### 8.5 退避与抖动

```js
const delay = Math.min(MAX_DELAY, BASE_DELAY * 2 ** this.retries) + Math.random() * 300;
// 500ms, 1s, 2s, 4s, 8s, 15s, 15s, ...  + 0~300ms 抖动
```

**为什么要有抖动**：服务端重启时，所有客户端会在同一时刻断开、同一时刻按相同的退避序列重连，形成同步的「重连风暴」。加 0–300ms 随机量把请求打散。

**为什么要上限**：无限指数退避会让断网 10 分钟后的用户等半小时。15s 上限意味着最坏情况下 15 秒内必然恢复。

**用户可主动加速**：`window.online` 事件、标签页重新可见（`visibilitychange`）、手动点「立即重连」，都会调 `retryNow()` 把 `retries` 归零并立即连接，不等退避。

### 8.6 seq 缺口检测与全量重拉

```js
// net.js: _onOp
if (msg.seq <= this.lastApplied) return;                       // 重放/乱序的旧帧
if (this.lastApplied > 0 && msg.seq !== this.lastApplied + 1) {
  this._forceResync('seq-gap');                                // 中间丢帧
  return;
}
```

缺口意味着「我错过了一些 op，且不知道错过了什么」。继续增量应用会让本地状态永久偏离——因为后续 op 是基于那个我没看到的状态计算的。

`_forceResync` 的做法：`lastApplied = 0`，以 4002 关闭连接，60ms 后重连拉全量快照。60ms 的延迟是为了让服务端的 `close` 处理先完成（避免旧连接的 `leave` 事件在新连接 `join` 之后到达，导致成员列表闪一下）。

`bootEpoch` 不匹配时也触发重拉：服务端每次启动生成新的 `bootEpoch`，客户端发现收到的广播带不同的 epoch，说明服务端重启过，内存状态可能是从磁盘重建的，必须重新对齐。

### 8.7 服务端重启

`server/index.js` 启动时：

```js
export const BOOT_EPOCH = `${Date.now().toString(36)}-${shortId(6)}`;
```

房间懒加载（第一次有人 `hello` 时才 `new Room().load()`），`load()` 从 JSONL 重放：

```js
// store.js
for (const line of lines) {
  try {
    const entry = JSON.parse(line);
    shapes.set(entry.shape.id, entry.shape);   // 后写覆盖前写
    seq = Math.max(seq, entry.seq);
  } catch { truncated += 1; }                  // 坏行跳过
}
```

JSONL 天然是「快照 + 增量」：每一行都是某个图形在某时刻的**全量**状态（不是 patch），所以重放时后写覆盖前写就得到最终状态，不需要按 seq 排序，也不需要反向应用。

**尾行截断修复**：进程崩溃可能留下半行 JSON。这半行如果留在文件里，下一次 `append` 会把它和新数据粘成一行新的坏数据，一条坏行变成两条。所以加载时检测到坏行就立刻用内存态原子重写整个文件：

```js
if (truncated > 0) {
  // 崩溃留下的半行会与下一次 append 粘成一行新的坏数据，
  // 因此加载后立刻用内存态重写文件（原子 rename）。
  this.compact(roomId, [...shapes.values()], seq);
  this.lineCounts.set(roomId, 1);
}
```

压缩用 `写临时文件 → fsync → rename`，rename 在同一文件系统内是原子的，不会出现「压缩到一半崩溃导致文件损坏」。

压缩触发条件：日志行数超过 500（`config.compactAfterLines`）。500 行 × 平均 300 字节 ≈ 150 KB，重放耗时可忽略。

### 8.8 多房间治理

服务端从一开始就是多房间的（`Map<roomId, Room>` + 懒加载），但「访客可以自己建房」把房间从「开发者手工指定的几个」变成了「用户随时可创建的资源」，于是四件事必须补上。

**① 房间号大小写归一**

房间号同时承担两个角色：内存里的 Map key，和磁盘上的文件名（`data/<roomId>.jsonl`）。而 NTFS / APFS 大小写不敏感——`?room=Team` 与 `?room=team` 在内存里是两个不同的 `Room`，在磁盘上却是**同一个文件**，重启后两份数据混进一个日志。

归一化放在协议层，客户端与服务端共用同一份实现：

```js
// shared/protocol.js
export function canonicalRoomId(raw) {
  return typeof raw === 'string' ? raw.trim().toLowerCase() : '';
}
```

三个入口都要用它：`getRoom()` 建 key、`normalizeOp()` 归一化 op 里的 `roomId`（否则客户端带着大写房间号进来，op 会被 `ROOM_MISMATCH` 全部拒掉）、`Store.fileOf()` 拼文件名（纵深防御）。

**② 空闲房间回收**

懒加载的代价是「只增不减」：每个 `Room` 常驻内存，还各带一个 `seen` 去重表和 `hwm` 高水位表。有人建房没人删，内存就随房间数线性增长。

```js
// 每分钟扫一次；无连接且空闲超过 TTL 才卸载
isIdle(now, ttlMs) {
  return this.members.size === 0 && now - this.lastActive >= ttlMs;
}
```

关键取舍：**只卸载内存，不删磁盘**。jsonl 保留，下次有人进来重新 `load()` 就恢复了——所以回收对用户完全无感，不需要做「房间是否还在」的迁移逻辑。`lastActive` 在 join / leave / presence 时刷新，避免「刚走的人马上回来」正好撞上回收。

**③ 建房配额**

「建一万个空房间」是最省力的 DoS：一次 `hello` 就能在内存里种一个 `Room`。两道闸：

- 全局：`rooms.size >= MAX_ROOMS`（默认 500）直接拒 `ROOM_LIMIT`
- 单 IP 滑动窗口：每小时 60 个新房间，超了回 `ROOM_RATE_LIMITED`

**只对「真的会新建」的房间计数**——进已有房间不消耗配额。这一条很关键：分享链接本来就是给一群人点的，如果 join 也算配额，第二个点链接的人就会被拦下。

**④ 探测接口与信息暴露的取舍**

「打错一个字就静默建了个空房间」是访客建房最伤体验的失败模式：用户以为数据丢了。解决办法是进房前先探测：

```
GET /api/rooms/:id → { roomId, exists, members, shapes }
```

只回答「在不在 / 几个人 / 多少图形」，**不返回任何图形内容**；房间没加载时也不去 load 它（否则探一下就把整个日志读进内存，探测接口成了放大器，此时 `shapes` 返回 `null`）。按 IP 限流 30 次/分钟，避免被当成房间号枚举器。

同一个理由也适用于 `/api/stats`：它会列出所有房间号和在线人数，等于绕过「房间号即凭证」，因此改为**仅本机回环可访问**，非回环一律 403。

**⑤ 客户端入口**

三件事合起来才能让访客「自己会用」：

| 入口 | 行为 |
| --- | --- |
| 顶栏「新建房间」 | 生成 8 位随机房间号（字符表去掉 `l/o/0/1`，口头传播不易错），整页跳转 |
| 房间输入框 | 输入即探测，显示「已存在 · N 人在线」或「新房间 · 进入后自动创建」；回车进入 |
| 「复制链接」 | 复制带 `?room=` 的完整 URL，即邀请链接 |

输入中文时**不静默回落到 demo**：`slugRoomName()` 会把非 ASCII 剥掉，剥完如果只剩无意义残渣（`我的白板 2026` → `2026`）就判定为无效，改发一个随机房间号并提示原因。demo 是所有人都能看到的公共房间，把打错字的访客丢进去比直接报错更糟——他会看到别人的内容，还以为自己建了新房。

## 9. 异常与安全

### 9.1 输入校验清单

所有进入系统的数据都要过一遍校验，且**客户端与服务端用同一份代码**。

| 层次 | 校验内容 | 失败处理 |
| --- | --- | --- |
| 传输层 | 帧掩码、RSV 位、操作码、分片合法性、UTF-8 严格性、帧大小 | 关闭连接（1002/1003/1007/1009） |
| 消息层 | 是合法 JSON、是对象、有 `type` 字段 | `BAD_JSON` / `BAD_MESSAGE` |
| 身份层 | `roomId` / `clientId` / `sessionEpoch` 格式；op 与连接的绑定 | `BAD_*` / `ROOM_MISMATCH` / `CLIENT_MISMATCH` |
| op 层 | `opId` 是 uuid、`kind` 合法、`ver` / `clientSeq` 是正整数、`target` 是 uuid | `BAD_*` |
| 字段层 | 白名单、类型、数值范围、颜色正则、文本码点长度、patch 字段数 | `BAD_*` / `UNKNOWN_FIELD` / `PATCH_TOO_LARGE` |
| 语义层 | `create` 必须带几何字段、图形类型不可变、房间上限 | `MISSING_GEOMETRY` / `TYPE_CONFLICT` / `ROOM_FULL` |

**数值越界走 clamp 而不是拒绝**，这是一个刻意的选择：

```js
// protocol.js: normalizeField
// 数值越界走 clamp（不是拒绝）——因为 clamp 是幂等的，两端执行结果必然一致；
// 而 NaN / Infinity / 非法颜色 / 超长文本属于「无法可靠解释」的输入，直接拒绝。
```

用户把图形拖到画布外 20 万像素，clamp 到 10 万比报错更友好，而且因为 clamp 幂等，两端算出来一定一样。但 `NaN` 无法参与任何比较（`NaN > 0` 和 `NaN < 0` 都是 false），会污染合并逻辑，必须拒绝。

**文本按码点计长**（`[...raw].length`）而不是 `raw.length`：后者会把一个 emoji 算成 2，导致「2000 字符上限」对不同内容有不同含义，且截断可能切断代理对产生乱码。

**客户端也不信任服务端**：`store.applyRemote` 里对收到的 shape 也跑一遍 `normalizeShape`。多一层校验的成本可忽略，但能防住「服务端有 bug 或者中间人」的情况。

### 9.2 限流

令牌桶，每连接独立：

```js
// 60 条/秒，突发 120
conn.bucket.tokens = Math.min(LIMITS.RATE_BURST, conn.bucket.tokens + elapsed * LIMITS.RATE_PER_SEC);
if (conn.bucket.tokens < 1) {
  conn.violations += 1;
  if (conn.violations >= LIMITS.MAX_PROTOCOL_VIOLATIONS) conn.close(1008, 'rate limit exceeded');
  return false;
}
```

60/s 对正常编辑足够（拖动已做 60ms 节流，最多约 16 条/秒），但能挡住脚本刷屏。连续违规 20 次才断开，避免因为突发拖动被误杀。

### 9.3 资源上限

| 资源 | 上限 | 超限行为 |
| --- | --- | --- |
| 单帧大小 | 64 KB | 1009 关闭 |
| 房间可见图形 | 5000 | `ROOM_FULL` 拒绝 |
| patch 字段数 | 12 | `PATCH_TOO_LARGE` 拒绝 |
| 文本长度 | 2000 码点 | `STRING_TOO_LONG` 拒绝 |
| `seen` 去重表 | 50000 条 | FIFO 淘汰（安全，见 7.6） |
| 待发队列 | 5000 条 | 前端限制 |
| pending 缓冲（快照期间） | 配置值 | 1008 关闭 |

所有上限都只在服务端强制执行，客户端的上限只是为了提前给用户反馈。

### 9.4 连接生命周期

```
upgrade → 握手校验 → 注册连接 → 启动 hello 超时计时器（10s）
       → 收到 hello → 绑定房间 → 发快照 → 标记 joined
       → 消息循环（每条先过限流）
       → close（任一方发起或超时）→ 清理成员 → 广播 leave
```

**hello 超时**：连接建立后 10 秒内不 `hello` 就断开。否则扫描器可以开一堆空连接耗尽文件描述符。

**空闲清扫**：每 20 秒扫一遍，60 秒无任何活动的连接主动断开（1001 Going Away）。这处理了「浏览器标签页被系统休眠后 TCP 连接还挂着」的情况——客户端那边心跳也会超时，但服务端不能指望客户端一定会自己断。

**重复 hello**：已加入房间的连接再发 `hello`，返回快照但不换房间、不重复广播 join。这是为了容忍客户端重连逻辑的边界情况。

### 9.5 静态资源安全

```js
// static.js: resolveSafe
// 路径穿越：/client/../../etc/passwd
```

只挂载 `/client/` 和 `/shared/` 两个前缀，解析后必须仍在根目录内，否则 403。同时 `req.url` 要先剥掉 query 和 hash：

```js
const urlPath = (req.url || '/').split('?')[0].split('#')[0] || '/';
```

（这个 bug 在开发中出现过：`/?room=xxx` 返回 404，因为 `/` 带 query 后匹配不上入口规则。）

### 9.6 崩溃恢复

| 故障 | 恢复机制 |
| --- | --- |
| 进程崩溃（写盘中途） | 尾行截断修复 + 立即压缩重写 |
| 进程崩溃（广播后落盘前） | 不可能：顺序是「先落盘再广播」 |
| 客户端崩溃 | 重连后从快照 + 队列恢复 |
| 客户端清缓存 | `clientSeq` 归零 → `SEQ_RESET` → 全量重拉（丢的是未同步的本地编辑，但服务端数据完好） |
| 网络分区 | 两侧继续工作，恢复后靠 LWW 合并 |
| 服务端重启 | `bootEpoch` 变化 → 所有客户端全量重拉 |

### 9.7 启动期异常

进程启动失败是最容易被忽略的一类「异常处理」——它发生在任何业务逻辑之前，却决定了别人第一次运行这个项目时的体验。

| 情况 | 处理 |
| --- | --- |
| 端口被占用（`EADDRINUSE`） | 默认**自动顺延**（8787→8788…，最多 10 个），每次打印一条 warn 说明原因，最终打印实际地址；10 个全占用才失败退出 |
| 需要固定端口（部署 / 反向代理 / CI） | `STRICT_PORT=1` 关闭顺延，冲突即退出 |
| 想让系统分配 | `PORT=0`（Node 原生语义），启动日志打印实际端口 |
| 低端口无权限（`EACCES`） | 直接提示「1024 以下需要管理员权限，换高位端口」 |
| 以上任一失败 | 打印可复制的排查命令（PowerShell 查端口占用并 `Stop-Process`、`$env:PORT=…` 换端口），以退出码 1 结束，**不抛原始堆栈** |
| 运行期 `error` 事件 | 挂常驻监听只记日志，避免变成 unhandled `'error'` 把进程打挂 |

设计取舍：**为什么默认顺延而不是直接报错**。端口冲突的成因几乎总是「上次的实例没关干净」，属于使用者不关心、也不该被要求理解的内部细节。让程序自己绕过去，比让人去查 PID 更符合「第一次运行就该跑起来」的目标。代价是端口可能漂移，所以每次顺延都打一条明确的 warn，并且保留 `STRICT_PORT=1` 给需要确定性地址的场景。

实现上有个细节：`listen` 失败后 `http.Server` 不会停留在 listening 态，因此可以继续用同一个实例重试下一个端口，不需要销毁重建。测试用两个真实子进程验证了「A 占住端口 → B 顺延并正常工作 → A 不受影响」以及 `STRICT_PORT=1` 的退出码与提示语（`tests/restart.test.js` 后两例）。

第 8 项值得单独说：断网**不是**调用应用内的「模拟断网」开关。A 页与服务器之间挂了一个可控 TCP 代理，断网时把在途连接全部 RST、并掐掉之后每一个新连接，所以断网期间的重连是**真的失败**，恢复后是**真的重连**。第 8 项断言的是「此时新请求确实发不出去」，用来防止测成一条假路径——早先版本用 CDP 的 `Network.emulateNetworkConditions`，实测它只拦新请求，已建立的 WebSocket 依然是 OPEN、`send()` 也照样成功，页面根本感知不到断网。

第 21 项是很多项目会漏掉的：即使所有功能断言通过，只要控制台有异常，就说明有代码路径在静默失败。断网期间浏览器必然报「连接被重置」，那正是被测行为本身，只豁免这几类，其余错误照样计入。

第 16 项来自一个真实 bug：空状态面板淡出时只设了 `opacity: 0`，元素仍留在布局里继续吃点击，把画布正中央约 300×200 的区域变成死区——画笔、框选、双击在那里全部失效，而当时的单元测试全绿。加上 `visibility: hidden` 之后才真正退出命中测试。

### 10.4 两个致命缺陷的复盘

这两个 bug 有一个共同特征：**单元测试全绿，但功能在真实浏览器里完全不可用**。它们暴露的是测试策略本身的漏洞，比 bug 本身更值得记录。

#### 缺陷一：WebSocket 握手 GUID 写错

**现象**：用自己写的测试客户端能连上，服务端日志正常，所有同步测试通过。但用浏览器打开页面，控制台报：

```
WebSocket connection to 'ws://localhost:8787/ws' failed:
Error during WebSocket handshake: Incorrect 'Sec-WebSocket-Accept' header value
```

**根因**：RFC 6455 的握手魔数常量写错了最后一段：

```js
// 错误
const GUID = '258EAFA5-E914-47DA-95CA-5AB0DC85B11F';
// 正确
const GUID = '258EAFA5-E914-47DA-95CA-C5AB0DC85B11';
```

`C5AB0DC85B11` 被写成了 `5AB0DC85B11F`——少了一个 `C`，末尾多了一个 `F`，长度一样，看起来毫无破绽。

**为什么测试没抓到**：`tests/ws.test.js` 里的测试客户端和服务端**共用同一个 GUID 常量**。两边用同一个错误值，算出来的 `Sec-WebSocket-Accept` 自然「对得上」——测试通过得毫无悬念，而且自洽。这是一个典型的「用被测对象验证被测对象」的错误。

**定位过程**：

1. 怀疑 SHA1 实现有问题 → 用 Python 独立复算，结果与服务端一致 → 排除
2. 怀疑中间有代理改写 → 抓包确认 header 原样到达 → 排除
3. 找 RFC 6455 官方的 key/accept 测试向量对比 → 发现不匹配
4. 抓 RFC 原文核对 GUID 字面量 → 定位到常量拼错

**修复**：

1. 导出 `computeAccept(key)` 供测试直接调用
2. 用 RFC 6455 §1.3 的官方向量钉死：

```js
// 客户端 key: dGhlIHNhbXBsZSBub25jZQ==
// 期望 accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
assert.equal(computeAccept('dGhlIHNhbXBsZSBub25jZQ=='), 's3pPLMBiTxaQ9kYGzzhZRbK+xOo=');
```

3. 加一个用 **Node 内置 `WebSocket`（undici 实现）** 的真客户端握手测试——它不会用我们的常量，是真正的第三方验证

**教训**：涉及标准协议的实现，必须用**官方测试向量**或**独立第三方实现**验证，绝不能只用自己的客户端自测。测试的价值取决于它有多「不同」，而不是它有多「多」。

#### 缺陷二：合并函数用错语义

**现象**：页面能加载，能画图，图形出现在自己屏幕上，但**任何实时同步都静默失效**。控制台报：

```
Uncaught TypeError: Cannot convert undefined or null to object
```

**根因**：`store.applyRemote` 里用错了合并函数：

```js
// 错误
this.shapes.set(incoming.id, mergeOp(current, incoming));
```

`mergeOp(shape, op)` 期望第二个参数是 **op**（内部读 `op.patch` 和 `op.ver`），但这里传的是 **shape**（字段在 `shape.fields` 里，没有 `patch`）。于是 `Object.keys(op.patch)` 对 `undefined` 调用，抛异常。

异常被 `net.js` 的 `try/catch` 捕获，只记了一行日志——所以界面不崩，只是「什么都不会发生」。这是最糟的失败模式：用户以为功能坏了，开发者以为代码跑通了。

**为什么测试没抓到**：`tests/` 里所有用例都直接测 `shared/merge.js` 的函数，以及服务端的 `room.applyOp`。**客户端的 `DocStore` 一层完全没有单元测试**，只靠端到端覆盖——而端到端在这个阶段还没写。

**修复**：

```js
// 正确：图形 vs 图形
this.shapes.set(
  incoming.id,
  current ? mergeShape(current, incoming, { authoritative: true }) : incoming,
);
```

并新增 `tests/client-store.test.js`（9 个用例），把客户端状态层纳入单测覆盖。

**教训**：测试覆盖率不是「测了多少行」，而是「每个模块是否有独立的验证入口」。只测底层函数、靠端到端兜住上层，等于让端到端承担它不该承担的职责——它慢、脆弱、定位困难，而这次的 bug 恰恰在它覆盖不到的地方。

这两个 bug 之后，项目的测试策略调整为：**每个有独立职责的模块都必须有直接的单测入口**，`client/js/store.js` 和 `client/js/net.js` 是重点。

## 11. 已知不足

诚实列出，因为知道边界比假装没有边界更有价值。

### 11.1 单进程内存态

房间状态在进程内存里（`Map<roomId, Room>`），只支持单实例部署。多实例需要：

- 广播改为 Redis Pub/Sub 或 NATS
- 或粘性会话（同一房间的客户端必须落到同一实例）
- 持久化从 JSONL 换成数据库

当前实现的数据量上限（单房间 5000 图形）也是基于内存假设设定的。

### 11.2 无鉴权

房间号即凭证，任何人拿到链接就能进、能改、能删。生产环境需要：

- 在 `hello` 阶段校验 token（JWT / session cookie）
- 房间级权限（只读 / 可编辑）
- 操作审计

协议层已经预留了位置（`hello` 消息可以扩展 `token` 字段），但没实现。

### 11.3 字段级 LWW 不是「意图保留」

两人同时拖同一个图形，结果是「版本大的赢」，而不是「位移叠加」。要做到后者需要：

- CRDT 的位置类型（如 Yjs 的 `Y.Map` + 相对定位）
- 或 OT 的转换函数（需要中心化服务器定义转换规则）

复杂度高一个量级。本项目的取舍是：**用明确、可解释、可测试的语义，换取实现复杂度**。LWW 的语义用户能理解（「后改的赢」），OT 的语义连实现者都经常搞错。

### 11.4 文本编辑是整串替换

两人同时编辑同一段文本，LWW 会让后写的**整段**覆盖先写的。字符级协同需要 OT 或序列 CRDT（如 Yjs 的 `Y.Text`）。

实际影响有限：白板上的文本通常很短，且「两人同时改同一段文字」比「两人同时改同一张图的同一字段」概率低得多。

### 11.5 历史无限增长

- `seen`（去重表）有 50000 上限并 FIFO 淘汰
- JSONL 超过 500 行压缩成快照
- 但没有做增量快照、时间旅行、版本对比

想做「历史回放」需要保留 op 序列（而不是只保留快照），存储成本高得多。

### 11.6 presence 是「尽力而为」

光标位置不做持久化、不做补发、不做顺序保证。丢一帧光标完全无害——下一帧就修正了。这是刻意的设计：presence 走的是「高频、可丢」通道，和文档 op 的「低频、必达」通道在语义上分开。

### 11.7 移动端未适配

触摸事件只做了基础支持（单指绘制、双指缩放），没有做手势优化、长按菜单、移动端工具栏布局。桌面端体验完整。

### 12.8 ping / pong

```json
{ "type": "ping", "t": 1730000015000 }
```

```json
{ "type": "pong", "t": 1730000015000, "serverSeq": 8 }
```

`pong` 带 `serverSeq` 是为了让调试面板能在心跳里顺带显示服务端进度，减少一次额外请求。
